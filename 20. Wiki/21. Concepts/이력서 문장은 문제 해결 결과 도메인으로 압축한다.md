# 이력서 문장은 문제 해결 결과 도메인으로 압축한다

## 영상에서 가져온 관점

[[2026-10-11-YouTube-이력서 그냥 제가 써드릴게요. 가져가세요]] 0:31~1:43과 [[2026-10-11-YouTube-취준 이력서 10분만에 방향성 제대로 알려줌]] 6:56~8:02는 기술 이름 대신 **문제·해결·결과·도메인**을 짧게 연결하라고 조언한다. [[2026-10-11-YouTube-이력서 처음 쓰시는 분들, 이 구성 그냥 그대로 쓰시면 됩니다]] 1:32~2:44는 신입에게 기본 구현과 역할도 보여주는 프로젝트형 이력서를 권한다.

## 한두 줄 작성 틀

> [어느 업무/기능]에서 [실제 발견한 문제]를 [본인 판단·구현]으로 해결하고, [검증 조건]에서 [확인된 변화]를 확인했다.

도메인은 서비스 이름만 뜻하지 않는다. 어떤 조회·이체·대사 업무에서 문제가 생겼는지 문장 안에 드러내는 것이다. “Redis 적용”, “API 구현”만으로 원인·역할·효과를 대신하지 않는다.

| 보유 증거 | 문장에 쓸 것 | 아직 쓰지 않을 것 |
|---|---|---|
| 기능을 구현·테스트함 | 목적·본인 구현·확인한 동작 | 측정하지 않은 UX 개선·성능 향상 |
| 실패를 재현하고 수정함 | 실패 조건·원인·수정·회귀 검증 | 실제 운영 장애였다는 표현 |
| 전후 성능을 동일 조건으로 측정함 | 지표·조건·전후·정확성·한계 | 환경이 다른 수치의 단순 개선율 |
| 이상형 설계만 있음 | 목표 문서의 미래형 | 제출 이력서의 과거형 성과 |

## 현재 프로젝트의 작성 예시 (목표 틀)

> [동시 출금 조건]에서 [잔액 규칙 위반]을 재현하고 [선택한 경합 제어]를 적용해, [반복 횟수·데이터 조건]에서 [오류 건수 전→후]를 검증했다.

대괄호는 실제 구현·실험 뒤 채운다. 모의 기관·합성 명세·로컬 테스트를 금융 실서비스 성과로 바꾸지 않는다. 기본 구현 항목도 필요하면 “중복 키 요청의 결과를 조회하는 API를 구현하고 [예외 조건]을 확인”처럼 기능의 이유와 검증 동작을 적는다.

[[2026-10-11-YouTube-면접관이 ‘얘는 다르다’ 느끼는 이력서 작성법 여기요.]] 1:50~3:10의 기술 차별화 예시는 정답이 아니라고 발표자가 명시했다. 남과 다른 기술보다 **이 제약에서 왜 이 선택을 했는가**가 먼저다.

> [!note] Bias Check
> Counter-argument: 모든 구현에 문제 해결 이야기가 필요한 것은 아니다. 기본 구현·운영·협업은 목적과 본인 기여를 짧게 보여줘도 된다.
> Data gap: 영상의 350ms→40ms는 예시이며 사용자 측정값이 아니다. 실제 결과가 없으면 숫자를 만들지 않는다.
