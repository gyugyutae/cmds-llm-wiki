# 컴퓨팅 사고의 추상화와 분해

## Core Idea

개발자의 핵심 역할은 코드를 많이 타이핑하는 것이 아니라 현실의 모호한 문제를 컴퓨터가 처리할 수 있는 구조로 바꾸는 것이다. 그 과정의 바깥쪽에는 **추상화**, 안쪽에는 **분해**가 있다.

```text
현실의 문제
→ 추상화: 경계·입력·출력·제약·인터페이스 정의
→ 블랙박스
→ 분해: 하위 문제·의존성·순서·예외 상황 설계
→ 구현
→ 검증: 출력과 실제 목적이 맞는지 확인
```

추상화는 세부 사항을 무시하는 일이 아니라, 현재 목적에 필요한 세부 사항과 숨겨도 되는 세부 사항을 구분하는 일이다. 분해는 작업 목록을 길게 적는 일이 아니라 각 조각이 독립적으로 이해·구현·검증될 수 있게 경계를 정하고 연결 관계를 밝히는 일이다.

## 김규태의 개발자 원칙

[[2026-07-26-Kim-Gyutae-AI-Era-Developer-Reflection]]에서 김규태는 이 관점을 AI 시대에 가장 필요한 개발자 역량으로 받아들였다.

> 개발자는 단순히 코드를 짜는 사람이 아니라 현실 문제를 입력과 출력으로 추상화하고, 블랙박스 내부에서는 문제를 최대한 잘게 분해해 해결 방법을 고민하는 사람이다.

이는 외부 전문가의 검증된 정의가 아니라 사용자 본인의 개발자 정체성과 성장 방향이다. 앞으로 프로젝트와 면접에서는 “무엇을 구현했는가”뿐 아니라 “현실 문제를 어떤 구조로 바꾸었고, 어디까지 분해했으며, 무엇으로 검증했는가”를 보여줘야 한다.

## 추상화 체크

| 질문 | 확인할 내용 |
|---|---|
| 누구의 문제인가? | 실제 사용자와 이해관계자 |
| 원하는 변화는 무엇인가? | 기능이 아니라 성공 상태 |
| 입력은 무엇인가? | 데이터, 사건, 사용자 행동 |
| 출력은 무엇인가? | 관찰 가능한 결과 |
| 제약은 무엇인가? | 시간, 비용, 권한, 성능, 안전 |
| 무엇을 숨길 것인가? | 호출자가 몰라도 되는 구현 세부 |
| 무엇을 드러낼 것인가? | 안정적인 인터페이스와 계약 |

## 분해 체크

| 질문 | 확인할 내용 |
|---|---|
| 가장 작은 검증 가능 단위는? | 독립적으로 테스트할 수 있는 하위 문제 |
| 의존성은 무엇인가? | 먼저 해결돼야 하는 작업과 공유 상태 |
| 순서는 왜 필요한가? | 데이터 흐름과 상태 전이 |
| 실패 지점은 어디인가? | 입력 오류, 권한 실패, 타임아웃, 경계값 |
| 다시 합칠 때 계약은? | 모듈 사이 입력·출력과 오류 처리 |

## AI와의 역할 분담

AI는 블랙박스 내부의 구현 후보, 테스트 사례, 리팩터링 대안을 빠르게 만들 수 있다. 그러나 현실 문제의 경계, 성공 기준, 위험 허용 범위, 결과 검증은 여전히 개발자가 소유해야 한다.

- 사람: 문제 선택, 추상화, 제약과 acceptance criteria, 최종 판단
- AI: 대안 탐색, 반복 구현, 설명, 반례와 테스트 후보 생성
- 사람과 AI 공동: 분해안 비교, 실패 원인 추적, 설계 수정

이 경계는 [[AI-Augmented Developer Positioning]]과 [[Human-AI Knowledge Boundary]]를 구체적인 문제해결 과정으로 연결한다.

> [!note] Bias Check
> Counter-argument: 추상화와 분해만으로 좋은 소프트웨어가 만들어지지는 않는다. 도메인 지식, 사용자 관찰, 구현 기본기, 테스트, 운영, 협업도 필요하다.
> Data gap: 핵심 설명의 출발점인 Gemini 답변은 AI 생성 조언이다. 실제 프로젝트에서 이 프레임이 설계 품질과 문제해결 속도를 높이는지는 프로젝트 로그로 검증해야 한다.
