# 능력 조합으로 희소성을 만드는 전략

## Core Idea

한 분야에서 절대적인 1등이 되지 못하더라도, 서로 보완되는 여러 능력을 실무 수준으로 결합하면 희소한 가치 제안을 만들 수 있다는 개인 커리어 전략이다.

김규태에게 이 전략은 개발 기본기를 얕게 만들기 위한 핑계가 아니다. 중심축은 개발이고, 다른 능력은 개발 결과를 더 잘 선택·설명·검증·확산하기 위해 붙는다.

```text
개발 기본기
× 시스템·성능 사고
× 특정 도메인
× AI 워크플로 설계
× 커뮤니케이션·리더십
× 콘텐츠·세일즈 감각
= 김규태만의 증거 조합
```

## Current Stack

아래 `현재 증거`는 연결된 기록의 위치이며, 해당 역량의 객관 수준을 인증하는 표가 아니다. 각 프로젝트 페이지의 verification boundary를 함께 읽는다.

| 능력 | 현재 증거 | 다음 강화 |
|---|---|---|
| 개발·성능 | [[financial-order-latency-lab]], [[Graduation-elasticsearch]] | 재현 로그와 수치 보강 |
| 제품 문제 정의 | [[cuee]] | 사용자 테스트와 권한 심사 기록 |
| AI 워크플로 | [[harness]], Threads automation | AI 경계와 생산성 효과 측정 |
| 리더십·교육 | 동아리 대표·부대표, 백엔드 세션 | 회의록, 자료, 팀원 피드백 |
| 세일즈·심리 | 독서 큐와 관심 | 실제 행동 실험 |
| 도메인 | 금융·백엔드·반도체·드론 탐색 | 한 축의 깊은 현장 지식 |

## Selection Rule

새 능력을 추가하기 전에 세 가지를 확인한다.

1. 중심 개발 역량을 강화하거나 시장에 전달하는가?
2. 현재 프로젝트에서 바로 실험할 장면이 있는가?
3. 결과를 Raw Source와 수치로 남길 수 있는가?

세 질문에 답하지 못하면 흥미로운 취미일 수는 있어도 현재의 커리어 스택 우선순위는 아니다.

## Evidence Over Labels

“상위 25%”는 검증된 통계가 아니라 영상이 제안한 직관적 표현이다. 실제 희소성은 자칭 수준이 아니라 결과의 조합으로 보여준다.

- 기술 설명을 비개발자에게 전달한 사례
- AI가 만든 결과를 직접 검증한 사례
- 사용자 문제로 제품 방향을 바꾼 사례
- 성능 병목을 수치로 찾아 수정한 사례
- 팀이 움직이도록 운영 체계를 만든 사례

> [!note] Bias Check
> Counter-argument: 너무 많은 능력을 동시에 쌓으면 어느 것도 채용 기준에 도달하지 못할 수 있다. 능력 조합은 깊이 부족을 숨기는 표현이 되어서는 안 된다.
> Data gap: 각 능력의 객관 수준과 조합이 실제 취업·소득 성과로 이어지는지는 아직 검증되지 않았다.
