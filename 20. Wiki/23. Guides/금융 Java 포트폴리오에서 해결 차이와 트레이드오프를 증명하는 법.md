# 금융 Java 포트폴리오에서 해결 차이와 트레이드오프를 증명하는 법

## 목적과 근거의 구분

사용자는 현재 금융 Java 포트폴리오가 “2단계 정도”라고 생각하며, 같은 문제의 해결 방식에 차이가 드러나는 3단계와 환경·제약·선택·트레이드오프의 타당성을 설명하는 4단계로 성장하고 싶다고 밝혔다. 이 목표를 이후 학습·실험·포트폴리오 검토의 기준으로 삼는다.

영상 [[2026-10-12-YouTube-개발자 이력서 4단계와 금융 Java 성장 목적]]의 네 단계는 발표자의 경험적 프레임이다. 사용자의 현재 수준을 인증하는 척도나 취업 보장이 아니다. [[financial-lab]]의 구현 기록은 과거 시점의 기록이고 [[금융 백엔드 포트폴리오 5장 원고]]는 목표 원고다. 이번 인제스트에서는 실제 코드·최신 테스트·성능을 확인하지 않았으므로 현재 단계 판정은 보류한다.

## 성장의 기준

| 구분 | 보여줄 내용 | 필요한 증거 |
|---|---|---|
| 2단계: 성과 | 어떤 조건에서 무엇이 얼마나 바뀌었는가 | 고정 환경·전후 결과·오류율·원본 지표 |
| 3단계: 해결 방식의 차이 | 흔한 설명에서 놓친 실패 조건을 어떻게 구분하고 해결했는가 | 재현 가능한 반례·원인·직접 코드/SQL 변경·실패 후 상태 |
| 4단계: 판단의 타당성 | 왜 이 조건에서 이 대안을 골랐으며 어떤 비용을 받아들였는가 | 실제 제약·대안 비교·결정 이유·반증 조건·재검토 기준 |

3단계의 차이는 기술 이름을 바꾸거나 낯선 도구를 추가하는 것만으로 생기지 않는다. 기존 해결이 놓치는 실패 경계를 발견하고, 그 경계까지 확인하는 과정에서 드러난다. 4단계는 선택의 장점뿐 아니라 손해와 적용 한계까지 설명할 수 있어야 한다. 이 문단은 영상과 기존 금융 사례를 연결한 AI 해석이다.

| 사례        | 3단계로 깊게 볼 문제                                | 4단계에서 비교할 선택과 비용                                                 | 확인할 증거                                        |
| --------- | ------------------------------------------- | ---------------------------------------------------------------- | --------------------------------------------- |
| 동시성       | 오류 0뿐 아니라 동일 계좌 집중·양방향 이체에서도 잔액/원장을 보존하는가   | 비관적 잠금·낙관적 잠금/재시도 등의 충돌률·대기·재시도·교착 비용. 실제 DB와 부하에 따라 선택          | 동일 데이터·집중도에서 성공/거절·잔액·원장·p99·락 대기 비교          |
| 원자성       | 예외가 발생했다는 사실과 실제 DB 변경이 취소됐다는 사실을 구분하는가     | 이체·원장을 묶는 트랜잭션 범위와 잠금 유지 시간, 예외 전파/처리 방식. 외부 HTTP 효과까지 취소할 수 있는가 | 출금 후·입금 후·원장 저장 중·커밋 전 실패, 종료 후 별도 DB 연결 재조회  |
| 멱등성·응답 유실 | 타임아웃을 실패로 단정하지 않고 이미 발생한 효과와 미확정 결과를 구분하는가  | 동기 호출과 영속 발송 작업의 복구성·저장 비용·완료 지연. 기관의 키/조회 보장에 따라 가능한 선택이 달라짐    | 커밋 직후 응답 차단·재시작·같은 키 다른 금액·중복 실행, 양쪽 DB 효과 확인 |
| 대사·복구     | 합계 일치가 놓치는 거래별 누락·중복·금액/상태 차이와 지연 명세를 구분하는가 | 전체/청크 처리의 메모리·처리시간·체크포인트 비용, 자동 조정과 검토의 오조정 위험                   | 독립 명세·정답 오류 목록·오탐/미탐·중단 후 재개·복구 후 재대사         |

위 방식이 기존 목표에도 포함되어 있으므로 새 성과라고 주장하지 않는다. [[거래 원장 실험과 대표 기술 글 계획]]의 실험을 실제로 실행하고 본인의 선택 이유를 채우는 것이 남은 일이다. 모의 기관 결과는 실제 금융기관 운영 경험과 구분한다.

## 첫 실행은 원자성 한 사례부터

현재 코드와 테스트를 먼저 읽어 DB/원장 구현 여부를 확인한다. 준비가 안 됐다면 현재 작은 구현 단계부터 진행하고, 준비됐다면 다음 질문을 실험으로 푼다.

**“출금 후 실패했을 때, 예외가 났다는 것 외에 돈과 거래 기록이 원상복구됐음을 어떻게 증명할까?”**

1. 본인이 정상·실패 후 기대 잔액과 원장 상태를 먼저 적는다.
2. 현재 구현으로 출금 후 실패를 재현하고 호출 종료 후 독립 DB 조회로 관측한다.
3. 현재 방식과 대안 하나를 같은 실패 조건에서 비교한다. 이미 정확하면 개선 전 오류를 꾸며내지 않는다.
4. 트랜잭션 경계와 예외 처리의 선택 이유, 구현 복잡도·잠금 비용·외부 효과의 한계를 기록한다.
5. 코드·SQL·실행 명령·커밋·관측값을 연결하고 AI 도움과 본인 판단을 구분한다.

단위 테스트만 통과한 상태를 DB rollback 검증으로 승격하지 않는다. 전체 구현 코드를 먼저 받기보다 예상 → 반례 → 힌트 → 직접 수정 → 검증 순서로 진행한다.

## 선택 하나마다 남길 기록

- **문제·불변조건:** 무엇이 어긋났고 무엇을 반드시 지켜야 하는가?
- **관측:** 어떤 입력·실패 위치·로그/SQL로 원인을 확인했는가?
- **실제 환경·제약:** DB·서버 수·부하·자원·시간·외부 계약 중 확인된 것은 무엇인가? 모르는 것은 미확인으로 둔다.
- **대안 A/B:** 각각 어떤 조건에서 유리하고 어떤 실패/비용이 생기는가?
- **본인 선택·이유:** 현재 조건에서 어떤 기준을 우선했는가?
- **검증:** 동일 조건의 명령·기대값·관측값·실패 결과·원본 근거는 무엇인가?
- **받아들인 비용·한계:** 성능 저하·복잡도·미확정 상태·운영 부담 중 무엇이 남는가?
- **선택이 바뀌는 조건:** 충돌률·부하·기관 보장 등이 어떻게 바뀌면 재검토할 것인가?
- **기여 경계:** 본인이 판단·작성·설명·수정한 부분과 AI 제안/생성 부분은 무엇인가?

## 포트폴리오와 면접에 옮기는 기준

검증 후 문장 구조는 “어떤 조건에서 어떤 실패를 발견했고 → 대안을 어떤 기준으로 비교했고 → 무엇을 선택했고 → 무엇으로 효과를 확인했으며 → 어떤 비용/한계가 남았다”로 정리한다. 지금은 완료형 이력서 문장을 만들지 않는다.

3단계의 완료 기준은 기존 해결이 놓치는 반례와 본인의 변경 지점을 직접 설명·재현·수정하는 것이다. 4단계의 완료 기준은 다른 대안이 더 나아지는 조건과 자신의 선택이 틀릴 수 있는 조건까지 말하는 것이다. 한 사례에서 이를 증명한 뒤 나머지 사례로 확장한다.

> [!note] Bias Check
> 참신한 도구가 더 좋은 해결이라는 보장은 없다. 기존 방법이 제약에 가장 적합할 수 있다. 영상의 단계·채용 전망은 단일 발표자의 경험적 주장이고, 위 네 사례는 실행 계획이다. 문서 완성도를 실제 구현력·성과로 대신 평가하지 않는다.
