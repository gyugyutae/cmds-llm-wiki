# 포트폴리오 문제 해결 블록과 그림을 편집하는 법

## 상세 사례의 순서

현재 사용자 확정안은 [[금융 백엔드 포트폴리오 5장 원고]]다. 개인 4장·협업 1장에 총 5블록을 같은 순서로 배치한다. 문제 원인은 발견 경로·관측 현상·원인/영향 약 3줄, 해결은 수정·비교·선택 이유 약 3~4줄이다. 결과에는 실제 변화와 성능/부하 검증 조건을 포함한다. 실제 페이지 배치는 아직 하지 않는다. 2026-10-14 최종 점검은 [[2026-10-14-Q-financial-portfolio-final-review-and-video-alignment]]를 따른다.

[[2026-10-11-YouTube-취준생 대부분 포트폴리오를 잘못 만들고 있습니다]] 0:36~1:38·6:21~7:41의 참고안은 **제목 → 그림 → 문제 → 해결 → 결과**의 블록을 약 4개 반복하는 것이다. 이는 사용자 결정인 포트폴리오 5장을 편집할 때의 참고이며, 사례 수나 1사례=1쪽을 강제하지 않는다.

| 요소 | 넣을 내용 | 근거 |
|---|---|---|
| 제목 | 어떤 업무의 어떤 문제를 해결했는지 | 실패 현상·변경 내용 |
| 그림 | 판단에 필요한 요청/데이터 흐름 또는 전후 비교 | 실제 구조·경계·측정 원본 |
| 문제 | 발견 경로·증상·사용자/업무 영향 | 로그·재현·확인한 요구 |
| 해결 | 원인·비교한 대안·선택 이유·본인 변경 | 코드·PR·판단 기록 |
| 결과 | 검증 조건·확인한 변화·남은 한계 | 테스트·실측·재대사·피드백 |

3:28~4:36에서 문제 약 3줄, 해결 약 3~4줄을 제안한다. 본문은 짧게 편집하되 결과 조건을 생략해 수치를 과장하지 않는다. 상세 실험은 대표 글에 연결한다.

## 그림을 고르는 기준

2:05~3:17에서는 구조도·시퀀스·전후 그래프 중 사례 이해에 도움이 되는 그림을 고르고, 본인이 설명할 수 없는 AI 그림을 붙이지 말라고 조언한다. 이 Wiki에서는 AI 사용 금지로 확대하지 않고 **본인이 각 상자·화살표·경계의 실제 의미를 확인하는 책임**으로 적용한다.

financial-lab은 내부 DB 트랜잭션과 외부 기관 HTTP, 결과 조회·명세·대사·복구 경로를 구분한다. 사례가 동시 출금이면 경합과 트랜잭션 경계를, 응답 유실이면 요청 키·미확정 상태·조회와 복구 순서를 그린다. 전체 아키텍처를 매 사례에 그대로 반복하지 않는다. 구조는 [[거래 원장 아키텍처와 장애 복구 설계]]를 참고한다.

## 5장 편집에 적용

- 기존 개인/협업 프로젝트에서 **검증 근거와 본인 판단이 가장 강한 사례**를 먼저 고른다.
- 사례마다 출처 프로젝트·기간·본인 역할을 식별하게 하고 같은 블록 순서를 유지한다.
- 동시성·중복 요청·응답 유실·대사는 목표 후보이며 이번 인제스트로 완료 사례가 되지 않는다.
- “그림이 없다”는 이유만으로 경험을 버리지 않는다. 구현 범위·통합·사용자 피드백 등 해당 사례를 설명하는 근거를 찾는다.
- 실제 PDF 렌더링 후 5장과 글자 크기·줄바꿈·링크를 확인한다. 긴 자막이나 집필 계획은 제출본에 넣지 않는다.

[[2026-10-11-YouTube-합격하는 개발자 포트폴리오 양식 공유]] 8:04~8:59는 링크를 클릭하지 않아도 프로젝트를 이해할 수 있게 요약하라고 조언한다. PDF에도 핵심 판단을 남기고 링크는 상세 근거로 사용한다.

> [!note] Bias Check
> Counter-argument: 4블록은 발표자 편집 예시다. 근거가 약한 사례를 넣어 수를 맞추면 문서가 약해진다.
> Data gap: 영어 자막에 오역이 있고 화면 템플릿은 미확보다. 페이지 수와 그림의 구현 일치 여부는 제출본 제작 때 확인한다.
