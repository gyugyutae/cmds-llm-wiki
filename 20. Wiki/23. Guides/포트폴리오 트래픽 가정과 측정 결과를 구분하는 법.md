# 포트폴리오 트래픽 가정과 측정 결과를 구분하는 법

## 참고 조언

[[2026-10-11-YouTube-취업 개발자 이력서 초 필살기 (초간단, 매우 쉬움)]] 1:12~2:39는 프로젝트의 예상 TPS·서버 사양을 **가정으로** 한 줄 기록하고 부하 테스트로 검증하라고 말한다. [[2026-10-11-YouTube-취준생 대부분 포트폴리오를 잘못 만들고 있습니다]] 5:50~6:21은 성능 숫자와 같은 정도로 테스트 조건을 보여주라고 조언한다.

## 구분해서 기록할 정보

| 정보 | 표현 방식 | 근거 |
|---|---|---|
| 업무량·피크 트래픽 | 설계 가정 | 사용자 수·행동 빈도·조회/쓰기 비율·피크 배수와 계산 |
| 서버·DB 사양 | 설계 목표 또는 실제 실험 환경 | CPU·메모리·DB·배포 구성 |
| 부하 테스트 결과 | 지정 조건의 실측 | 부하 시나리오·기간·데이터량·반복·오류율·지연 |
| 실제 운영량 | 운영 관측 | 운영 로그·집계 기간·사용자와 거래량 |

가정을 적은 것만으로 그 부하를 처리했다고 말하지 않는다. 로컬/모의 기관 실험이 통과해도 실제 금융 운영 경험으로 승격하지 않는다. k6 언급은 도구 후보이지 이번에 실행한 테스트가 아니다.

## 현재 ideal 원고에 적용

최신 개인 4개·협업 1개 구성은 [[금융 백엔드 포트폴리오 5장 원고]]를 따른다. 아래 2쪽 원고는 이전 구성의 참고 기록이다.

[[금융 백엔드 포트폴리오 2쪽 원고]]의 10만 DAU·30만 이체/일·조회:이체 5:1·피크 15배·313 API RPS/52 이체 TPS와 API/DB 사양은 **기존 설계 가정**이다. 이번 인제스트는 계산이나 코드·환경을 재검증하지 않았고 실측값을 추가하지 않았다.

이력서에는 가정과 인프라 기준을 한두 줄로 묶고, 포트폴리오에는 조건과 결과를 연결한다. 예: `[가정] 일 이체 N건·피크 배수 P로 처리량을 산정; [실측] 환경 E·데이터 D에서 부하 L·기간 T로 오류율·p99·실제 거래 반영을 검증`.

성능 비교는 같은 요청/기관 계약·데이터·환경·정확성 기준에서 한다. HTTP 성공 수와 실제 유효 거래 수를 구분하고, 빠르지만 정합성이 깨진 결과를 개선 성과로 쓰지 않는다. 실행·전후 기록은 [[거래 원장 실험과 대표 기술 글 계획]]의 증거 요구에 연결한다.

> [!note] Bias Check
> Counter-argument: 과도한 트래픽 가정은 실제 사용자 문제보다 규모를 과시하게 만들 수 있다. 업무량의 이유와 최소 검증 범위를 먼저 설명한다.
> Data gap: 영상은 특정 금융 시스템 용량 산정의 공식 기준이 아니다. 실제 실험 환경·측정 원본과 재현 결과는 별도로 확보해야 한다.

## 2026-10-12 사용자 목적: 예상 환경에서 예방한 이유를 납득시킨다

[[2026-10-12-YouTube-이력서에 문제 해결을 쓸 수가 없어요-예상 환경과 예방]]와 이번 사용자 요청에 따라, 이후 금융 Java 학습·개발·이력서 검토에서는 **서비스 가정 → 회원/행동량 → 피크 부하 → 위험 재현 → 대안·예방 → 결과·비용·한계**를 연결한다. 실제 트래픽이 없어도 설계 가정에 따른 검증 경험을 만들 수 있다. 예방 성과는 해당 실험 조건에서 위험이 줄어든 증거로 표현한다.

이 목적은 [[금융 Java 포트폴리오에서 해결 차이와 트레이드오프를 증명하는 법]]의 3·4단계 성장 목표에 연결된다. 숫자를 크게 잡는 것이 목적이 아니라 “이런 조건 때문에 이 위험을 다뤘고, 이 비용을 받아들여 이 방법을 선택했다”를 설명하는 것이 목적이다.

### 서비스와 수요 가정

현재 프로젝트는 [[financial-lab]]의 계좌 이체·거래 원장 학습 시스템이다. 최종 소비자 서비스와 실제 고객층은 아직 확정하지 않았다. 계획 후보는 **계좌 간 이체 요청·거래 내역 조회·미확정 거래 복구를 제공하는 금융 백엔드**다. 실제 은행 서비스·회원 확보 경험이라고 쓰지 않는다.

회원 수만으로 부하는 정해지지 않는다. 아래 값을 하나의 가정 시트에 기록하고 낮음/기준/높음 시나리오를 둔다.

| 입력 | 기록할 값과 근거 |
|---|---|
| 전체 회원 M | 목표 서비스의 대상 범위·도입률, 사용자 확정 전에는 미정 |
| 일 활성 비율 a | DAU = M × a. 회원·DAU·동시 접속자는 구분 |
| 1 DAU당 이체 t | 일 이체량 = DAU × t. 반복·급여일 등 가정 이유 |
| 조회:이체 비율 r | 조회 API 수가 이체 API 수의 r배라는 정의 |
| 피크 배수 p | 일평균 대비 배수와 지속 시간. 저녁/급여일/집중 이벤트의 가정 |
| 추가 API·재시도 | 로그인·페이지당 여러 요청·중복 요청·조회 폴링은 별도 산정 |
| 데이터와 편중 | 계좌/원장 수·보관 기간·집중 계좌 비율·키 재사용률 |
| 품질 기준 | API별 p99·오류율·완료 지연·잔액/원장 규칙. 시험 전 본인이 정함 |

현재 원고의 **기준 가정**은 DAU 100,000명, 1인당 일 3회 이체, 조회:이체 5:1, 피크 15배다. 수요 자료로 검증한 예측이 아니다. 전체 회원 수는 미정이다. 예컨대 활성 비율을 20%로 *추가 가정*하면 회원 500,000명으로 역산되지만, 이는 산식 예시이고 사용자가 확정한 회원 목표가 아니다.

- 일 이체: 100,000 × 3 = 300,000건.
- 일 조회: 300,000 × 5 = 1,500,000건.
- 이 두 API의 일 요청: 1,800,000건.
- 피크 API 요청: 1,800,000 / 86,400 × 15 = **312.5 RPS**.
- 피크 이체 요청: 300,000 / 86,400 × 15 ≈ **52.08건/초**.

원고의 313 RPS/52 TPS는 반올림한 설계 목표다. 52는 이체 요청 도착 목표이며 실제 성공·확정 TPS와 구분한다. 다른 API와 재시도가 포함되면 총 요청은 달라진다. 거래 1건의 DB 쿼리/원장 행 수가 여러 개일 수 있으므로 API RPS를 DB QPS로 그대로 쓰지 않는다.

### 가정을 예방 실험으로 바꾸는 방법

| 가정·위험 | 비교·예방 후보 | 효과 확인 |
|---|---|---|
| 특정 계좌로 이체 집중 → 락 대기·교착·잔액 오류 | 잠금 방식·잠금 순서·재시도 범위 비교 | 성공/거절/재시도·p99·락 대기·잔액/원장 |
| 앱 인스턴스 증가 → 같은 키가 다른 서버로 유입 | 영속 키 제약·조건부 상태 변경 후보 | 다중 인스턴스 동일 키 요청의 실제 효과 건수 |
| 조회/원장 데이터 증가 → 조회 비용 증가 | SQL·인덱스·페이지 처리 비교 | 동일 데이터 EXPLAIN·p99·쓰기/저장 비용 |
| 피크에서 응답 유실·재시도 → 미확정/중복 처리 | 내부 결과 조회와 외부 기관 복구를 분리 | 결정적 응답 차단·재시작·양쪽 거래 기록 |

이는 구현 방향과 실험 계획이다. 현재 코드를 읽고 다음 작은 작업을 정하며, 재현·변경·검증 전에는 “예방했다”라고 쓰지 않는다. 장애 실험은 정상 부하 실험과 구분한다. 이미 정확한 구현에 가짜 개선 전 오류를 만들지 않는다.

### 단일 파드에서 확장 용량을 추정하는 순서

1. 같은 API 구성·데이터·DB·자원에서 단일 인스턴스가 품질 기준을 만족하는 지속 처리량 C1을 측정한다. CPU·메모리·GC·DB/커넥션 풀·락·생성기 병목과 원장 정확성을 같이 본다.
2. **선형 확장 가정값 = C1 × N**으로 계산하고 미검증 추정이라고 표시한다. 단일 파드는 서버/노드 한 대와 같지 않으며 같은 노드의 여러 파드는 자원을 나눠 쓴다.
3. 저비용 2개 인스턴스 시험이 가능하면 공유 DB와 로드밸런서를 두고 C2를 측정한다. 효율 e2 = C2 / (2 × C1)을 기록한다. 이 값도 모든 N에서 유지된다고 보장하지 않는다.
4. 공유 DB·락·외부 기관·노드 자원 병목을 확인한다. 앱만 늘려도 DB 용량은 그대로일 수 있고 총 커넥션 수는 인스턴스 수와 함께 늘 수 있다.
5. 미검증 N의 계획에는 효율 e(N), 여유율 u를 가정하여 Cplan(N) = C1 × N × e(N) × u로 민감도 계산한다. DB 등 병목과 장애 시 남는 용량은 별도 제약으로 검사한다.

예시 숫자는 계산 연습만 한다. C1=120 API RPS, e=0.8, u=0.7을 가정하면 4개는 268.8, 5개는 336 RPS로 산정된다. 이는 앞의 312.5 RPS 목표를 계산상 넘는 계획 후보일 뿐 실제 확장 결과가 아니다. 예시의 e·u는 권장 표준값이나 측정값이 아니다. API 처리량과 이체 완료 TPS는 같은 요청 비율·성공률·확정 지연에서 따로 확인한다.

실제 Kubernetes를 쓰지 않으면 “파드” 대신 실제 실행 단위(프로세스/컨테이너/VM 인스턴스)로 기록한다. 이 추정을 위해 Kubernetes 도입부터 할 필요는 없다. CPU·메모리 requests/limits와 노드 배치는 측정 조건에 포함한다. 자원 요청은 배치에 사용되고 제한은 실행 중 적용된다는 근거: [Kubernetes 공식 자원 문서](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/). 여기서 비용과 공유 병목에 대한 판단은 프로젝트 적용 해석이다.

목표 도착 부하를 시험할 때는 응답이 느려져도 요청 도착률을 유지하는 arrival-rate 모델을 검토한다. iteration당 HTTP 요청 수를 정의하여 iteration rate와 RPS를 구분하고 dropped iterations·생성기 한계를 기록한다. 근거: [Grafana k6 공식 부하 모델 문서](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/).

### 서버 비용 추정

파드 개수 × VM 가격으로 바로 계산하지 않는다. VM 기반 배포라면 먼저 파드 자원·노드당 배치·시스템 예약·장애 여유로 **필요 노드 수**를 정한다. 서버리스/파드 과금 모델이면 그 상품의 실제 과금 단위를 따른다.

월 추정 비용 = 앱 노드 비용 + DB/복제/스토리지/IO 비용 + 로드밸런서 + 네트워크 전송 + 로그/모니터링 + 백업 + 사용한 플랫폼 관리 비용.

각 항목은 리전·상품·사양·수량·운영 시간·가격 확인일·가격 출처를 기록한다. 목표 부하에서의 비용과 한 인스턴스 장애 시 목표를 유지하는 비용을 별도로 제시한다. 고정 DB에 앱만 증설하는 안과 DB도 증설하는 안을 나누며, 미검증 비용은 견적 추정이라고 표시한다. 이번에는 상품/리전/실측이 없으므로 비용 금액을 만들지 않는다.

### 이력서·포트폴리오에 전달할 구조

현재 목적 설명은 다음처럼 쓸 수 있다.

> 실제 운영 트래픽이 없는 계좌 이체·원장 프로젝트에서, 사용자 행동과 피크 부하를 가정하고 정합성·처리량·자원 비용을 함께 검증하는 것을 목표로 한다.

검증 후에는 아래 구조의 빈칸을 실제 증거로 채운다.

> [설계 가정] 대상·DAU·행동 빈도에 따라 피크 부하를 산정했다. [재현] 해당 부하/실패 조건에서 위험을 확인했다. [판단·구현] 대안 A/B의 비용을 비교해 방법 X를 선택했다. [실측] 환경·데이터·기간에서 정확성·p99·완료 처리량을 확인했다. [추정·한계] 다중 인스턴스 용량/비용은 검증 범위를 표시했다.

이력서는 환경·문제·선택·핵심 결과를 한두 문장으로 압축하고, 포트폴리오는 가정의 이유·대안·원본 결과·비용·한계를 연결한다. 같은 실험 ID·커밋·조건을 사용한다. 외부 실제 장애를 해결했다는 표현 대신 **“가정 부하에서 재현한 위험을 개선/예방 검증했다”**라고 쓴다.

첫 산출물은 가정 시트 1개와 실험 결과표 1개다. 실제 회원 목표·활성 비율·피크 이유·SLO·실험 자원·비용 상품은 사용자 결정 또는 측정이 남아 있다.

> [!note] Bias Check
> 단일 파드의 선형 배수는 검증되지 않은 확장 가정이다. 실제 수요가 없어도 예방 실험은 가능하지만 가정의 합리성과 관측 범위를 설명해야 한다. 목표 숫자만 채운 문서를 실험 성과로 승격하지 않는다. 과도한 자원 투입보다 같은 품질 기준에서 필요한 최소 비용을 비교한다.
