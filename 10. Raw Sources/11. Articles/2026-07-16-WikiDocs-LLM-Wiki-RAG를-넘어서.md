우리가 LLM(Large Language Model, 대규모 언어 모델)에게 문서를 주고 질문하는 방식은 대부분 같은 구조를 따른다. 문서를 올리고, 질문하면, LLM이 관련 조각을 찾아 답을 만든다. 문제는 이게 매번 처음부터 다시 시작한다는 점이다. 다섯 개 문서를 종합해야 답할 수 있는 미묘한 질문을 던지면, LLM은 그때마다 흩어진 파편을 다시 찾아 조립한다. 축적이 없다.

Andrej Karpathy(테슬라 AI 총괄 출신, OpenAI 공동창립 멤버)가 제안한 "LLM Wiki"는 이 문제에 대한 근본적으로 다른 접근이다. LLM이 단순히 문서를 검색하는 게 아니라, 직접 위키를 써서 지식을 누적시킨다. 한 번 정리한 지식은 다음 질문에서 다시 정리할 필요가 없고, 새 자료가 들어오면 기존 위키 위에 덧쌓인다. 이 패턴이 왜 기존 RAG와 본질적으로 다른지, 그리고 실무에서 어떻게 작동하는지 살펴보자. <박재홍의 실리콘밸리>

## 핵심요약

- LLM Wiki의 핵심은 "매번 검색해서 재조립"이 아니라 "한 번 정리해서 계속 쌓아가는" 지식 구조다. RAG가 질문마다 처음부터 시작하는 반면, LLM Wiki는 이전에 정리한 결과 위에 새 정보를 통합한다.
- 아키텍처는 세 층으로 나뉜다. 원본 자료(불변), LLM이 작성·유지하는 위키(마크다운 파일들), 그리고 위키 운영 규칙을 담은 스키마 문서. 인간은 읽고 방향을 잡고, LLM은 쓰고 정리한다.
- 주요 작업은 세 가지: Ingest(새 자료 통합, 한 자료가 10~15개 페이지를 업데이트), Query(위키 기반 답변 생성 후 결과를 다시 위키에 저장), Lint(모순·고아 페이지·빈 교차참조 점검).
- 인간이 위키를 포기하는 이유는 유지보수 부담이 가치보다 빨리 커지기 때문인데, LLM은 교차참조 갱신, 요약 최신화, 모순 표시 같은 반복 작업을 거의 비용 없이 처리한다.
- 이 패턴의 진짜 의미: LLM의 역할이 "질문에 답하는 도구"에서 "지식을 구조화하고 유지하는 에이전트"로 전환된다. 1945년 Vannevar Bush가 구상한 Memex(개인 지식 저장소)가 80년 만에 실현 가능해진 셈이다.

## RAG의 한계: 매번 처음부터 다시 시작하는 문제

RAG(Retrieval-Augmented Generation, 검색으로 찾은 정보를 LLM에 함께 넣어 답하게 하는 기법)는 현재 LLM 활용의 표준이다. NotebookLM, ChatGPT 파일 업로드, 대부분의 기업용 문서 QA 시스템이 이 방식을 쓴다. 문서를 작은 조각(chunk)으로 나누고, 질문이 들어오면 관련 조각을 찾아 LLM 프롬프트에 넣는다.

이 방식의 근본적 약점은 "축적이 없다"는 점이다. 다섯 개 논문의 결론을 종합해야 하는 질문을 오늘 하고, 내일 비슷한 질문을 하면 LLM은 또다시 다섯 개 조각을 찾아 조합한다. 어제의 종합 결과는 어디에도 남지 않는다. 지식이 복리로 쌓이지 않고, 매번 단리로 계산된다.

Karpathy가 지적하는 핵심 차이는 이것이다. RAG에서 LLM은 "검색 엔진 + 요약기"이지만, LLM Wiki에서 LLM은 "편집자 + 사서"다. 전자는 질문할 때만 작동하고, 후자는 자료가 들어올 때부터 작동한다.

## 세 층 아키텍처: 원본, 위키, 스키마

LLM Wiki의 구조는 세 층으로 나뉜다.

**첫째, 원본 자료(Raw Sources)**. 논문, 기사, 데이터 파일, 이미지 등 큐레이션한 소스다. 이 층은 불변(immutable)이다. LLM은 읽기만 하고 절대 수정하지 않는다. 진실의 원천(source of truth) 역할을 한다.

**둘째, 위키(The Wiki)**. LLM이 생성하고 유지하는 마크다운 파일 디렉토리다. 요약 페이지, 개체(entity) 페이지, 개념 페이지, 비교 페이지, 종합 분석 등으로 구성된다. 새 자료가 들어오면 LLM이 관련 페이지를 업데이트하고, 교차참조를 갱신하고, 모순을 표시한다. 인간은 이 위키를 읽기만 한다. LLM이 쓴다.

**셋째, 스키마(The Schema)**. CLAUDE.md나 AGENTS.md 같은 설정 문서로, 위키의 구조 규칙, 컨벤션, 워크플로를 정의한다. "요약 페이지는 이런 형식으로", "새 자료 통합 시 이 순서로 처리" 같은 지침이 담긴다. 인간과 LLM이 함께 발전시키는 메타 문서다.

이 세 층의 분리가 중요한 이유가 있다. 원본은 절대 오염되지 않으니 항상 돌아갈 곳이 있고, 위키는 LLM이 자유롭게 재구성할 수 있으니 구조가 고정되지 않으며, 스키마는 LLM의 행동을 제어하니 품질을 관리할 수 있다.

## 세 가지 핵심 작업: Ingest, Query, Lint

**Ingest(통합)**. 새 자료를 원본 디렉토리에 넣고 LLM에게 처리를 지시한다. LLM은 자료를 읽고, 핵심을 추출하고, 요약 페이지를 쓰고, 인덱스를 갱신하고, 관련 개체·개념 페이지를 업데이트하고, 로그에 기록한다. 하나의 자료가 10~15개 위키 페이지를 건드릴 수 있다. Karpathy는 한 번에 하나씩 자료를 넣으며 직접 확인하는 방식을 선호한다고 밝혔지만, 여러 자료를 일괄 처리하는 것도 가능하다.

**Query(질의)**. 위키에 대해 질문한다. LLM은 인덱스를 먼저 읽어 관련 페이지를 찾고, 해당 페이지를 읽어 답을 종합한다. 여기서 중요한 점: 좋은 답변은 다시 위키에 새 페이지로 저장된다. 비교 분석, 발견한 연결 고리, 새로운 통찰이 채팅 히스토리 속에 묻히지 않고 위키에 남아 계속 참조된다. 탐색 자체가 지식으로 축적되는 구조다.

**Lint(점검)**. 주기적으로 LLM에게 위키 건강 상태를 점검시킨다. 페이지 간 모순, 새 자료로 무효화된 오래된 주장, 연결이 없는 고아 페이지, 언급만 되고 전용 페이지가 없는 중요 개념, 빠진 교차참조 등을 찾는다. LLM은 조사할 새 질문이나 찾아볼 자료도 제안한다.

## 인덱싱과 로그: 위키의 네비게이션

위키가 커지면 LLM도 어디에 뭐가 있는지 알아야 한다. 두 개의 특수 파일이 이 역할을 한다.

`index.md` 는 콘텐츠 중심의 카탈로그다. 모든 페이지의 링크, 한 줄 요약, 메타데이터가 카테고리별로 정리된다. LLM은 질문을 받으면 인덱스를 먼저 읽어 관련 페이지를 식별한 뒤 해당 페이지로 들어간다. 약 100개 소스, 수백 개 페이지 규모에서 이 방식이 잘 작동하며, 임베딩 기반 RAG 인프라 없이도 충분하다.

`log.md` 는 시간순 기록이다. 언제 무엇을 통합했고, 어떤 질문을 했고, 언제 점검을 돌렸는지 추적한다. 일관된 접두사(예: `## [2026-04-02] ingest | Article Title`)를 쓰면 단순 텍스트 도구로도 파싱할 수 있다.

```bash
grep "^## \[" log.md | tail -5
```

이 명령 하나로 최근 5개 활동을 즉시 확인할 수 있다.

## 활용 시나리오: 개인부터 팀까지

Karpathy가 제시하는 활용 범위는 넓다.

**개인 지식 관리**. 건강, 목표, 심리, 자기계발 관련 자료를 계속 넣으면서 자기 자신에 대한 구조화된 그림을 만들어간다. 일기, 기사, 팟캐스트 메모가 하나의 체계로 엮인다.

**장기 리서치**. 주제 하나를 몇 주에서 몇 달에 걸쳐 파고들 때, 논문과 기사를 읽을 때마다 위키에 통합한다. 연구 주제(thesis)가 점진적으로 발전하는 과정이 위키에 남는다.

**독서 보조**. 책을 읽으며 챕터별로 통합하면 인물, 테마, 줄거리 연결이 자동으로 교차참조된다. 팬 위키(예: Tolkien Gateway 같은 수천 페이지 규모의 인터링크된 위키)를 혼자서, 읽으면서 동시에 만들 수 있다.

**팀/비즈니스**. Slack 스레드, 회의록, 프로젝트 문서, 고객 통화를 먹이면 LLM이 내부 위키를 최신 상태로 유지한다. 팀원 누구도 하고 싶어하지 않는 유지보수를 LLM이 맡는다.

## 실제 작업 환경: Obsidian + LLM 에이전트

Karpathy의 실제 워크플로는 이렇다. 한쪽 화면에 LLM 에이전트(Claude Code, Codex 등)를 열고, 다른 쪽에 Obsidian(마크다운 기반 노트 앱)을 연다. LLM이 위키를 편집하면 Obsidian에서 실시간으로 결과를 확인한다. 링크를 따라가고, 그래프 뷰로 구조를 보고, 업데이트된 페이지를 읽는다.

Karpathy의 비유가 정확하다. Obsidian은 IDE, LLM은 프로그래머, 위키는 코드베이스다. 위키가 곧 git 저장소이기도 하니 버전 관리, 브랜칭, 협업이 공짜로 따라온다.

보조 도구도 몇 가지 언급된다.

- **Obsidian Web Clipper**: 브라우저 기사를 마크다운으로 변환해 원본 자료로 빠르게 수집
- **이미지 로컬 저장**: Obsidian 설정에서 첨부 파일 경로를 고정하고 단축키로 이미지를 다운로드하면, URL이 깨져도 LLM이 이미지를 직접 참조 가능
- **Obsidian 그래프 뷰**: 위키의 연결 구조를 시각적으로 파악. 허브 페이지, 고아 페이지를 한눈에 식별
- **Marp**: 마크다운 기반 슬라이드 형식. 위키 콘텐츠로 바로 프레젠테이션 생성
- **Dataview**: 페이지 YAML 프론트매터에 대한 쿼리 플러그인. 태그, 날짜, 소스 수 기반 동적 테이블 생성
- **qmd**: 마크다운 파일 전용 로컬 검색엔진. BM25/벡터 하이브리드 검색과 LLM 리랭킹 지원. CLI와 MCP(Model Context Protocol) 서버 모두 제공

## 왜 작동하는가: 유지보수 비용의 붕괴

인간이 위키를 포기하는 패턴은 거의 항상 같다. 처음엔 열정적으로 페이지를 만들지만, 교차참조 갱신, 요약 최신화, 새 정보와 기존 정보의 모순 표시 같은 유지보수가 쌓이면서 부담이 가치를 넘어선다. 위키의 가치는 연결에 있는데, 연결을 유지하는 비용이 너무 높다.

LLM은 이 방정식을 뒤집는다. 지루함을 느끼지 않고, 교차참조를 업데이트하는 걸 잊지 않으며, 한 번에 15개 파일을 건드릴 수 있다. 유지보수 비용이 거의 0에 수렴하니, 위키가 커질수록 가치만 올라간다.

인간의 역할은 소스를 큐레이션하고, 분석 방향을 잡고, 좋은 질문을 던지고, 그 모든 것이 무엇을 의미하는지 생각하는 것이다. 나머지는 전부 LLM의 몫이다.

## Memex에서 LLM Wiki까지: 80년의 간극

Karpathy는 이 아이디어가 Vannevar Bush의 Memex(1945)와 정신적으로 연결된다고 밝힌다. Bush는 "As We May Think"라는 에세이에서 개인이 문서를 저장하고 문서 간 연상적 경로(associative trails)를 만드는 기계를 구상했다. 웹이 결국 실현한 건 공개적이고 분산된 하이퍼텍스트였지만, Bush의 원래 비전은 더 사적이고, 더 적극적으로 큐레이션되며, 문서 사이의 연결이 문서 자체만큼 가치 있는 시스템이었다.

Bush가 풀지 못한 문제는 "누가 유지보수를 하느냐"였다. 문서 간 연결을 만들고, 새 문서가 기존 연결에 어떤 영향을 주는지 추적하고, 전체 구조를 일관되게 유지하는 작업. 바로 그 부분을 LLM이 처리한다.

## 핵심통찰

이 패턴이 시사하는 바는 LLM의 역할 전환이다. "질문하면 답하는 도구"에서 "지식을 구조화하고 유지하는 지속적 에이전트"로의 전환. 흥미로운 점은 이를 위해 새로운 인프라가 거의 필요 없다는 것이다. 마크다운 파일, git, 그리고 LLM 에이전트만 있으면 된다. RAG가 "검색 인프라"를 요구했다면, LLM Wiki는 "에이전트가 파일을 읽고 쓸 수 있으면 충분하다"는 전제에서 출발한다. 이것은 임베딩 DB나 벡터 검색 같은 복잡한 파이프라인 없이도, 에이전트의 읽기/쓰기 능력만으로 지식 축적 문제를 풀 수 있다는 실험적 증거이기도 하다. 물론 위키 규모가 수천 페이지를 넘어가면 인덱스 파일만으로는 한계가 올 수 있고, 스키마 설계의 질이 위키 전체의 질을 결정한다는 점에서 "스키마 엔지니어링"이라는 새로운 기술 영역이 열릴 가능성도 있다.
