# FastReqs 프로젝트 기준 문서

> 이 문서는 제안서와 2026-10-06 사용자 대화에서 결정한 사항을 정리한 실행 기준이다. 프로그램은 아직 구현하지 않았다. 팀 전체 승인 문서가 아니라 김규태와의 대화를 바탕으로 작성한 팀 검토용 초안이다. 사용자 확정 사항, 에이전트 제안, 미정 사항을 구분한다.

## 1. 프로젝트 목적과 현재 상태

FastReqs는 AI를 활용하는 개발팀이 요구사항을 빠르고 체계적으로 관리하도록 돕는 Slack 봇과 CLI다. 대화·회의에서 나온 요구사항과 사용자의 기존 문서를 비교하여 추가·변경·제외 후보를 제안하고, 부족한 정보를 질문한 뒤 사람이 승인한 변경만 로컬 Markdown에 반영한다. 개발 생산성과 요구사항 관리·문서화 비용 절감이 목표지만, 비용 감소 효과는 아직 측정하지 않은 목표다.

- 과목: 소프트웨어개발론. 중간발표의 WBS 작성 담당은 김규태.
- 현황: 주제와 제안서만 작성. 코드·연동·음성 처리·테스트·배포는 모두 미착수.
- 팀: 김규태, 손강민, 임성완. 공식 역할·팀장은 아직 정하지 않았다.
- 투입 가능 시간: 각자 주 3시간, 팀 전체 주 9시간. 과거의 주 4시간 조건은 폐기한다.
- 팀 검토용 문서 목표: 2026-10-07. 중간발표 제출: 다음 주, 정확한 날짜 미정.
- 프로그램 완성 및 최종발표 마감: 2026-12-20. 12월 말·12월 31일은 폐기한다.
- 완성 수준: 지정 Slack 채널 하나에서 팀원이 시연하는 프로그램. 실제 서비스 출시·외부 고객 운영은 범위에 포함하지 않는다.
- AI API: 교수에게 연구실 지원 여부를 문의해야 한다. 지원 미확보. 미지원 시 각자 10,000원, 총 30,000원을 API에 사용할 계획이다. 이는 호스팅 예산이 아니다.
- 팀이 아는 언어: C와 Python 정도. AI 도움으로 개발할 예정이며 언어 선택은 열려 있다.

## 2. 확정된 제품 구성과 실행 조건

### 연구실 PC의 Slack 봇

연구실 PC를 상시 켜서 봇 프로그램을 실행한다. 지정 채널 하나에 봇을 추가하고 대화 이벤트를 수집한다. Slack 채널에 봇을 초대하는 것만으로 프로그램이 실행되는 것은 아니다. 사용자 CLI가 종료되어도 연구실 봇의 대화 감지·보관은 계속된다. 연구실 PC나 봇이 중지되었을 때의 완전한 무손실 복구는 보장하지 않으며 구현 시 가능한 재조회 범위를 확인한다.

### 사용자 PC의 CLI

CLI는 사용자가 로컬 문서 폴더를 지정하고 봇과 연결하며 `/conflict` 등 프로젝트 기능을 실행하는 도구다. CLI가 실행 중인 동안만 로컬 문서를 읽고 승인 변경을 적용할 수 있다. CLI와 별도의 백그라운드 에이전트·데몬·자동 시작 프로그램은 만들지 않는다.

CLI가 종료되거나 PC가 꺼져 있으면 봇은 대화를 보관한다. CLI가 다시 연결되면 해당 사용자의 최신 문서를 읽고 보관된 대화와 비교하여 개인 변경안을 생성한다. 연결 방법·신원 확인·보관 형식은 아직 설계하지 않았다. Socket Mode를 연구실 봇의 Slack 연결에 사용하는 것은 에이전트 제안이며 기술 확정 사항은 아니다.

### 사용자별 문서

두 사람의 문서가 달라도 된다. 각 사용자의 기존 문서와 같은 채널 대화를 별도로 비교한다. 누구나 자기 문서 변경을 승인할 수 있고, 한 사용자의 승인이 다른 사용자 PC의 문서를 수정하지 않는다. 회사에서 사용하는 문서도 사용자 지정 로컬 폴더에 있는 경우를 대상으로 이해하며, 실제 회사 시스템 연동은 약속하지 않는다.

## 3. Slack 요구사항 변경 흐름

1. 지정 채널의 대화를 수집한다. 일반 대화를 독립적인 요약 문서로 만드는 기능은 제외한다.
2. 10분간 새 대화가 없거나 마무리 표현을 감지하면 해당 대화 세션의 처리를 시작한다.
3. CLI가 꺼진 사용자에 대해서는 대화를 보관하고 재연결을 기다린다.
4. 연결된 사용자의 기존 Spec과 현재 대화 세션을 비교한다. 기존 문서가 없으면 최초 초안을 생성한다.
5. 요구사항 추가·변경·제외 후보를 생성한다. 상충 요구사항이 있으면 비교하여 사람이 선택하도록 한다.
6. Who·What·Why가 부족하면 봇이 보완 질문을 한다. 사용자가 답변하거나 `종료`를 입력할 때까지 진행한다.
7. 봇이 해당 사용자에게 Slack 개인 메시지로 후보와 문서 변경안을 전달한다.
8. 사용자가 Slack에서 승인·거절·수정 요청을 한다. 승인은 후보 단위로 처리하는 초안이다.
9. 승인된 내용만 연결된 사용자 CLI를 통해 그 사용자의 로컬 문서에 반영한다.
10. 정보가 부족한 후보는 수정하지 않고 미승인 상태로 남긴다. `종료`는 불완전한 후보를 자동 승인하는 명령이 아니다.

마무리 표현의 목록, 문장 판별 방식, 세션 경계, 질문 제한 시간은 구현 전 결정한다. 서로 다른 이벤트가 같은 세션을 중복 처리하지 않도록 해야 한다. 승인 대기 중 원본 문서가 바뀌면 변경안을 재검토하는 방식은 에이전트의 설계 제안이다.

## 4. MP3 회의 입력 흐름

사용자가 MP3를 업로드한다. raw는 원본 MP3이고, meeting은 음성을 텍스트로 변환하여 회의 일시·참석자·결정사항·요구사항 후보를 포함한 문서다. 회의록 정리는 수행하지만 Slack 일반 대화 요약과 혼동하지 않는다.

1. MP3 원본을 보존한다.
2. 음성 전사를 생성한다.
3. 회의 메타데이터와 결정사항·요구사항 후보를 정리한다.
4. 기존 Spec과 비교하고 Slack 흐름과 같은 보완 질문·사람 승인·문서 갱신을 수행한다.

업로드 위치는 미정이다. 1차 제안은 CLI에서 로컬 MP3 경로를 입력하는 방식이다. 일시·참석자 정보를 음성에서 확인하지 못하면 사용자 입력 또는 미상으로 기록하고 추측하지 않는다. 실시간 녹음, 실시간 회의 참여, 자동 화자 신원 식별은 현재 필수 범위가 아니다.

## 5. 문서 산출물과 생성 범위

모든 문서는 사용자 PC의 지정 폴더에 Markdown으로 저장한다. 구체적인 파일명과 템플릿은 팀 검토 전 제안이다.

| 문서 | 내용 및 처리 |
|---|---|
| User Story | Who·What·Why를 갖춘 검토 자료. Spec과 별도 파일 보관. 승인한 요구사항에 따라 갱신 |
| Spec | 기능 설명, 입력·출력, 처리 규칙, 예외 상황, 인수 조건. 승인한 내용만 갱신 |
| PRD | 제품 목적·범위·요구사항을 담는 별도 Markdown. 세부 템플릿은 설계 단계 확정 |
| ADR | 기술 선택과 이유가 대화에서 확인될 때만 작성. 선택·이유가 없으면 생성하지 않음 |
| API 설계 | 경로, HTTP 메서드, 요청·응답, 오류 등의 설계 문서 |
| DB 설계 | 테이블, 컬럼, 키, 관계 등의 설계 문서 |
| meeting | MP3 전사와 회의 메타데이터·결정사항·요구사항 후보 |
| raw | 원본 MP3. Markdown 요약을 raw라고 부르지 않음 |

User Story·Spec 외에 영향을 받는 PRD·API·DB 문서의 갱신안을 함께 보여주는 것은 설계 초안이다. ADR의 과거 결정을 덮어쓰지 않고 대체 관계를 남기는 방식을 제안한다. 최초 실행 시 문서 초안을 만들고 사람 승인 후 저장한다.

API·DB 설계는 FastReqs가 관리하는 대상 프로젝트의 설계 문서 생성 기능이다. 이 문서를 근거로 대상 프로젝트의 실제 API 서버를 구현하거나 DB를 생성·마이그레이션하는 기능은 제외한다. FastReqs 자체의 봇·CLI 연결 코드와 대화 보관 기능은 개발에 필요하므로 이 제외 조건과 구분한다.

## 6. CLI `/conflict`

이 프로젝트에서 새로 구현할 CLI 명령이다. 현재 Codex에 설치되어 있거나 작동하는 기존 스킬이라고 주장하지 않는다.

- 검사 대상: 지정 폴더의 전체 요구사항·설계 문서. User Story·Spec·PRD·ADR·API·DB를 포함한다. meeting의 근거 추적도 검사 설계에 반영한다.
- 검사 목적: 문서들에 상충하는 내용이 있는지 확인한다. 승인된 내용의 누락·불일치 검증도 요구사항에 포함한다.
- 출력 초안: 충돌 문서·근거 위치·상충 내용·해결 후보를 표시한다.
- 사람이 해결안을 선택하고 승인한 뒤 적용한다. 자동으로 어느 문서가 맞는지 결정하여 덮어쓰지 않는다.
- 과거 ADR과 현재 ADR의 대체 관계를 구분한다. 단순 문구 차이를 모두 충돌이라고 판단하지 않도록 한다.
- 코드와 Spec 비교·코드 자동 수정은 제외한다. 추가 CLI 스킬 이름은 아직 정하지 않았다.

## 7. 최종 시연의 완료 기준

사용자는 다음 두 핵심 흐름이 작동하면 완료로 판단하는 데 동의했다.

1. Slack 대화 → 기존 Spec 비교 → 추가·변경·제외 후보와 보완 질문 → Slack 개인 메시지 승인 → 로컬 관련 Markdown 갱신.
2. MP3 업로드 → 회의록 생성 → 기존 Spec 비교 → 같은 승인·갱신 과정.

최종 테스트에는 최초 문서 생성, 정보 부족 시 수정 보류, 두 사용자 문서 분리, `/conflict`, CLI 종료 시 대화 보관과 재연결을 포함한다. CLI를 닫은 뒤 즉시 로컬 파일이 수정되는 동작은 완료 기준이 아니다.

## 8. 현재 진척 보고와 WBS 작성 원칙

- 완료 사실: 주제 선정과 제안서 작성. 세부 범위는 이번 대화로 정리했지만 팀 리뷰 전이다.
- 미착수: 개발, Slack 설정, AI·음성 API 검증, 설계 문서 템플릿, 테스트 및 배포.
- WBS: 레벨 0 프로젝트 전체 목표 → 레벨 1 단계·인도물 → 레벨 2 추정 가능한 작업 패키지.
- WBS 전체 목표의 표시 제목: **요구사항 관리 Slack 봇 개발**. 레벨 1은 **요구분석·설계·코딩·테스트** 네 단계로 구성한다.
- 텍스트 트리·시각 트리·표에 동일한 WBS ID를 사용한다. 제출용 표는 ID, 선행 작업 ID, 작업 완료도, 우선순위, 작업 이름, 기간, 시작 날짜, 완료 날짜 순서다.
- 제출용 계획과 진척 MD에는 트리와 표만 담고, 실행 조건·비용·팀 검토 사항 등의 설명은 이 프로젝트 기준 문서에서 관리한다. HTML에서도 텍스트 트리·시각 트리·표를 제공한다.
- 최신 작업 묶음은 요구분석 6개, 설계 4개, 코딩 7개, 테스트 6개다. 설계에 대화·승인 흐름과 AI 분석·회의·충돌 검사 설계를 추가했다.
- 코딩은 Slack 대화 수집·종료 감지, CLI 연결·로컬 문서 관리, AI 요구사항 분석·초안 생성, Slack 승인·문서 갱신, MP3 회의 처리, `/conflict` 검사·해결, 재연결·오류·비용 관리의 7개로 묶었다. 보완 질문·최초 문서 생성·버전 보호·관련 문서 생성은 이 작업들에 포함한다.
- 코딩 작업을 묶은 뒤 표의 기간은 7~14일의 달력 기간으로 재배치했다. 설계 추가와 작업 병합에 따른 담당·노력 추정은 팀 재검토 대상이다.
- 문서화·리뷰·중간발표·최종발표·검증·운영 준비도 범위에 포함한다.
- 담당자와 작업시간·세부 일정은 에이전트 초안이며 팀 확정 전이다. 계획치를 실제 투입 시간으로 주장하지 않는다.
- 소규모 수업 프로젝트는 각자 주 3시간이므로 강의의 일반적인 8~80시간 규칙을 기계적으로 적용하지 않는다. 더 작은 패키지를 사용하는 이유를 WBS에 명시한다.
- 비용은 API 총액 30,000원을 중복 합산하지 않고 공동 예산으로 관리한다. 학생 노동시간과 현금 비용을 구분한다. 연구실 PC 사용의 추가 현금 비용은 확인 전이다.

| 문서 소유 | 사용자별 로컬 문서 | 한 PC의 팀 공용 문서만 갱신 |
| 로컬 연결 | CLI 실행 중에만 | 별도 백그라운드 연결 프로그램 |
| 상시 감지 | 연구실 PC 봇 실행 | 무료 호스팅을 기본 전제로 함 |
| User Story | 별도 파일 생성·갱신 | 저장 여부 미정 |
| API·DB | 설계 문서 생성 포함 | 자동 생성 범위에서 제외하는 제안 |
| ADR | 기술 선택과 이유 확인 시 작성 | 모든 대화에서 무조건 생성 |

## 10. 남은 결정과 설계 제안

아래는 기능 목표를 다시 묻는 질문이 아니라 첫 WBS 단계에서 결정할 항목이다.

| 항목 | 현재 상태 / 다음 행동 |
|---|---|
| 중간발표 정확한 날짜 | 다음 주로만 확인. 담당 교과 공지 확인 |
| 팀 역할 | 임시 배정 후 팀원 합의. 공식 팀장 미정 |
| 언어·라이브러리 | 에이전트 추천은 Python + Slack Bolt + 공통 문서 엔진. 비교·실험 후 팀 결정 |
| AI·음성 API | 교수에게 지원 문의. 제공자·모델·과금·음성 길이 제한 확인 |
| PC 운영체제 | 연구실 PC와 팀원 PC의 OS 미확인. CLI 설치·실행 검증에 필요 |
| 사용자-CLI 연결 | 사용자 인증, 연결 ID, 폴더 범위, 재연결 상태를 설계 |
| 오프라인 승인 | CLI가 꺼진 순간 승인하면 적용 대기. 재연결 후 최신 파일 비교 및 필요 시 재승인하는 안 |
| MP3 업로드 | CLI 파일 경로 입력 제안. Slack 첨부 방식은 아직 확정하지 않음 |
| 세션 종료 | 10분 무대화 또는 마무리 표현. 표현 목록·중복 이벤트 방지 확정 |
| 산출물 갱신 | User Story·Spec 갱신은 확정. 나머지 문서의 영향도·승인 묶음 설계 |
| 회의 메타데이터 | 사용자 보완 입력 방식·필수 필드 확정 |
| 비용 추적 | 호출·음성 처리 비용 기록, 실패·재시도 한도 설정 |
| 연구실 PC 운영 | 전원·절전·네트워크·재시작 방식 확인. 원격 PC 설정 변경은 별도 사용자 요청 필요 |

주 9시간 안에서 모든 기능을 구현하는 일정은 아직 검증하지 않았다. AI 도움으로도 연결·파일 변경·음성 처리·테스트에 시간이 든다. 먼저 Slack → 승인 → 로컬 파일 변경의 최소 흐름을 검증하고, 지연 시 팀이 범위·일정을 다시 합의한다. 에이전트는 필수 기능을 임의로 삭제하거나 구현했다고 보고하지 않는다.

## 11. 후속 에이전트 작업 지침

1. 이 문서와 WBS를 먼저 읽고 사용자 최신 지시가 있으면 우선한다.
2. 확정 사항을 반복 질문하지 않는다. 미정 기술 결정은 후보·검증 결과로 구체화한다.
3. 진행 상황을 실제 코드·파일·테스트 결과로 확인한다. 이 문서를 구현 완료 증거로 사용하지 않는다.
4. 변경안과 승인된 파일 버전을 구분하고, 사용자의 승인 없이 요구사항 파일을 수정하는 제품 동작을 만들지 않는다.
5. 다른 사용자 폴더를 수정하지 않는다. CLI가 꺼진 동안 파일 적용이 가능하다고 설명하지 않는다.
6. 기존 문서·MP3 원본·이 프로젝트와 무관한 로컬 변경을 보존한다.
7. 문서 변경 후 최신 결정·미결 사항·진척·완료 기준을 함께 갱신한다.
8. AI가 만든 코드와 팀원이 검토·수정·검증한 내용을 구분하여 기록한다.
