# 개발계획서 초안

작성일: 2026-09-27
상태: 제출 양식에 옮기기 전 팀 검토용. 웹 UI는 팀 결정, 추가 역할 배분은 제안이다. 실제 HWP 양식에서 1페이지/2페이지 제한에 맞춰 편집해야 한다.

## 과제명

**프로펠러 제조 변경 시제품의 요구사항 검토를 지원하는 AI 에이전트**

제품명: Propeller Evidence Agent

## 과제소개 — 1페이지 이내 작성용

### 목적

프로펠러 제작 재료·공법을 변경하면 시제품이 요구 추력과 소음·토크 제약을 만족하는지 다시 검토해야 한다. 품질 엔지니어는 기존 시험·해석 근거의 적용 가능성을 확인하고, 추가 검증이 필요한 항목을 구분해 다음 제작·시험 단계로의 진행을 검토한다. 본 과제는 이 과정에서 조건 대조, 수치 비교, 추가 해석 준비 및 근거 보고를 지원하는 AI 에이전트를 개발한다. 실제 현장의 작업 부담과 절차는 품질 엔지니어 및 시험·해석 전문가 자문으로 구체화한다.

### 개발 내용

1. **요구사항 구조화:** 자연어 요청에서 후보, 시험 조건, 추력 하한, 소음·토크 상한을 추출하고 사용자에게 확인받는다.
2. **기존 사례 검토:** 사례를 직접 재사용·참고 가능·새 증거 필요로 분류하고 차이와 근거를 표시한다.
3. **요구사항 비교:** Python으로 지표를 계산하고 요구사항별 충족·미충족·판단 불가를 제시한다. 기존품 대비 개선 여부는 별도로 표시한다.
4. **추가 검증 분기:** 미측정 조건 요청 시, 준비된 CFD로 산출 가능한 지표만 사전 점검·사람 승인 후 Fluent로 실행한다. 실측이 필요한 항목은 추가 시험 대상으로 남긴다.
5. **진행 시각화와 근거 보고:** 실제 도구 실행 상태, 비교 수치, 출처, 한계를 웹 화면에 보여주고 사람이 최종 검토한다.

데모는 ENOLA 공개 연구 데이터의 XOAR 9×7 ABS·PA12 제작품을 7350RPM에서 비교하는 것으로 시작한다. “미측정 8500RPM이나 새 형상에서도 같은 결론인가?”라는 후속 질문으로 근거 재사용과 추가 검증의 분기를 보여준다. 현재 확보 자료는 제작 방식과 재료가 함께 달라지므로 재료만의 인과효과를 주장하지 않는다. 연구용 데이터를 사용한 시연이며 실제 제품 출하·안전 인증을 대신하지 않는다.

### 기대효과

품질 검토자가 조건 확인과 자료 정리에 직접 개입하는 부담을 줄이고, 요구사항·측정 근거·추가 검증 계획을 연결해 재현 가능한 검토를 지원한다. 전체 경과 시간뿐 아니라 사람의 실제 개입 시간과 오류·누락을 측정해 효과를 평가한다. 절감률은 사전 확정하지 않는다.

## 개발 환경 및 기술 스택 — 체크 항목 제안

| 양식 항목 | 기재안 |
|---|---|
| 예상 사용 AI 모델 | 기타: 도구 호출 지원 LLM API, 9/29 대회 지원 안내 후 선정. 특정 모델 사용을 확정하지 않음 |
| 예상 사용 프레임워크 | 기타: LangGraph, Streamlit, PyFluent 및 MCP 연동 |
| 예상 개발 언어 | Python |
| 클라우드 지원 필요 여부 | 아니오: Windows PC에서 로컬 실행·브라우저 접속. LLM API는 모델 선정 후 원격 호출 가능 |

Windows Pro PC 한 대에서 Streamlit 웹 화면을 열어 시연한다. 화면은 Python 에이전트·LangGraph·SQLite·Fluent 실행과 로컬에서 연결한다. 별도 대형 프론트엔드와 클라우드 호스팅은 범위에 두지 않는다. 팀은 Fluent Student에서 시연 케이스를 실행하고 출력 지표를 검증했다고 보고했다. Streamlit 승인 버튼에서 PyFluent/MCP를 호출하고 결과·실행 로그를 저장하는 통합은 개발 예정이다. API 개인 예산은 1인 1만원 이내, 3인 합산 최대 약 3만원이며 지원 안내 후 호출량 제한과 비용 기록을 적용한다.

## 개발계획 — 2페이지 이내 작성용

### 개발방법 및 방법론

한 개의 사용자 요청이 입력부터 근거 보고까지 완료되는 작은 기능 단위로 개발하고, 실제 데이터 및 전문가 검토를 병행한다. LLM은 요청 해석·도구 선택·설명을 맡고, 수치 계산과 조건 검사는 Python 규칙으로 수행한다. LangGraph에 상태 전이·보류·승인·오류 경로를 구성한다. 승인된 입력과 허용 도구만 실행하고, 결과와 입력 버전을 기록한다.

시험 데이터의 채널·교정·단위·반복 측정 정보를 확인한다. 전문가에게 요구사항 기준을 요청하되 확보하지 못하면 대회용 가상 요구사항임을 표시한다. 강체 CFD의 재료 이름만 변경해 제조 방식별 소음·변형 차이를 예측하지 않는다. 실제 케이스의 형상·조건이 공개 데이터와 다르면 CFD 연동 시연을 별도로 구분한다.

### As-Is / To-Be

| As-Is — 인터뷰로 검증할 문제 가설 | To-Be — 개발 목표 |
|---|---|
| 담당자가 기록을 찾아 비교 조건을 대조 | 자연어 요청에 맞는 사례 검색과 조건 차이 표시 |
| 기존품 대비 개선과 요구사항 충족을 별도로 정리해야 함 | 절대 기준 충족과 상대적 개선을 구분한 비교표 |
| 미측정 조건에 어떤 추가 검증이 필요한지 다시 검토 | 증거 부족을 식별하고 가능한 해석·필요 실측으로 분기 |
| 해석 준비·진행 확인·보고에 반복 개입 | 승인형 실행과 상태 기록, 근거 보고 후 사람 검토 |

### 목표 성능 및 검증

- 기존 근거 재사용·추가 해석·판단 보류의 **3개 경로**를 동일 환경에서 시연한다.
- 정상·조건 불일치·정보 누락·승인 거부·실행 실패를 포함한 테스트를 구성한다. 승인 거부 테스트에서는 solver 실행 호출이 **0회**여야 한다.
- 비교 결과마다 원본·조건·판정 기준·출처 유형을 연결하고, 미확인 항목은 판단 불가로 남긴다.
- 실제 solver 이벤트/상태·결과 파일과 화면 표시가 일치하는지 확인한다.
- 동일 과제의 수작업과 에이전트 작업에서 총 경과 시간, 사람 개입 시간, 검토 사례 수, 누락·오판을 비교한다. 작은 표본의 결과를 일반적 절감률로 확대하지 않는다.
- 전문가에게 품질 절차와 음향·해석 범위 검토를 요청하고, 반영 사항과 미검증 항목을 구분한다.

### 주요 위험과 대응

공개 데이터 메타데이터 부족은 경고·판단 보류로 처리한다. Fluent 사례 실행은 사용자 보고상 검증 완료됐고, 제품 내 호출 경로 연결을 초기에 검증한다. API 지원 미정에 대비해 모델 호출부를 분리하고 비용 한도를 기록한다. 주어진 기간에는 H200·GraphRAG·자동 최적화·복잡한 CAD·FSI를 제외한다.

## 팀 검토 메모 — 제출 본문에서 제외

- 로컬 웹 UI·Windows 실행은 사용자 결정이다. 역할의 추가 배분은 팀 확인이 필요하다.
- Fluent 케이스 실행·출력 지표 검증은 사용자 보고다. 계획서 최종본에는 케이스명·출력 항목·검증 로그를 팀이 기록해 제시한다.
- 계획서 작성 9/27, 결과물 10/6, 발표 10/12는 사용자 제공 일정이다.
- ENOLA 데이터 사전 분석은 기획 검토 중 수행한 분석이며, 팀 제품 구현 완료와 구분한다.
