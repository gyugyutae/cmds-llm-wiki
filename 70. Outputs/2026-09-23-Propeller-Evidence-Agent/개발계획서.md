# 개발계획서

## 과제명

프로펠러 제조 변경 시제품의 요구사항 검토를 지원하는 AI 에이전트

## 1. 과제소개 (1페이지 이내)

### 목적

재료나 제작 공법이 달라진 프로펠러 시제품을 검토할 때, 기존 시험·해석 사례가 새 조건에도 적용되는지 판단하고 요구 추력·소음·토크 기준의 충족 여부와 추가 CFD·실측 필요성을 근거와 함께 제시하는 AI 에이전트를 개발한다. 최종 판단과 다음 단계 진행 여부는 담당자가 결정한다.

### 개발 내용 설명

1. 자연어 요청에서 비교 목적, 후보, 시험 조건, 요구 추력·소음·토크 기준을 정리하고 사용자에게 확인받는다.
2. SQLite의 기존 사례를 ‘직접 재사용 가능’, ‘참고 가능’, ‘새 증거 필요’로 분류하고 조건 차이와 출처를 표시한다.
3. 비교 가능한 수치는 Python으로 계산한다. 요구 기준 충족 여부와 기존품 대비 개선 여부를 구분하고, 근거가 부족하면 판단을 보류한다.
4. 기존 근거의 적용 범위를 확인한 뒤, CFD 항목은 점검 목록과 담당자 승인 후 Fluent로 검토한다. 실측이 필요한 항목은 추가 시험 대상으로 제시한다.
5. Streamlit 화면에 실제 실행 상태와 결과를 표시하고, 수치·출처·조건·계산·한계를 포함한 검토 보고서를 만든다.

공개 ENOLA 연구 데이터의 XOAR 9×7 ABS·PA12 제작품을 7350RPM 조건에서 비교하고, 미측정 8500RPM이나 새 형상 질문으로 사례 재사용·추가 해석·판단 보류의 분기를 시연한다. 확보 데이터에서는 재료와 제작 방식이 함께 달라지므로 재료만의 효과라고 단정하지 않는다. 연구용 시연이며 제품 출하 승인이나 안전 인증을 대신하지 않는다.

### 기대효과

기존 자료 검색과 조건 대조, 결과 정리를 지원해 품질 검토자가 재사용 가능한 근거와 추가 검증 필요성을 한눈에 확인하도록 한다. 시연에서는 전체 처리 시간, 사람의 개입 시간, 누락·오판 여부를 함께 측정하며, 검증 전에는 업무 절감률을 단정하지 않는다.

## 개발 환경 및 기술 스택

예상 사용 AI 모델: 기타 — 도구 호출을 지원하는 모델을 검토하고 9월 29일 대회 지원 안내 후 선정 예정

예상 사용 프레임워크: LangGraph, Streamlit, PyFluent 및 MCP 연동

예상 개발 언어: Python

클라우드 지원 필요 여부: 아니오 — Windows Pro PC에서 로컬 실행하고 브라우저로 접속한다. 단, 선정 모델에 따라 LLM API는 원격 호출될 수 있다.

## 2. 개발계획 (2페이지 이내)

### 개발방법

Windows Pro PC에서 Streamlit 웹 화면, Python 에이전트, SQLite, Ansys Fluent를 연결한다. LangGraph가 요청 정리, 사례 검색, 조건 비교, 추가 검증, 승인·보류·오류 흐름을 관리한다. LLM은 요청 해석과 결과 설명을 맡고, 단위·조건 확인과 수치 계산은 Python 규칙으로 처리한다. CLI는 개발·점검용으로만 사용하며, 담당자가 승인하지 않은 Fluent 실행은 허용하지 않는다.

Fluent Student에서 시연 케이스를 실행하고 출력 지표를 확인한 상태라고 팀은 보고했다. 제품 화면의 사람 승인부터 PyFluent/MCP 호출, 실제 실행 상태와 결과 수집, SQLite 저장까지 연결하고 재현 로그를 확보한다. 일반 유동 CFD 결과를 실측 소음으로 표현하거나, 재료명만 바꾼 해석으로 재료별 소음 차이를 입증했다고 주장하지 않는다.

### 일정

9월 28일~29일: 검증된 Fluent 케이스·출력 지표·로그 정리, 지원 모델 확인, 자문 인터뷰 시작

10월 4일~5일: 정상·조건 불일치·정보 누락·승인 거부·실행 실패 시나리오 점검, 오류 수정과 발표자료 준비

10월 6일: 결과물 검증 및 제출

10월 12일: 발표 심사

### 개발방법론

요구사항·근거 확인 → 핵심 검색·비교 흐름 구현 → 사람 승인형 Fluent 연동 → 시나리오 검증 순으로 단계적으로 개발한다. 각 단계에서 팀원이 결과를 확인한 뒤 다음 단계로 진행한다. 전문가 인터뷰로 현행 업무 절차와 실제 요구 기준을 확인하고, 확인되지 않은 기준은 대회용 가상 요구사항으로 구분한다. 정상 흐름뿐 아니라 입력 누락, 조건 불일치, 승인 거부, 실행 실패를 포함해 반복 점검한다.

### 목표 성능 (정량·정성)

정량 목표 및 검증 기준:

1. 기존 사례 재사용, 추가 CFD 검토, 근거 부족으로 인한 판단 보류의 3개 경로를 각각 1회 이상 시연한다(3/3 경로).
2. 정상, 입력 누락, 조건 불일치, 승인 거부, Fluent 실행 실패의 5개 시나리오에서 기대한 분기와 안내가 모두 나오는지 확인한다(5/5).
3. 담당자가 실행을 거부한 경우 Fluent 호출 횟수는 0회여야 한다.
4. 수치 결과가 포함된 시연 보고서의 모든 결과에 출처, 시험 조건, 적용 기준, 계산값, 한계를 연결한다(대상 항목 100%).
5. 실제 Fluent 실행 시 화면에 표시된 상태·결과와 로그·산출물이 일치하는지 확인한다(실행 건 100%).

정성 목표: 요구 기준 충족과 기존품 대비 개선을 구분하고, 사례의 적용 범위와 조건 차이를 사용자가 확인할 수 있게 한다. 근거가 부족한 질문에는 결론을 단정하지 않고 추가 CFD, 실측 또는 판단 보류를 제시한다. 최종 판단은 담당자가 내리며, 제한된 시연 결과를 제품 승인·안전 인증이나 일반적인 업무 절감률의 근거로 사용하지 않는다.

### As-Is / To-Be

As-Is (검증할 문제 가설): 품질 담당자가 기존 기록과 시험 조건을 직접 찾아 대조하고, 요구사항별 결과와 추가 시험 필요성을 별도로 정리해야 할 수 있다. 실제 절차와 부담은 품질 엔지니어·시험 및 해석 전문가 인터뷰로 확인한다.

To-Be (개발 목표): 자연어 요청을 구조화하고, 기존 사례의 재사용 가능성·조건 차이·출처를 함께 보여준다. 요구 기준 충족 여부와 기존품 대비 개선 여부를 나누어 보고하며, 근거가 부족하면 추가 CFD와 실측 필요성을 구분해 담당자에게 제시한다.

### 팀원 역할분담

김규태(팀장): 에이전트 흐름, MCP·Fluent 연결, SQLite 및 전체 통합을 담당한다.

백창민: 비교 규칙, 데이터·음향 처리, 단위와 조건 검사를 담당하고 비교 결과 화면과 시나리오 구성을 검토한다.

김석준: 전문가 인터뷰와 소통, 시연 CFD 케이스·수동 실행 및 결과 검토를 맡고 점검 순서와 시연 절차를 전문가에게 확인한다.

※ 세부 UI 업무 등 추가 역할 배분은 팀 협의로 확정한다.

### 주요 위험 및 대응

공개 음향 데이터의 마이크 위치·교정·반복 측정 정보가 부족하면 소음 우열 판단을 보류하고 확인되지 않은 메타데이터를 표시한다. 실제 요구 기준을 확보하지 못하면 가상 기준임을 명시한다. 제품 화면과 Fluent 자동 연결이 제한되면 검증된 실제 실행 범위만 시연하고, 가상 진행 상태를 실제 실행처럼 보여주지 않는다. CFD는 물리적 타당성이나 인증을 보장하지 않으므로 결과의 한계를 함께 제시한다. 제한된 개발 기간에는 H200, GraphRAG, 자동 최적화, 복잡한 CAD 기능을 제외한다.
