# Rotor Engineering Knowledge Agent — PRD

작성일: 2026-09-25
상태: 팀 합의·구현 기준안
제품 시연명: **Propeller Evidence Agent**

> **한 문장 제품 정의:** 담당자가 자연어로 프로펠러 CFD 검토를 요청하면, 에이전트가 실제 엔지니어 점검 순서에 맞춰 입력·해석 조건을 확인하고, 승인된 케이스만 Fluent에서 실행하며, 검토 과정과 근거를 실시간으로 보여주는 항공우주 제조 검토 도구.

## 1. 문제와 제품 방향

프로펠러 후보를 CFD로 검토할 때는 형상 파일만 넣고 계산 버튼을 누르는 것으로 충분하지 않다. 형상 버전, 단위, 격자 품질, 경계조건, 솔버 설정, 수렴 상태와 결과 파일을 순서대로 확인해야 한다. 과거 케이스와 조건이 다르면 비교가 성립하지 않을 수 있고, 실행을 자동화하더라도 사용자는 무엇이 검사됐고 왜 멈췄는지 확인할 수 있어야 한다.

우리의 MVP는 **새 형상의 물리적 타당성을 보장하거나 최적 프로펠러를 자동 발견하는 제품이 아니다.** 검증 가능한 한 개의 기준 케이스와 제한된 파라미터 범위에서, 전문가가 확인한 점검 절차를 반복 가능하게 적용하고 CFD 작업의 실제 상태와 증거를 기록하는 **승인형 CFD 실행 하네스**다.

### 핵심 사용자

- 1차 사용자: 프로펠러 시험·해석을 검토하는 제조품질 담당자
- 협업 사용자: CFD/설계 엔지니어, 시험 담당자, 기술 검토자
- 사용 맥락: 후보 형상이나 기존 해석 케이스가 준비됐을 때, 실행 전 조건을 확인하고 승인된 계산을 재현 가능하게 수행한 뒤 결과를 보고해야 하는 상황

## 2. 이번 대회 MVP의 범위

### 포함

- Windows Pro PC 한 대를 통합 실행 환경으로 사용
- Ansys Fluent Student 설치·실행 가능 여부를 실제 케이스로 조기 검증
- 단순하고 명시된 파라미터만 바꾸는 후보 케이스 구성; 복잡한 CAD 자동 설계는 하지 않음
- 자연어 요청의 목표·입력 파일·후보 파라미터를 구조화
- 팀이 인터뷰와 검토로 만든 순서형 체크리스트 실행
- 체크 결과, 실제 도구 호출, Fluent 상태·수렴 지표를 화면에 표시
- 모든 필수 게이트를 통과한 뒤 사람 승인으로 해석 시작
- 결과·입력·버전·한계·보류 근거가 연결된 분석 보고서 생성
- 실제 비교 가능한 시험 사례가 있을 때만 소음 비교를 제시

### 제외

- H200 의존 기능: 제공 조건과 접근 방법 확인 전까지 MVP에서 제외
- GraphRAG 및 대규모 지식 그래프
- 자동 형상 최적화, 자유 형상 생성, 복잡한 자동 CAD/메싱
- 무검토 자동 실행, 임의의 조건을 AI가 보완하는 동작
- 소음 예측 모델 또는 검증되지 않은 새 형상의 물리적 성능 예측
- 인증·안전성 보증, 현업의 보편 표준을 구현했다는 주장

## 3. 핵심 기능 4가지

### 1) 자연어 요청을 실행 가능한 케이스로 변환

사용자가 “이 프로펠러 후보를 기준 케이스와 같은 조건으로 점검하고, 승인 전에 차이를 보여줘”처럼 요청한다. 에이전트는 목표, 파일, 형상 버전, 변경 파라미터와 필요한 조건을 정해진 스키마로 추출한다. 불명확하거나 필수 입력이 없는 항목은 추정하지 않고 확인 대상으로 남긴다.

### 2) 전문가 순서 기반 CFD 사전 점검

에이전트는 인터뷰와 실제 케이스 검토로 확인된 순서대로 점검을 실행한다. 예: 파일·형상 버전 확인 → 단위/좌표/파라미터 범위 확인 → 메시 상태·품질 확인 → 경계조건·재료·회전 조건 확인 → 솔버 설정 및 기준 케이스와의 차이 확인. 항목마다 `통과 / 경고 / 보류`와 관측값·기준·근거를 기록한다. 인터뷰 전에는 “전문가 검토 체크리스트”라 부르지 않고 **팀 초안**으로 표시한다.

### 3) 승인 후 Fluent 실행과 과정의 실시간 시각화

점검을 통과한 경우에도 해석 전 승인 버튼을 둔다. 승인 후 실제 Fluent 세션에서 케이스를 열고, 허용된 설정을 적용하고, 실행한다. 화면 타임라인은 단계별 상태와 가능한 실제 solver iteration, residual/monitor 값, 도구 결과를 표시한다. PyFluent는 솔버 이벤트·모니터 콜백으로 진행 정보를 전달할 수 있고, LangGraph는 노드 업데이트나 사용자 정의 이벤트를 스트리밍할 수 있다. 다만 PyFluent-MCP 호출 하나가 iteration 이벤트를 자동으로 UI에 흘려보낸다고 가정하지 않는다. 조기 기술검증으로 MCP 경유 실시간성이 안 되면 PyFluent 이벤트 브리지 또는 단계·주기적 상태조회로 구현 범위를 조정한다. [LangGraph stream modes](https://reference.langchain.com/python/langgraph/types/StreamMode) · [PyFluent events](https://fluent.docs.pyansys.com/version/dev/user_guide/events.html) · [PyFluent monitors](https://fluent.docs.pyansys.com/version/dev/user_guide/monitors.html)

### 4) 근거 연결 보고서와 비교 가능성 판정

보고서에는 요청, 사용 파일과 해시, 형상/케이스 버전, 체크리스트 결과, 기준 케이스 대비 차이, 승인자, Fluent 설정·실행상태, 수치 결과, 비교 가능성, 한계 및 후속 조치를 담는다. 소음은 측정/해석 자료와 조건이 비교 가능할 때에만 비교한다. 조건이 다르거나 물리 모델·검증 근거가 부족하면 소음 우승자를 제시하지 않는다.

## 4. 데모의 킥: 결과 화면이 아니라 ‘검토 과정이 보이는 실행’

**권고: 완전 자동으로 돌리고 결과만 보여주기보다, 자동 사전 점검 + 명시적 승인 + 실제 진행 시각화를 결합한다.** 결과만 보여주면 일반적인 챗봇 보고서처럼 보이고, 무승인 자동 실행은 신뢰·안전·재현성 질문을 부른다. 반대로 실제 점검 이벤트를 시간 순서로 보여주면 관람자는 에이전트가 무엇을 확인하고 어떤 도구를 호출했는지 눈으로 따라갈 수 있다.

화면에는 AI의 숨은 추론이나 연출된 “생각 중” 문장을 보여주지 않는다. 다음과 같은 **관측 가능한 작업 증거**만 보여준다.

| 화면 요소 | 표시 예 | 구현 원칙 |
|---|---|---|
| 요청 구조화 | 목표: 기준 케이스 재사용 검토 / 변경 변수: 피치각 | 원문과 추출값을 나란히 보여주고 수정 가능 |
| 점검 타임라인 | 형상 파일 확인 완료 → 메시 품질 확인 경고 → 경계조건 대조 완료 | LangGraph 실제 노드 이벤트에서 상태 갱신 |
| 근거 카드 | 요구값, 실제값, 단위, 출처 파일/위치, 판정 규칙 | 없는 근거는 빈칸/미확인으로 표시 |
| 승인 게이트 | 실행 예정 케이스·조건 변경·예상 작업 표시 후 승인 대기 | 사람의 승인 이전에는 solver 실행 금지 |
| 라이브 실행 | Fluent 세션, iteration, residual/force monitor, 실행/종료 상태 | solver 이벤트나 실제 상태조회값만 표시; 가짜 진행률 금지 |
| 최종 케이스 기록 | 입력 hash, 실행 프로파일, 결과 파일, 경고, 한계 | 보고서에서 원본 산출물로 추적 가능 |

### 데모 시나리오

1. **성공 경로:** 실제 기준 케이스를 선택하고 자연어로 제한된 파라미터 후보를 요청한다. 요청 구조화 → 순서형 체크 → 결과/근거 확인 → 사람 승인 → Fluent 실행 및 진행 이벤트 → 케이스 기록 보고서까지 보여준다.
2. **보류 경로:** 형상 버전 누락, 잘못된 단위, 메시 품질 실패 또는 필수 경계조건 불일치 중 하나를 의도적으로 입력한다. 에이전트는 어느 검사에서 어떤 실제값이 기준을 벗어났는지 보여주고 solver를 시작하지 않는다. 해결 방법 또는 추가로 필요한 자료도 제시한다.

가능하면 같은 세션에서 두 경로를 연속 시연한다. **정상 실행 능력과 안전하게 멈추는 능력을 모두 눈으로 증명**하기 때문이다.

## 5. ‘보류 근거 설명’은 구현 가능한가?

가능하며, MVP에서도 현실적으로 구현할 수 있다. 핵심은 LLM에게 보류 사유를 자유롭게 지어내게 하지 않는 것이다.

각 검사는 아래와 같은 구조화 결과를 낸다.

```json
{
  "checkId": "boundary_condition_match",
  "status": "hold",
  "observed": {"rpm": 8200, "unit": "rpm"},
  "expected": {"rpm": 8500, "unit": "rpm"},
  "evidence": "case_setup.json#/operating_conditions/rpm",
  "reasonCode": "REFERENCE_CONDITION_MISMATCH",
  "nextAction": "기준 케이스와 동일한 RPM으로 조건을 맞추거나, 변경 조건을 담당자가 승인하세요."
}
```

Python/검증 규칙이 실제값과 기대값을 비교해 상태·사유 코드를 결정하고, LLM은 이미 결정된 사실을 읽기 쉬운 문장으로 표현한다. 사유 코드가 없거나 증거를 읽지 못하면 “판정 불가—담당자 확인 필요”로 처리한다. 테스트는 알려진 통과/실패 fixture를 만들고 기대한 코드·상태가 나오는지 자동 검증한다. 이렇게 하면 “왜 보류했는가”를 값·규칙·출처로 재현할 수 있다. 이것은 **주어진 검사 규칙과 파일이 정확하다는 조건에서의 절차적 타당성**이지, CFD 결과의 물리적 타당성 보증은 아니다.

## 6. 차별성과 심사에서 강조할 점

### 우리만의 차별성

1. **자연어에서 실제 엔지니어링 실행까지:** 채팅 답변에서 멈추지 않고 점검·승인·Fluent 작업·결과 기록으로 연결한다.
2. **절차를 강제하는 에이전트:** 체크리스트 순서, 실행 게이트, 실패 분기를 워크플로우에 내장한다. 자유 대화가 중요한 검사를 건너뛰지 못하게 한다.
3. **증거가 보이는 진행:** 단계별 결과를 숫자·기준·파일 출처와 연결하고, 실제 solver 이벤트를 실시간으로 보여준다.
4. **설명 가능한 보류:** “AI가 위험하다고 판단”이 아니라 불일치 필드·관측값·기대값·근거와 다음 조치를 보여준다.
5. **과장하지 않는 CFD:** 해석이 실행됐다는 것과 해석이 물리적으로 검증됐다는 것을 분리하고, 비교 가능한 사례가 있을 때만 소음 결과를 비교한다.

### 발표 문장

> “우리는 AI에게 항공우주 안전판정을 맡기지 않았습니다. 엔지니어가 실제로 확인하는 순서를 워크플로우로 고정하고, AI가 자료를 연결하고 도구가 검사하게 했습니다. 관람객은 승인 전 점검부터 Fluent 진행 상황까지 볼 수 있고, 근거가 깨지면 왜 멈췄는지 확인할 수 있습니다.”

대상 수상을 보장할 수는 없다. 공식 평가표가 공개되면 그 항목에 맞춰 데모·검증 증거를 재배치한다. 심사 전까지는 작동하는 end-to-end 흐름, 실제 케이스, 전문가가 검토한 점검 순서, 측정 가능한 시간/오류 개선을 준비한다.

## 7. 실제 케이스와 인터뷰 증거 확보 계획

### 시연 케이스 확보

연구실 또는 팀원이 가진 propeller CAD/Fluent 케이스를 **1순위**로 요청한다. 파일 소유자와 사용 목적을 확인하고, 대회 시연 허가와 민감정보/형상 공개 범위를 명확히 한다. 원본은 수정하지 않고 demo copy를 사용한다.

가능한 한 케이스 번들을 함께 확보한다.

- CAD 원본과 형상/설계 버전 식별 정보
- Fluent case/data (`.cas.h5` / `.dat.h5`) 또는 mesh, journal/setup 파일
- 형상 단위, 좌표/회전축, 회전속도, 유체/재료, 경계조건
- 격자 설정/품질 정보, 솔버·모델 설정과 실행 이력
- 결과/측정 자료, 알려진 기준 결과와 담당자 해석
- 출처·소유자·사용 허가·취득일·파일 hash

먼저 Fluent GUI에서 케이스를 수동 실행해 파일 호환성과 완료 여부를 확인한다. 다음으로 PyFluent 연결, MCP 상태/mesh 검사, 승인형 실행, 결과 저장을 각각 스모크 테스트한다. 케이스를 1–2일 안에 확보하지 못하면 공개/교육용 Fluent 예제 또는 연구 공개 자료로 **연동 파이프라인만** 시연하되, 이를 실제 프로펠러 현장 케이스라고 부르지 않는다. 프로펠러 형상·소음 주장을 하려면 해당 근거가 있는 별도 데이터가 필요하다.

### 현업 인터뷰

프로펠러 CFD/시험/품질 담당자 또는 Ansys 경험이 있는 실무자·지도 멘토 1–2명에게 20–30분 인터뷰를 요청한다. 질문은 실제 업무를 회상하도록 구체적으로 한다.

1. 최근 프로펠러 케이스 하나를 검토할 때 실제로 확인한 순서는 무엇이었나?
2. 단계마다 어떤 파일/값을 보고, 왜 확인하나?
3. 어떤 값·상태면 통과, 경고, 중단 또는 재검토인가? 기준 출처는 무엇인가?
4. 자주 틀리는 설정이나 다시 하는 작업은 무엇이며, 그 결과 시간·품질에 어떤 영향이 있나?
5. 자동화에 맡겨도 되는 단계와 반드시 사람이 승인해야 하는 단계는 무엇인가?
6. 결과를 신뢰하기 전에 어떤 수렴·격자·보존·검증 정보를 확인하나?
7. 우리 체크리스트에서 틀렸거나 빠진 항목이 무엇인가?

동의를 받고 날짜·직무 맥락·질문/답변·인용 허가를 기록한다. 실명·회사명 공개는 별도 허가를 얻는다. 인터뷰 한두 건은 현장 절차의 보편성을 증명하지 않는다. 결과물에는 “인터뷰한 담당자 검토를 반영한 데모 체크리스트”라고 범위를 정확히 쓴다.

### 최소 증거 패키지

- 사용 허가된 실제/교육 케이스 1개와 그 출처·버전·파일 hash
- 인터뷰 메모 1–2건과 체크리스트 변경 이력
- 통과 fixture, 보류 fixture, Fluent 실행 로그의 재현 가능한 테스트
- 단계별 이벤트와 최종 보고서가 일치하는 화면 녹화/시연
- 사전 점검 소요 시간, 수동 대비 반복 시간, 검사 누락/보류 정확도에 대한 작은 평가표

## 8. 제조 효용과 기대 비즈니스 가치

단기 효용은 소음 저감 자체가 아니라 **시험/해석 케이스 준비와 사전 검토의 반복·누락·추적 부담을 줄이는 것**이다.

- 형상/해석 조건과 파일 버전을 한 번에 확인해 잘못된 케이스 실행 위험을 낮춤
- 검토 순서를 표준화해 담당자별 편차와 인수인계 부담을 줄일 가능성
- 조건 불일치 시 실행 전에 멈춰 불필요한 해석 시간을 줄일 가능성
- 입력·도구·결과·승인 이력을 묶어 검토 보고서 작성과 재현을 지원
- 이후 축적된 케이스를 검색/비교해 중복 해석 검토와 지식 손실을 줄일 기반 마련

잠재 고객은 프로펠러·eVTOL·회전익 개발/시험/품질 팀이다. 비즈니스 가설은 CFD 엔지니어의 준비·검토 시간과 재실행 비용 절감, 시험/해석 이력의 재사용성 향상이다. 아직 인터뷰와 시간 측정 전이므로 절감률, 매출, 불량 감소를 사실처럼 제시하지 않는다. 파일 보안·라이선스·검증 책임·현장 시스템 연동이 상용화 장벽이다.

잘 되었을 때의 다음 단계는 검증된 점검 템플릿과 사례 라이브러리를 여러 부품/팀으로 확장하고, 실제 생산·시험 데이터와 연결해 어떤 검토가 시간을 절약했는지 측정하는 것이다. 장기적으로는 검증된 범위 내 파라미터 스윕과 설계 후보 추천을 추가할 수 있지만, 현재 MVP의 약속은 아니다.

## 9. 구현 가능성 및 2주 계획

**판정: 제한된 실제 케이스의 사전 점검 + 승인 + Fluent 실행 + 진행 표시 + 보고서까지는 2주 내 시연을 목표로 할 수 있다.** 다만 Fluent Student 설치/제약, 케이스 파일 호환, PyFluent/MCP 접근, iteration 이벤트 연결은 첫 1–2일의 기술 스파이크에서 확인해야 한다. 모든 과정을 완전 자율화하거나 새 형상의 신뢰 가능한 소음 예측을 2주 안에 완성하는 범위는 아니다.

| 시점 | 완료 기준 |
|---|---|
| 1–2일 | Windows 설치/라이선스 확인, 실제 또는 대체 케이스 확보, Fluent GUI 수동 실행, PyFluent 연결, MCP 호출과 모니터 이벤트 가능 여부 확인 |
| 3–4일 | 전문가/멘토 인터뷰, 순서형 체크리스트 초안 검토, 규칙·사유 코드 및 최소 데이터 구조 확정 |
| 5–7일 | 자연어 입력 구조화, 파일/버전/조건 점검, 통과·보류 결과를 UI에 이벤트로 표시 |
| 8–10일 | 사람 승인 후 Fluent 실행, 진행 상태/실제 지표 스트리밍, 오류·중단 상태 처리 |
| 11–12일 | 근거 보고서와 케이스 기록 생성, 비교 가능한 기존 소음 사례가 있으면 비교 기능 연결 |
| 13–14일 | 성공/보류 경로 리허설, 설치 PC에서 재현, 데모 영상과 한계 설명 준비 |

최우선 위험은 **케이스/라이선스/MCP를 늦게 확인하는 것**이다. 첫 이틀 안에 실제 solver가 돌아가지 않으면 MCP 자체에 매달리지 말고 PyFluent 직접 연결이나 Fluent journal/API로 축소한다. 시각적 데모는 단계 이벤트를 유지하고, solver iteration 실시간 표시가 불가능하면 그 한계를 명시하며 실제 상태 polling으로 대체한다.

## 10. 성공 지표와 테스트 기준

- E2E 데모가 동일 PC에서 처음부터 끝까지 재현된다.
- 입력한 체크 항목마다 실제 상태·값·근거가 표시된다.
- 보류 fixture는 반드시 solver 실행 전에 차단되고, 정확한 사유 코드를 낸다.
- 승인 없이는 solver 실행 tool이 호출되지 않는다.
- 화면의 진행 상태와 Fluent 로그/이벤트/산출물이 일치한다.
- 보고서의 케이스 ID·입력 파일·설정·결과가 재현 가능하게 연결된다.
- 전문가/멘토가 체크리스트에서 수정하거나 동의한 부분과 미검증 부분이 구분된다.
- 수동 점검과 비교한 시간 차이를 동일 과제로 측정한다. 작은 데모 표본으로 일반적인 생산성 향상을 주장하지 않는다.

## 11. 주요 위험과 정직한 한계

| 위험 | 대응 |
|---|---|
| 실제 propeller case를 못 구하거나 공개가 불가 | 첫 1–2일에 확인. 대체 예제는 연동 시연으로만 설명하고 현장 유효성 주장은 금지 |
| Student 라이선스/기능 제약 또는 Fluent 실행 실패 | 실제 설치에서 조기 검증. PyFluent/MCP가 막히면 journal/API 호출로 축소 |
| MCP 도구가 solver 진행 이벤트를 실시간 중계하지 않음 | PyFluent event bridge 또는 polling 기술 스파이크; 연출된 진행률은 사용하지 않음 |
| 체크리스트가 전문가 표준을 대표하지 않음 | 인터뷰 범위와 검토자를 공개하고 팀 초안과 검토 완료 항목을 구분 |
| CFD가 실행돼도 물리적으로 맞지 않을 수 있음 | 검증된 케이스와 모델 한계 명시. 수렴/메시 검사는 물리적 정확도 인증이 아님 |
| 소음 데이터가 부족하거나 조건이 달라 비교 불가 | 소음 승자/인과 설명을 보류하고, 비교 불가 이유와 필요한 동일 조건 데이터를 제시 |
| 자연어 추출 오류·규칙 오적용 | 구조화된 사용자 확인, 결정론적 검사, 테스트 fixture, 사람 승인 |
| 하드웨어/AI 기능에 범위가 분산됨 | H200·GraphRAG·최적화 제외; 핵심 성공 기준은 한 케이스의 보이는 E2E 실행 |

## 12. 팀의 즉시 할 일

1. 케이스 파일 보유자에게 연락해 사용 허가·형상 자료·실행 파일·조건을 요청한다.
2. Fluent Student를 Windows PC에 설치하고 확보한 케이스를 GUI로 연 뒤 짧은 계산을 완료한다.
3. PyFluent 직접 세션, PyFluent-MCP 상태/mesh 기능, 실행 후 로그 수집을 각각 분리해 테스트한다.
4. solver iteration/residual 이벤트를 화면에 전달하는 최소 기술 데모를 만든다. 불가 시 polling 대안을 확정한다.
5. 현업자/멘토 인터뷰를 진행하고 체크리스트 순서와 중단 기준을 리뷰받는다.
6. 팀이 체크리스트 v0, 이유 코드, 화면 상태 표현, 승인 책임자를 합의한다.
7. 테스트용 통과/보류 케이스를 최소 2개 만들고, 자동 테스트로 solver 차단 여부를 검증한다.
8. 실제 소음 측정/검증 데이터가 확보될 때만 소음 비교를 추가한다.
