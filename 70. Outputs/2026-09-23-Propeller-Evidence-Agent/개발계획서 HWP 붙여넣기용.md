# 개발계획서

## 과제명

프로펠러 제조 변경 시제품의 요구사항 검토를 지원하는 AI 에이전트

## 과제소개 (1페이지 이내)

### 목적

프로펠러의 재료나 제작 공법을 변경해 시제품을 만들면, 품질 담당자는 해당 시제품이 요구 추력과 소음·토크 제약을 만족하는지 검토해야 한다. 이때 기존 시험·해석 사례가 새 시제품의 근거로 재사용 가능한지 확인하고, 부족한 항목에는 추가 해석이나 실측이 필요한지 판단해야 한다. 본 과제는 이 검토를 돕는 AI 에이전트를 개발한다. 에이전트는 사람이 제시한 가설과 기준을 바탕으로 사례와 조건을 대조하고, 추가 검증 절차를 안내하며, 근거가 연결된 보고서를 작성한다. 최종 판단과 다음 단계 진행 여부는 사람이 결정한다.

### 개발 내용

1. 사용자의 자연어 요청에서 비교 목적, 후보, 시험 조건, 요구 추력, 소음·토크 기준을 정리하고 확인받는다.
2. SQLite에 저장된 기존 사례를 직접 재사용 가능, 참고 가능, 새 증거 필요의 세 단계로 분류하고 조건 차이와 출처를 보여준다.
3. 비교 가능한 수치는 Python으로 계산한다. 요구사항 충족 여부와 기존품 대비 개선 여부를 구분해 충족, 미충족, 판단 불가로 제시한다.
4. 미측정 조건이나 새 형상 질문에는 기존 근거의 적용 범위를 먼저 확인한다. Fluent로 산출 가능한 항목은 점검 목록과 사람 승인 후 실행하고, 실측이 필요한 항목은 추가 시험 대상으로 남긴다.
5. 웹 화면에서 실제 점검·도구 실행 상태와 결과를 보여주고, 수치·출처·조건·한계를 담은 검토 보고서를 생성한다.

시연은 공개 ENOLA 연구 데이터의 XOAR 9×7 ABS·PA12 제작품을 7350RPM 조건에서 비교한다. 이어 “미측정 8500RPM이나 새 형상에서도 같은 결론인가?”라고 질문해 사례 재사용, 추가 해석, 판단 보류의 분기를 보여준다. 확보 데이터에서는 재료와 제작 방식이 함께 달라지므로 재료만의 효과라고 단정하지 않는다. 연구용 데이터 시연이며 제품 출하 승인이나 안전 인증을 대신하지 않는다.

### 기대효과

기존 자료 검색과 조건 대조, 비교 결과 정리를 지원해 품질 검토자가 근거와 추가 검증 필요성을 한눈에 확인하도록 한다. 전체 처리 시간뿐 아니라 사람의 실제 개입 시간, 누락·오판 여부도 측정한다. 검증 전에는 업무 절감률을 단정하지 않는다.

## 개발 환경 및 기술 스택

예상 사용 AI 모델: 기타 — 도구 호출을 지원하는 모델을 검토하고 9월 29일 대회 지원 안내 후 선정 예정

예상 사용 프레임워크: LangGraph, Streamlit, PyFluent 및 MCP 연동

예상 개발 언어: Python

클라우드 지원 필요 여부: 아니오 — Windows Pro PC에서 로컬 실행하고 브라우저로 접속한다. 단, 선정 모델에 따라 LLM API는 원격 호출될 수 있다.

## 개발 계획 (2페이지 이내)

### 개발방법 및 방법론

Windows Pro PC 한 대에서 Streamlit 웹 화면, Python 에이전트, SQLite, Ansys Fluent를 연결한다. CLI는 개발·점검용으로만 사용한다. 사용자의 요청을 구조화한 뒤 사례 검색, 조건 비교, 추가 검증 분기를 순서대로 수행한다. LangGraph는 단계·승인·보류·오류 흐름을 관리한다. LLM은 요청 해석과 결과 설명을 맡고, 단위·조건 확인 및 수치 계산은 Python 규칙으로 처리한다. 승인되지 않은 solver 실행은 허용하지 않는다.

Fluent Student에서 시연 케이스 실행과 출력 지표 확인은 완료했다고 팀이 보고했다. 제품 화면의 사람 승인부터 PyFluent/MCP 호출, 실제 상태·결과 수집, SQLite 저장까지 연결하고 재현 로그를 확보한다. 일반 유동 CFD 결과를 실측 소음으로 표현하지 않으며, 재료명만 바꾼 해석으로 재료별 소음 차이를 입증했다고 주장하지 않는다.

### As-Is / To-Be

As-Is — 검증할 문제 가설: 품질 담당자가 기존 기록과 시험 조건을 찾아 대조하고, 요구사항별 결과 및 추가 시험 필요성을 별도로 정리해야 할 수 있다. 이 업무의 실제 절차와 부담은 품질 엔지니어·시험 및 해석 전문가 인터뷰로 확인한다.

To-Be — 개발 목표: 자연어 요청을 구조화하고, 사례의 재사용 가능성과 조건 차이를 출처와 함께 표시한다. 요구 기준 충족 여부와 기존품 대비 개선 여부를 분리해 보고하며, 근거가 부족하면 가능한 해석과 필요한 실측을 구분해 사람에게 제시한다.

### 역할 분담

김규태(팀장): 에이전트 흐름, MCP·Fluent 연결, SQLite 및 전체 통합을 담당한다.

백창민: 비교 규칙, 데이터·음향 처리, 단위와 조건 검사를 담당한다. 비교 결과 화면과 테스트 구성도 함께 검토한다.

김석준: 전문가 인터뷰와 소통, 시연 CFD 케이스·수동 실행 및 결과 검토를 담당한다. 점검 순서와 시연 절차를 전문가에게 확인한다.

※ 세부 UI 업무 등 추가 역할 배분은 팀 협의로 확정한다.

### 목표 성능 및 검증 방법

1. 기존 사례 재사용, 추가 CFD 검토, 근거 부족으로 인한 판단 보류의 세 경로를 시연한다.
2. 승인 거부 시 Fluent 실행 호출이 0회인지 확인하고, 누락·조건 불일치·실행 실패를 올바르게 보류하는지 시험한다.
3. 모든 결과에 원본 출처, 시험 조건, 기준, 계산값 및 한계를 연결한다. 실제 기준을 전문가에게 확인하며, 확보하지 못한 기준은 ‘대회용 가상 요구사항’으로 표시한다.
4. 화면의 실행 상태·결과와 Fluent 실제 로그·산출물이 일치하는지 확인한다.
5. 같은 검토 사례에서 수작업과 에이전트의 총 경과 시간, 사람 개입 시간, 발견한 누락·불일치를 기록한다. 작은 표본으로 일반적인 절감률을 주장하지 않는다.

### 주요 위험 및 대응

공개 음향 데이터의 마이크 위치·교정·반복 측정 정보가 충분하지 않으면 소음 우열 판단을 보류하고 확인되지 않은 메타데이터를 표시한다. 실제 요구 기준을 확보하지 못하면 가상 기준임을 분명히 한다. 제품 내 Fluent 자동 연결이 제한되면 검증된 실제 실행 범위만 시연하고, 시뮬레이션된 진행 상태를 실제 실행처럼 보여주지 않는다. CFD는 물리적 타당성이나 인증을 보장하지 않는다. 제한된 개발 기간에는 H200, GraphRAG, 자동 최적화, 복잡한 CAD 기능을 제외한다.
