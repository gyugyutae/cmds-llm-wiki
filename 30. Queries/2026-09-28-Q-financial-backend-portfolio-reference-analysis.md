# 금융권 백엔드 포트폴리오 레퍼런스 분석과 김규태의 V0.1 설계

## 결론

이번 1차 조사에서 금융권 백엔드 신입·준신입 회고, 증권사 전형 후기, 공식 채용공고 1건과 공고 미러 1건, 카카오페이·토스 기술 글, 공개 코드 저장소까지 32개 레퍼런스를 선별했다. 합격 후기 3건은 당사자의 자기보고이며 합격 원인을 입증하는 통계가 아니다. 증권사 후기 1건은 1차 면접까지의 경험이라 합격 사례로 세지 않았다. 회사 기술 블로그는 현업 문제를 설명하는 1차 자료지만, 개인 프로젝트가 회사 내부 규모나 인프라를 그대로 복제하라는 뜻은 아니다.

가장 적합한 포트폴리오는 특정 증권 업무에 한정하지 않고, 금융 서비스 전반에 통하는 거래 정확성·데이터 정합성·실패 복구를 코드와 재현 가능한 테스트로 보여주는 Java 백엔드 프로젝트다. 현재 financial-lab의 계좌 이체를 첫 시나리오로 유지하되, 바깥 소개는 은행 계정계나 증권 OMS 한 가지로 좁히지 않는다.

이력서는 짧게 만들고 각 주장을 실행 가능한 코드·테스트·설계 기록·기술 글로 연결한다. 기술 블로그는 홈 링크가 아니라 문제 하나를 깊게 설명한 글로 이력서에서 바로 연결한다.

## 범위와 평가 기준

### 사용자 목표와 시간

- 목표 직무: 여의도 금융권의 백엔드 개발 신입. 은행·증권사·카드·결제·핀테크 및 금융 IT 전반을 열어 둔다.
- 학습 가능 시간: 주 30시간(이번 대화에서 사용자가 직접 밝힘).
- 위키에 기록된 졸업 예정 시점은 2027년 8월이다. 확인 응답을 기다리는 값이므로 채용 자격 판단에는 조건부로 쓴다.
- 위키의 financial-lab은 2026-09-26 스냅샷이다. 이번 분석에서는 2026-09-28 현재 코드도 읽기 전용으로 확인했다.

### 자료를 읽는 기준

1. 채용 결과가 작성자 글에서 분명한가?
2. 지원자의 자기 해석과 채용기관의 공식 요건을 구분했는가?
3. 실제 코드를 볼 수 있는가, README에 기능 주장만 있는가?
4. 문제·선택·검증·한계를 재현할 수 있는가?
5. 김규태의 현재 직접 구현 범위에 맞는가?

「100% 성공」 영상은 조사 절차의 출발점으로 삼았다. 영상 작성자는 합격 포트폴리오와 조언을 대량 수집해 이상적인 포트폴리오를 먼저 설계하자고 권하지만, 영상 말미에는 자신은 이력서·포트폴리오로 취업을 준비해 본 적이 없고 다른 사람 사례로 전략을 검증해야 한다고 밝힌다. 따라서 제목의 성공률이나 200~300개라는 숫자는 증거로 받아들이지 않고, 목표 역할 정의 → 사례 수집 → 공통 패턴과 예외 분석 → 현재 역량에 맞게 범위 조정이라는 절차만 적용한다.

## 분석: 이력서와 기술 글에 적용할 기준

### 이력서에는 주장과 근거의 연결이 보여야 한다

한 페이지 이력서에는 직무 정체성, 대표 프로젝트, 본인 기여, 검증 결과, 바로 확인할 링크를 넣는다. 프로젝트 문장은 “무슨 문제인가 → 내가 맡은 일 → 어려운 선택 → 무엇으로 확인했나” 순으로 압축한다. 수치에는 기준선·실험 환경·부하 패턴을 붙인다.

부하 예측은 설계 가정, 부하 테스트 수치는 실제 측정으로 구분한다. “월 사용자 1만 명을 가정해 분당 100건 요청 시나리오를 잡았다”와 “로컬 MySQL·4 vCPU/8 GB에서 k6로 60초 측정한 p95는 …”는 다른 종류의 주장이다. 실서비스를 운영하지 않았다면 실서비스 TPS라고 쓰지 않는다.

이 기준을 적용한 이상형 workload 한 줄은 [[2026-09-28-Q-ideal-financial-backend-portfolio]]에 추가했다. API 요청 RPS와 이체 TPS를 구분하고, 한국은행 계좌이체 통계는 시장 전체의 규모 비교에만 쓰며 DAU·피크 배수·서버 사양은 별도의 프로젝트 가정으로 분리했다.

### 기술 글은 재현 과정을 설명한다

1. 독자가 이해할 문제와 금융상 영향
2. 현재 설계와 요구사항·제약
3. 재현 가능한 실패 테스트·데이터·실행 방법
4. 선택한 방안과 비교한 대안
5. 같은 조건에서 측정한 전후 결과
6. 실패한 시도, 남은 한계, 적용하지 않을 조건

회사 블로그의 기술 밀도는 목표로 삼되, 회사 규모의 인프라는 복사하지 않는다. 첫 글 후보는 DB 저장을 구현한 뒤의 **“계좌이체에서 출금 후 예외가 나면 잔액과 거래기록은 어떻게 되는가? Spring transaction rollback을 실패 주입으로 확인하기”**다. 실패 주입과 DB 재조회가 아직 없으므로 지금 완성된 성과처럼 쓰지 않는다.

## 김규태 포트폴리오 V0.1

### 포지셔닝

**금융 서비스의 거래 규칙과 데이터 정합성을 Java 백엔드로 구현하고, 실패·재시도·동시 요청을 테스트와 SQL로 검증하는 신입 백엔드 개발자.**

현재 코드 단계에 맞춘 표현은 다음과 같다.

**금융 서비스의 거래 정합성 문제를 Java/Spring으로 학습·구현하며, 기능과 실패 조건을 직접 설명할 수 있는 백엔드 개발자로 성장하고 있습니다.**

프로젝트 바깥 이름은 기존 저장소 이름을 급히 변경하지 않는다. 금융권 전체에 통하는 후보로 “금융 거래 데이터 정합성 실험실 (Financial Transaction Integrity Lab)”을 검토하고, 첫 사용 사례가 계좌이체임을 명시한다.

### 대표 프로젝트의 검증 순서

1. 현재 메모리 기반 계좌 API의 성공·실패 테스트 범위를 완성한다.
2. 관계형 DB와 스키마를 추가하고 SQL·인덱스·제약조건을 설명한다.
3. 이체와 원장 기록이 한 DB transaction에서 함께 commit/rollback되는지 장애를 주입해 확인한다.
4. 동시 출금의 음수 잔액·lost update를 재현하고 조건부 UPDATE·낙관적 잠금·비관적 잠금 중 선택 근거를 남긴다.
5. 같은 idempotency key의 재시도에서 한 번만 상태가 바뀌는지 테스트한다. “요청이 정확히 한 번 전달된다”가 아니라 “중복 요청이 한 번의 유효한 결과를 만든다”고 쓴다.
6. 거래 원장과 잔액을 대사하고 불일치를 찾는 SQL/배치를 검증한다.
7. 실행계획·인덱스 전후 조회·p95/p99·오류율을 같은 조건에서 측정한다.
8. 실제 필요가 생긴 뒤에만 이벤트·캐시·분산 구조를 추가한다. 초기에 Kafka·Redis·Kubernetes·MSA를 붙이지 않는다.

하나의 대표 프로젝트를 은행·카드·PG·증권·핀테크 공고에 맞춰 설명한다. 은행은 원장/잔액 일관성, 카드·PG는 승인·취소·중복 요청과 대사, 증권·금융 플랫폼은 상태 전이·정확한 조회·지연시간·감사 가능성을 앞에 둔다. 업권별로 프로젝트를 여러 개 만드는 대신 검증된 공통 기반의 설명 초점을 바꾼다.

### 산출물 제안

- 1쪽 이력서: 지원 직무 소개, 대표 프로젝트, 직접 기여·검증 결과, 기술 글 링크.
- GitHub README: 목적, 업무 규칙, 구조 그림, 실행법, 테스트 명령, 현재 범위와 한계.
- 기술 설명 문서 3~4개: 도메인/데이터 모델, transaction·rollback, 동시성·멱등성, SQL·성능 실험.
- 짧은 시연: 정상 이체와 강제 실패·동시 요청 테스트를 보여주는 영상이나 GIF.

CUEE·연구실·리더십은 보조 증거로 쓸 수 있지만 금융 백엔드 구현처럼 표현하지 않는다. 대표 Java 프로젝트가 검증될수록 앞에 배치한다. 상세 기여 경계는 [[MOC-Portfolio]]를 따른다.

## 현재 이력서 V0과 미래 문장 틀

### 현재 코드에서 확인한 V0 문장

2026-09-28 저장소를 읽기 전용으로 확인했다. 현재 main의 HEAD는 8d7234c이고 작업 트리는 깨끗했다. 이번 확인에서는 테스트를 실행하지 않았다.

> Java/Spring Boot로 계좌 생성·조회·입금·출금·이체 API의 메모리 기반 수직 절편을 구현했습니다. Account 도메인에서 BigDecimal 잔액과 양수 금액·잔액 부족 규칙을 다루고, AccountTest에 계좌 규칙 및 정상 이체 테스트를 작성했습니다.

이 문장은 DB transaction·원장·동시성·멱등성·성능을 입증하지 않는다. 현재 AccountService는 ConcurrentHashMap에 변경 가능한 Account 객체를 저장하고, 이체는 출금 후 입금한다. map이 동시성 컬렉션이라는 사실만으로 잔액 변경이나 전체 이체가 원자적·스레드 안전하다고 주장할 수 없다. Gradle에 JPA/H2/MySQL 의존성이 있어도 현재 소스에는 Entity·Repository·Migration이 없으므로 DB 영속화를 했다고 쓰지 않는다.

9월 26일 Wiki에는 수취 계좌 없음·동일 계좌 실패 테스트와 HTTP API 확인이 기록되어 있으나, 9월 28일 checkout의 테스트 파일에는 AccountService의 정상 이체 외 그 실패 테스트가 보이지 않았다. 과거 사용자 보고는 보존하되, 코드에서 복원하거나 재확인하기 전까지 최신 이력서에는 넣지 않는다.

### 증거가 생긴 뒤 채울 문장 틀

아래는 구현·측정 후에만 실제 값으로 채운다.

- Spring Boot와 MySQL 이체에서 잔액·거래·원장 기록의 transaction 범위를 설계하고, 출금 뒤 예외 주입 테스트에서 전체 rollback을 확인했다.
- 동시 출금 [요청 수/시작 잔액]을 재현하고 [DB 제어 방식]으로 초과 출금을 막았으며, 최종 잔액과 성공 건수가 기대값과 일치함을 검증했다.
- idempotency key를 적용해 같은 key 재시도 [N]회에서 상태 변경이 한 번만 일어남을 확인했다.
- [데이터 규모] 조회에서 EXPLAIN 결과를 확인하고 인덱스/쿼리 변경 후 p95가 [측정값]으로 변했다. 환경은 [CPU·RAM·DB 버전·부하 도구]였다.
