# 거래 원장 실험과 대표 기술 글 계획

목표·포맷은 [[금융 백엔드 포트폴리오 5장 원고]], 계약·상태·복구 규칙은 [[거래 원장 아키텍처와 장애 복구 설계]]를 따른다. 이 파일은 재현·측정만 정의한다. 에이전트는 실제 코드를 먼저 읽어 미완료한 작은 작업을 추천한다. 구현 순서 권장: DB/원장·원자성→동시성→내부 멱등성→모의 기관→대사/복구→측정/글. 포트폴리오 장 순서와 개발 순서는 다를 수 있다.

## 실험 실행 계약

- 초기 데이터·코드 커밋·실패 위치·기대 규칙을 고정하고 정상→실패→복구→독립 DB 재조회로 확인한다.
- 단위 테스트는 금액/예외, DB 통합은 원자성/제약/경합, API는 입력/응답 계약, 별도 기관은 분산 실패를 확인한다.
- 비교용 부분 커밋/단순 재시도 구현은 실험용이라고 표시한다. 정상 구현이 이미 정확하면 가짜 개선 전 오류를 만들지 않는다.
- 전후 기관의 키/조회 보장·데이터·부하·환경·실패 지점을 동일하게 둔다. 다른 계약 실험은 별도 결과다.
- 실패는 커밋 직후 응답 차단·특정 저장 단계 예외·프로세스 종료처럼 위치를 제어한다. 시간 지연만으로 커밋 위치를 추정하지 않는다.
- SQL은 실제 스키마에 맞춰 작성한다. 명령·결과 없는 계획을 통과로 표시하지 않는다.

## 필수 실험 행렬

| 사례 | 입력·실패 조건 | 독립 확인·증거 |
|---|---|---|
| 1 동시성 | 동일 계좌 집중·양방향 이체·잔액 부족·충돌/교착 | 초기/최종 잔액·성공/거절 건수·원장 합계·락 대기/재시도. 잠금 대안 비교 |
| 2 원자성 | 출금 후·입금 후·원장 저장 중·커밋 전 예외 | 호출 TX 종료 뒤 별도 연결에서 잔액·거래·원장 전체 반영/취소 |
| 2 예외 처리 | 예외 유형·전파·catch/정상 반환·rollback 설정 | 실패 위치×예외×처리 경로×DB 결과 표. 테스트 자동 rollback/캐시와 구분 |
| 3 내부 키 | 순차/동시 동일 키·다른 금액 재사용·커밋 후 응답 유실·앱 재시작 | 같은 거래 ID·효과/원장 반영 건수·충돌 응답·저장 결과 조회 |
| 3 외부 유실 | 기관 커밋 직후 응답 차단·조회 지연/부재 | 기관 확정/우리 미확정→조회 후 확정. 예약과 원장 변화 확인 |
| 3 외부 재시작 | 접수 커밋 후 Worker 전 종료·기관 응답 후 로컬 확정 전 종료·중복 Worker/임대 만료 | 영속 작업 재발견·같은 기관 키·조건부 확정·중복 효과 없음 |
| 3 최종 판단 | 최종 거절·장기 미확정·충돌 결과 | 거절 보장에 따른 한 번 해제·미확정 유지/검토·감사 기록 |
| 4 오류 탐지 | 누락·중복·금액/상태 차이·지연 명세 | 기관 독립 기록+정답 오류 목록 대비 탐지·오탐·미탐 |
| 4 재개 | 청크 중간 종료·동일 명세 재수신·수정 버전·업무일/휴일 경계 | 체크포인트·최종 처리 집합·누락/중복·버전 이력 |
| 4 복구/SQL | 유형별 조회/조정·재대사·쿼리/인덱스/처리 단위 비교 | 조정 근거·잔여 차이·EXPLAIN·실행시간·정확성 유지 |

기관이 중복을 막으면 재전송의 관측 결과는 호출 증가/미확정 잔류일 수 있다. 중복 지급이 발생했다고 쓰지 않는다. 외부 거래는 내부 계좌 합계만으로 검증하지 않고 기관 효과·예약·출금/원장 관계도 검사한다.

## 측정·결과 기록

### 공개 금융 이용량과 프로젝트 가정 — 2026-10-14 조사

| 공개 근거 | 확인한 규모 | 해석 범위 |
|---|---|---|
| 한국은행, 2025년 국내 지급결제동향, 참고 2 | 인터넷뱅킹 계좌이체 일평균 2,826만 건. 등록고객 2억 4,464만 명 | 전국 은행 합계, 자행/타행 이체 포함. 고객은 은행 간 중복 합산이며 DAU가 아님 |
| 한국은행, 2025년 전자지급서비스 이용현황 | 간편송금 일평균 742만 건 | 여러 제공자의 합계. 단일 개인 간 송금 서비스의 수요나 피크가 아님 |
| 한국은행, 2026년 상반기 전자지급서비스 이용현황 | 간편송금 일평균 금액 1조 1,728억 원 | 더 최근 자료의 본문은 금액을 제시. 금액을 요청 수/초로 환산하지 않음 |

출처: [한국은행 작성 2025년 국내 지급결제동향 PDF — KDI 보관본, 참고 2](https://eiec.kdi.re.kr/policy/callDownload.do?num=278605&filenum=1&dtime=20260330165037), [2025년 전자지급서비스 이용현황](https://www.bok.or.kr/portal/bbs/B0000502/view.do?nttId=10097038&menuNo=201265), [2026년 상반기 전자지급서비스 이용현황](https://www.bok.or.kr/portal/bbs/B0000502/view.do?menuNo=201265&nttId=11064870).

전국 일평균을 86,400초로 나누면 계좌이체 약 327.1건/초, 간편송금 약 85.9건/초다. 이것은 전국 거래의 시간 평균이고 개별 API 요청 수·피크·한 은행 처리량은 아니다. 서로 다른 통계이므로 합산하지 않는다. 위 자료에서 개별 은행의 DAU당 이체 횟수·조회 API 비율·피크 RPS·서버 수는 확인하지 못했다.

따라서 기존 10만 DAU·일 3회·피크 15배를 금융권 실측에서 가져온 값이라고 말할 수 없다. 개인 간 송금 서비스의 회원 확보 예측 대신, 다음 부하 시나리오를 **검토안**으로 사용한다.

| 단계 | DAU·일 이체 빈도 | 일 이체 | 조회:이체·피크 배수 | 피크 API / 이체 요청 |
|---|---|---|---|---|
| 작은 규모 | 1만 명·1회 | 1만 건 | 5:1·15배 | 약 10.4 RPS / 1.74건/초 |
| 확장 검증 | 10만 명·1회 | 10만 건 | 5:1·15배 | 약 104.2 RPS / 17.36건/초 |
| 스트레스 | 10만 명·3회 | 30만 건 | 5:1·15배 | 312.5 RPS / 52.08건/초 |

일 이체 = DAU × 일 이체 빈도. 피크 API RPS = 일 이체 × (1+조회 비율) / 86,400 × 피크 배수. 이체 도착률과 유효 완료 TPS를 구분한다. 조회·이체 각각 한 HTTP 요청이라는 산식이며 로그인/폴링/재시도는 별도 부하로 추가한다.

10만 DAU·일 1회는 설명 가능한 확장 시나리오의 제안값이고, 5:1·15배는 조회 혼합과 집중도를 바꿔 병목을 비교할 시험값이다. 실제 서비스 이용 빈도라는 주장은 하지 않는다. 회원 M과 활성 비율 a는 DAU=M×a로 연결하지만 둘 다 사용자 결정 전에는 미정이다. 피크 지속 시간·API별 p99/오류율 기준·키 재사용률·집중 계좌 분포도 시험 전에 정한다. 기본 개발 완료 뒤 **10→50→100 API RPS**를 순차 검증하고, 300 RPS 부근은 기준 단계 완료 후 자원 범위에서 도전한다. 요청 비율은 고정하여 전후 비교한다. 수치 달성 자체보다 정확성·병목·선택 이유의 설명을 완료 기준으로 둔다.

### 피크 산정과 통과 조건 점검 — 논의 중인 검토안

현재 초안의 약점은 15배의 관측 근거·집중 시간·초 단위 급증 조건이 없고, 100 RPS 시험이 기존 104.2 RPS 목표보다 낮다는 점이다. 단계 시험 10→50→100 RPS와 별도로, 기존 목표를 사용하면 105 RPS 이상의 지속 시험을 통과해야 해당 목표를 검증했다고 쓸 수 있다.

**실제 금융 서비스의 산정 방법 참고:** [카카오페이 온라인 결제 성능 개선 사례](https://tech.kakaopay.com/post/improve-service-performance/)는 평소 40~50 결제 TPS, 이벤트 시 3~5배 증가, 신규 가맹점의 추가 예상량을 근거로 300 결제 TPS 목표를 정했다. 결제 TPS와 API 요청 TPS를 구분한다. 개인 간 송금의 피크 배수를 제시한 사례가 아니므로 3~5배나 300을 본 프로젝트에 그대로 적용하지 않는다. [카카오페이 성능 테스트 환경 사례](https://tech.kakaopay.com/post/perftest_zone/)는 이벤트·아키텍처 변경 전에 서비스 성능을 별도 환경에서 검증하는 방식을 설명한다.

프로젝트의 근거는 세 층으로 기록한다: 공개 통계/사례는 외부 규모와 산정 방법, 대상 사용자·행동·집중 비율/시간은 설계 가정, 처리 가능량·지연·정합성은 직접 실측이다. 송금 집중을 일으키는 구체 상황은 아직 미정이며, 평일 저녁·월말을 관측된 피크라고 단정하지 않는다.

피크 창의 평균 API RPS = 일 이체량 × 집중 비율 / 집중 시간(초) × (1+조회 비율). 일 10만 이체·조회:이체 5:1에서 다음 두 조건을 **대체 피크 모델**로 논의한다.

| 집중 가정 | 거래 수·계산 | 창 안의 평균 부하 |
|---|---|---|
| 하루 이체의 15%가 15분에 집중 | 15,000 / 900 × 6 | 100 API RPS, 이체 약 16.7건/초 |
| 하루 이체의 10%가 5분에 집중 | 10,000 / 300 × 6 | 200 API RPS, 이체 약 33.3건/초 |

비율·지속 시간은 외부 자료에서 관측한 수치가 아닌 설계 검토안이며, 위 값은 창 안의 평균이지 초 단위 최대값이 아니다. 실제 도착 시계열이 없으므로 ‘가장 큰 피크를 예측했다’는 표현 대신 ‘명시한 집중·급증 조건을 검증했다’고 쓴다. 두 모델은 별도 시나리오로 시험하고 기존 15배 모델을 확정적으로 대체하지 않는다. 조회의 동시 유입·재시도/폴링이 늘면 혼합 비율도 별도 시험한다.

**자원 검토안:** 로컬은 기능·시나리오·관측 도구 확인에 사용하고, 앱·DB·부하 생성기를 분리한 소액 클라우드 실험을 제안한다. 같은 호스트에 모두 배치했다면 결과에 자원 경합을 명시한다. 자원 사양·상품·리전·예산은 사용자 결정 전에는 미정이다. 기존 API 3대 배치 가정과 실제 시험 환경을 구분한다.

**정상 피크 SLO 검토안:** 조회 p99 ≤300ms, 내부 이체 p99 ≤500ms, 예상 밖 실패율 <0.1%, 잔액/원장 불일치·중복 효과 관측 0건. 금융권 표준이 아니라 사용자의 응답 경험과 정확성 검증을 위한 초기 목표 제안이다. API별 지연은 성공 요청의 분포와 전체 응답 분포를 함께 보고, 예측 가능한 잔액 부족/입력 거절·같은 키 재사용과 시스템 오류/타임아웃을 별도 집계한다. p99·오류율은 시험 전체뿐 아니라 피크 단계별/시간 창별로 계산한다. 표본 수와 원본 로그를 남기며 0건 관측을 일반적 무오류 보장으로 쓰지 않는다.

외부 기관 송금은 접수 응답과 최종 완료를 구분한다. 기관 지연을 고정/변경한 조건에서 최종 확정 지연·미확정 체류·복구 조회를 별도로 측정하고, 내부 이체의 500ms 목표를 외부 완료 시간에 그대로 적용하지 않는다. 정확한 접수·완료 목표는 기관 모의 계약과 함께 다음 논의에서 정한다.

**지속·급증·회복 검토안:** 워밍업 5분 → 단계별 부하 5분 → 목표 피크 15분 → 2배 부하 5분 → 평시 부하 10분으로 복귀하여 오류율·p99·backlog·DB 연결·메모리 회복을 본다. 추가로 목표 부하 30분 지속 시험, 목표의 4배 도착 부하 30초 시험을 각각 별도 ID로 수행한다. 이는 15분 창의 평균만으로 초 단위 급증을 설명할 수 없다는 약점을 보완하는 스트레스 조건이다. 단계/반복마다 데이터 조건을 맞추고, 생성기 부족으로 도착 부하를 만들지 못하면 목표 통과로 처리하지 않는다.

정상 목표 피크에서는 SLO와 정합성을 모두 만족해야 통과한다. 초과 부하에서는 정상 처리량 달성을 자동 요구하지 않고 제한/거절·타임아웃·재시도·데이터 보존을 관측한다. 회복 시험에서는 backlog가 무한히 증가하지 않고 줄어드는지, 정상 지연·연결·메모리 수준으로 돌아오는지와 실제 회복 시간을 기록한다. 동시 실패 주입의 중복 효과/부분 반영 검증은 부하만 높이는 시험과 구분한다.

**피크를 견뎠다는 제출 문장 — 실험 후에만 사용:** “일 이체 N건 중 P%가 T분에 몰리는 조건에서 목표 L RPS를 산정하고, 환경 E·데이터 D에서 목표 피크/지속/급증·회복을 검증했다. 조회·이체 p99와 예상 밖 실패율은 각각 실측 X·Y·Z였으며 불일치/중복 효과는 표본 K건에서 0건 관측했다. 초과 부하에서의 처리 제한·회복 시간과 자원 비용은 별도로 기록했다.” 현재는 계획이며 통과값은 없다.

### 단일/2개 인스턴스·공유 DB·비용 실험

실행 전제는 영속 DB·원장·트랜잭션·멱등성 기본 검증이다. 2026-10-14 읽기 전용 점검의 financial-lab은 커밋 8d7234c이며 AccountService의 메모리 저장·이체와 기본 도메인/정상 이체 테스트 단계다. JPA/MySQL 의존성 선언은 있지만 소스에 Repository·DB Entity·원장·멱등성 구현은 확인되지 않았다. 이번에 테스트는 실행하지 않았다. 지금 메모리 처리량을 DB 금융거래 용량으로 사용하지 않는다.

| 실험 ID | 구성·입력 | 기록·판단 |
|---|---|---|
| CAP-1 | 단일 앱·실제 영속 DB, 조회:이체 5:1, 10→50→100 RPS | 고정 CPU/메모리·데이터·워밍업/기간에서 p99·오류율·유효 완료 TPS·잔액/원장·CPU/GC·DB IO/연결/락. 정한 품질 기준을 만족하는 최대 지속 API RPS를 C1로 측정 |
| CAP-2 | 앱 2개·로드밸런서·CAP-1과 같은 공유 DB/데이터/요청 비율 | 양쪽 앱 자원과 노드 배치·총 커넥션 풀을 기록. 같은 품질 기준의 C2를 측정하고 e2=C2/(2×C1) 계산. 같은 키를 다른 앱으로 보내 중복 효과 검사 |
| CAP-DB | 균등 계좌/집중 계좌, 조회/이체 비율 변화, 앱 1/2개 | DB CPU·IO·풀 대기·락 대기·교착/재시도로 공유 병목 구분. 앱·DB 사양·SQL 중 무엇을 바꾸면 좋은지 비교. 전후에는 한 요인씩 변경 |
| COST-1 | 목표 104.2 RPS, 기존 API 3대 배치 후보 | 실측 C1/C2로 후보 대수 검토. 미검증 N은 효율·여유율별 추정으로 표시. DB 병목과 한 앱 장애 시 남는 용량은 별도 확인 |

CAP-1/2는 자원 조건을 같게 두되, 같은 노드의 여러 컨테이너와 독립 노드의 인스턴스를 구분한다. 파드 수와 서버/노드 수는 같지 않다. 실제 배포를 쓰지 않으면 프로세스/컨테이너/VM이라는 실제 실행 단위를 쓴다. Kubernetes 도입은 필수 전제가 아니다.

목표 도착률 시험은 arrival-rate 방식으로 설계하고 iteration당 HTTP 요청 수를 명시한다. 목표/실제 RPS·dropped iterations·부하 생성기 CPU를 함께 기록한다. 1회 실행이나 오류 응답만 빠른 결과로 C1/C2를 정하지 않는다. 반복·분포·재현 명령을 보존한다.

미검증 대수 N의 용량 후보는 C1×N×e(N)×u로 계산한다. e(N)은 확장 효율, u는 계획 여유를 반영하는 계수이며 선택 근거와 민감도를 적는다. e2를 모든 N에 그대로 보장하지 않는다. 단순 C1×N은 선형 확장을 가정한 값으로만 표시한다.

비용표는 `상품/리전 | 사양 | 수량 | 운영 시간 | 단가·확인일·공식 출처 | 월 추정 | 추정 근거/한계`로 작성한다. 앱 노드·DB/Standby·디스크/IO·로드밸런서·전송·로그/모니터링·백업·사용한 관리 비용을 포함한다. 노드 수는 인스턴스/컨테이너 자원·노드당 배치·시스템 예약으로 정하며 파드 개수에 VM 단가를 바로 곱하지 않는다. 기본 운영안과 한 인스턴스 장애 시 목표 유지안을 따로 비교한다. 상품·리전·예산이 미정이므로 금액은 미확인으로 둔다.

이력서에는 가장 강한 동일 실험의 정합성·p99·완료 TPS를 요약하고, 포트폴리오 결과에는 CPU/메모리·DB 대기·복구 비용과 검증한 확장 효율을 연결한다. 확장 용량·월 비용 추정은 실측과 구분한다.

정상 부하와 결정적 장애 실험을 분리한다. 기록: 커밋·Java/DB 버전·서버/API 수·CPU/메모리/스토리지·부하 생성기·계좌/거래 건수·집중도·키 재사용률·기관 지연/계약·실패 위치/비율·워밍업/기간·반복 횟수. 반복 3회 이상을 시작 계획으로 두고 실제 횟수·변동을 보고한다.

결과: 오류/부분 반영·중복 효과·잔액/예약/원장 차이, 접수와 최종 완료 TPS/지연, p95/p99·오류율, 미확정 체류·복구시간·backlog, 대사 탐지/오탐/미탐·처리시간·재개 후 누락/중복. k6 dropped iterations와 생성기 병목도 기록한다. 104 API RPS는 확장 검증 검토안, 기존 313 API RPS/52 이체 요청/초는 스트레스 가정이며 모두 실측이 아니다.

각 실행은 `실험 ID | 커밋·조건 | 명령 | 기대값 | 관측값 | 통과/실패·차이 | 원본 파일 | 다음 작업`으로 남긴다. ‘N건/R회에서 관측 오류 0’으로 표현하고 일반적 보장으로 확대하지 않는다. 정확성 비용·속도 저하도 보고한다.
