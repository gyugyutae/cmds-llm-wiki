# 아키텍처·대표 기술 글·협업·지원 준비 목표

> [!note] Bias Check
> 공개 합격 회고는 자기 보고이며 공개한 사람만 보이는 표본이다. 은행 IT·인턴 합격을 여의도 증권사 백엔드 정규직 합격과 동일시하지 않는다. 아래 수치는 합격선이나 평균이 아니다. 이상형 설계와 준비 목표는 완료한 경력이 아니다.

## 아키텍처를 보여주는 방법

기존 세 상자는 문제 해결의 순서를 요약했지만 서비스 경계·저장소·통신·실패 이후 데이터 경로를 보여주지 못했다. 전체 구조는 사용자→API→거래 DB, 영속 발송→모의 기관의 독립 DB, 명세→대사→검토·복구를 한 장에 표시한다. 상세 장애 시퀀스와 대사 흐름은 별도 문서로 연결한다.

- [상세 아키텍처](../70.%20Outputs/2026-10-06-Financial-Portfolio/거래%20원장%20아키텍처와%20장애%20복구%20설계.md)
- [2쪽 편집 원고](../70.%20Outputs/2026-10-06-Financial-Portfolio/금융%20백엔드%20포트폴리오%202쪽%20원고.md)

모듈 수를 늘리는 대신 DB 커밋과 외부 호출의 경계, 미확정 상태, 재시도·기관 조회·재대사 경로를 설명한다. 내부 이체는 같은 DB 트랜잭션으로, 외부 거래는 자금 예약·발송 의도·기관 확인으로 구분한다. 정산 집계와 기관 간 실제 결제 완료도 구분한다.

## 대표 기술 글: 한 문제를 끝까지 추적

2026-10-07 집필 기준은 [[2026-10-07-Q-representative-article-detailed-plan]]이다. 주제 후보 비교·일곱 절의 구체 질문·재현 순서·기관 계약을 고정한 전후 비교·자격 표기 기준을 반영했다. 아래는 개요이며 실제 결과는 측정 후 채운다.

**제목 후보:** 「이체는 끝났는데 응답은 오지 않았다 — 멱등 재시도와 거래 대사로 결과를 복구한 과정」

중심 질문은 ‘기관에서는 처리했지만 우리 서비스는 결과를 모를 때 돈과 거래 상태를 어떻게 안전하게 확정하는가’다. 동시성·원자성은 이 문제를 설명하는 기반, 대사는 확인과 복구 경로로 연결한다. 네 주제를 독립된 장문의 튜토리얼로 모두 넣기보다 하나의 실패가 발견·재현·해결·검증되는 과정을 깊게 쓴다.

| 순서 | 글에 들어갈 내용 | 첨부 증거 |
|---|---|---|
| 1 | 서비스 배경, 정확성 요구, 왜 응답 유실을 골랐는가 | 업무 규칙·금액 보존·중복 방지 조건 |
| 2 | 최초 방식과 실패 위치: 커밋 완료와 응답 전달은 다르다 | 최소 재현 명령·타임라인·양쪽 DB 기록 |
| 3 | 요청 키·거래 상태·예약 잔액·트랜잭션 경계 | API 계약·스키마·상태 전이·핵심 코드 |
| 4 | 검토한 대안과 선택 이유 | 동기 호출만 유지 / 영속 발송, 재전송 / 결과 조회의 실패 조건·비용 |
| 5 | 구현하면서 발견한 반례 | 같은 키 다른 금액, Worker 중단, 중복 실행, 늦은 결과·명세 |
| 6 | 전후 측정과 정확성 검증 | 고정 조건의 k6·검증 SQL·원본 지표·반복 실험 |
| 7 | 거래 대사·재개·복구와 정산 집계 연결 | 정답 오류 목록·명세 버전·체크포인트·조정 이력 |
| 8 | 비용·한계·남은 위험 | 외부 키 보장 의존, 보관 기간, 미확정 장기 체류, 모의 기관·장애 전환 범위 |

**전후 비교의 우선순위:** 중복 반영·잔액/원장 불일치·미결 거래 잔류를 먼저 보고, 유효 완료 TPS·p99·복구시간·DB 경합을 함께 본다. 정확성이 개선되며 처리 속도가 줄었다면 그 비용을 숨기지 않는다. 유한한 실험에서 오류 0건은 모든 조건에서 정확하다는 증명이 아니다.

기관 응답 유실과 내부 DB 커밋 후 클라이언트 응답 유실을 구분한다. 네트워크 전달이 한 번만 이뤄진다고 쓰지 않고, 어떤 요청 키·DB 제약·확정 조건에서 거래 효과 중복을 막았는지 설명한다. 결과의 정답은 k6의 HTTP 성공 수만으로 판단하지 않고 독립 기관 기록·검증 SQL과 비교한다.

**기술 글 레퍼런스의 좋은 점과 적용:**

- [토스 정산 개편 글](https://toss.tech/article/42671): 정산 문제를 운영과 연결하고, 거래 추적·재처리·비교 검증·대규모 처리의 선택을 설명한다. 우리 글도 업무 영향→대안→검증→운영 한계를 이어 쓴다. 실제 대규모 운영 경험이 없는 부분은 합성 실험으로 표시한다.
- [카카오뱅크 펀드 배치 글](https://tech.kakaobank.com/posts/2412-financial-batch-system-with-airflow/): 요구사항과 대안의 비용, 업무 로직과 스케줄러의 경계, 재실행 시 업무 날짜를 설명한다. 우리 글에도 실행 날짜와 거래 업무일의 차이, 재실행 계약을 포함한다. Airflow·Kubernetes를 그대로 도입할 필요는 없다.

기업 글과 같은 깊이를 목표로 삼되 기업 운영 규모를 흉내 낸 수치로 전문성을 표현하지 않는다. 독자가 같은 실패를 재현하고 선택의 이유와 제한을 검토할 수 있는 것이 이 글의 품질 기준이다.

## 3~4주 제작 계획

최소 거래 흐름·DB·모의 기관이 실행 가능한 시점부터의 실험·집필 계획이다. 프로젝트 전체를 처음부터 완성하는 기간을 뜻하지 않는다.

| 주차 | 수행 | 주말에 남길 결과 |
|---|---|---|
| 1주 | 요구·정확성 조건 고정, 기존 방식 실패 재현, 핵심 질문 확정 | 재현 스크립트·타임라인·초기 목차 |
| 2주 | 대안 비교·구현, 응답 유실/중복/중단 반례 확인 | 의사결정 기록·핵심 diff·실패 행렬 |
| 3주 | 같은 환경에서 전후 반복 측정, SQL 검증·대사·복구, 초고 | 원본 결과·그래프·재현 README·초고 |
| 4주 | 독립 독자의 재현·질문 반영, 한계·인과관계·문장 검토 | 글 공개본·고정 커밋·실험 패키지 |

3주로 줄이면 마지막 두 주를 합치고 실험 종류를 줄인다. 결과 없는 표를 채우거나 재현 불가능한 성능 주장으로 시간을 맞추지 않는다. 대표 글 링크는 블로그 홈 대신 이 글로 직접 연결한다.

## 협업 프로젝트는 금융일 필요가 있는가

필수로 두지 않는다. 개인 프로젝트가 금융 정확성·SQL·장애 복구를 보여주므로 협업에서는 실사용 요구 변경, API 계약, 코드 리뷰, 데이터 처리, 공동 배포와 본인 구현을 보여주는 것이 좋다. 실제 프로젝트 선택은 아직 미정이며 업무 데이터 검증·리포트는 후보일 뿐이다.

팀장으로 일정 조율만 맡지 않는다. API·데이터 모델·작업 상태·실패 재실행 중 연결된 핵심 모듈을 직접 책임지고, 팀원의 PR을 검토하며 통합·릴리스를 이끈다. 본인 코드·리뷰·회의 결정·사용자 피드백·배포 변경을 연결해 기여를 증명한다. 금융 주제가 반복되어도 팀원의 코드와 시스템을 통합한 증거가 없다면 협업의 장점을 전달하기 어렵다.

우리은행 회고의 장소 데이터 처리, KIDB 회고의 비금융 프로젝트는 비금융 주제도 지원 설명에 사용된 사례다. 다만 KIDB 회고 작성자는 입사 후 개발 업무가 없었다고 밝혀 목표 백엔드 직무의 성공 사례로 세지 않는다. 주제가 금융이어야 한다는 요구를 이 자료에서 도출할 수는 없다.

과거 Speaking Lv6를 현재 IH로 환산하지 않는다. 인턴 최종 합격을 신입 정규직 전환으로 쓰지 않는다. GPA가 높은 공개 사례만 보고 4점대가 합격 기준이라고 결론 내리지 않는다.

추가 [하나은행 2025 합격 회고](https://wk99.tistory.com/15)는 프로젝트·면접·코딩/SQL 경험을 보여주지만 동일한 스펙 항목이 모두 공개되지 않아 위 비교에 넣지 않았다. [한국투자증권 합격 후기 모음](https://jasoseol.com/blog/post/한국투자증권-합격-후기-자소서-팁-인적성-면접-질문/)은 직무가 혼합되어 전체의 스펙을 IT 합격자의 공통점으로 세지 않았다.

**자료에서 말할 수 있는 것:** 프로젝트를 자기 역할과 기술 질문으로 설명하는 준비가 중요하게 등장한다. 자격증·어학·인턴의 조합은 서로 다르다. 이 세 명의 평균이나 공통 필수 자격은 계산하지 않는다. 경험이 합격을 일으켰다고 인과관계를 단정할 수도 없다.

[2026 신한투자증권 공식 공고](https://recruit.shinhansec.com/recruit/view.do?annoId=4059453)는 ICT에 백엔드 등을 포함하고 ICT 관련 자격을 우대한다. 금융 관련 자격도 우대 예시지만 모두 취득해야 한다는 조건은 아니다. 이 공고의 학위·졸업 시기는 해당 모집 기준이며 2027 지원 자격은 새 공고에서 확인한다.

## 우리의 이상형 준비 목표와 제출 표기

| 항목 | 준비 목표 | 제출 시 원칙 |
|---|---|---|
| 학력 | 현재 학교·SW 전공·실제 졸업 예정일을 정확히 표기 | 실제 학점은 확인 후 필요하면 기입; 타인의 4점대를 목표 스펙처럼 덧붙이지 않음 |
| 경험 | 백엔드 개발 인턴/현장실습 1회가 이상적. 3~6개월은 계획 예시이며 필수 합격 조건 아님 | 실제 기간·직접 구현·리뷰·배포 결과를 기입. 없으면 꾸며 넣지 않음 |
| 협업 | 실사용 서비스 1개에서 팀장 + 핵심 백엔드 구현 | 본인 PR·합의·통합·사용자 피드백으로 기여 표시 |
| 자격 | 정보처리기사·SQLD를 우선 후보로 준비 | 실제 취득한 것만 표기. 응시 자격·채용공고에 맞춰 일정 결정 |
| 어학 | 기존 결정인 TOEIC Speaking IH를 유지 | 유효한 실제 성적·취득일 확인. AL·TOEIC 900은 공통 필수로 요구하지 않음 |
| 수상·추가 활동 | 관련 수상이 있으면 결과와 본인 기여 활용 | 없어도 별도 항목을 만들지 않음. 금융 자격·클라우드 자격은 공고 요구와 비용에 따라 선택 |

개인 금융 프로젝트·협업 출시·코테/SQL을 준비의 중심으로 유지한다. 관련 인턴은 좋은 추가 증거지만 자격·어학을 끝없이 늘리는 목표로 바꾸지 않는다. 계획 원고에는 목표로 표기하고 실제 제출본에는 달성한 항목만 남긴다. 마지막 페이지 영상의 원문 확인은 사용자 요청대로 보류한다.

## 레퍼런스 기준에 대한 점검

- 코딩웨일 관점: 현재 능력에 맞춰 축소하기 전에 목표 직무의 이상형 증거를 설계했다. 금융 정확성과 협업 기여의 서로 다른 증거를 연결했다.
- 생각등대 관점: 프로젝트 기본 정보·한 줄 운영 가정·그림·문제·해결/선택 이유·결과/한계 형식을 유지하고 그림을 시스템 경계·데이터 흐름으로 보완했다.
- 남은 격차: 설계가 좋아도 직접 작성한 코드·재현·측정·사용자 결과가 채워지기 전에는 우수 합격자의 실제 경험과 동등하다고 평가할 수 없다. 제출 2쪽은 편집 목표이며 PDF 렌더링으로 페이지 수를 확인한 상태는 아니다.
