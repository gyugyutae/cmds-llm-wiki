# 금융 포트폴리오의 연동·대사·팀장 역할·검증 설계

2026-10-06 사용자는 실제 기관 협력 대신 합성 트래픽 검증을 검토하고 거래 대사와 복구를 중심으로 선택했다. 최신 제출 분량·k6·공식 금융 업무 근거는 [[2026-10-06-Q-two-page-financial-portfolio-k6-and-domain-rules]]에 정리했다. 아래 01:00/01:10 명세·대사 예시는 공식 마감 시각이 아니며 초기 설계 예시로 남긴다.

## 추천 범위 — 사용자 선택 전 제안

이상형은 **내부 이체·원장 + 별도 서버/DB를 가진 모의 기관과의 연동·대사**로 제안한다. 실제 기관 테스트 환경은 접근이 허용되면 어댑터 계약 확인에 추가한다. 실제 기관 협약은 현재 확보되지 않았고 상대 기관의 협력을 예측할 수 없다.

내부 이체의 DB 원자성과, 별도 기관에 이미 반영된 거래의 불확실성은 다른 문제다. 외부 HTTP 호출을 로컬 DB 트랜잭션에 넣었다는 사실만으로 두 기관에 원자성이 생기지 않는다. 외부 이체는 별도 업무 흐름으로 두고 요청 ID·기관 거래 ID·결과 미확정 상태·조회·대사를 정의한다. 구체적인 자금 예약/확정/해제 규칙은 구현 전에 결정한다.

금융결제원 개발자 안내는 가입·서비스 신청·키 등록·응답 테스트 데이터 등록·API 테스트 절차를 설명한다. 통합포털은 실제 API 이용의 신청·계약 절차와 일부 서비스의 테스트 자격 제한을 설명한다. 개인에게 특정 이체 API가 허용된다는 확약은 이 자료만으로 하지 않는다. [개발자 안내](https://developers.kftc.or.kr/dev/starter/starter), [이용 절차](https://openapi.kftc.or.kr/intro/useProcedure)

| 방식 | 얻을 수 있는 경험 | 판단 |
|---|---|---|
| 내부 DB 처리 | 원자성·동시성·원장 모델·SQL 검증 | 대표 프로젝트의 기반 |
| 별도 모의 기관 | 네트워크 실패·결과 미확정·독립 기록 대사·복구 | 이상형에 포함할 추천 확장 |
| 공식 테스트 환경 | 실제 API 계약·인증·오류 처리 | 접근 허용 시 보강. 실계좌 운영 증거와 구분 |
| 실제 기관 운영 연동 | 계약·기관 협업·실제 운영 제약 | 기회가 생기면 강한 추가 경험. 현재 확보된 범위는 아님 |

모의 기관은 별도 실행 프로세스와 저장소를 가진다. 고정 성공 JSON만 반환하지 않고 요청 ID별 중복 방지·처리 결과 조회·기관 거래 기록을 구현한다. 성공 뒤 응답 유실, 지연, 장애, 중복 전달, 명세 지연·누락을 제어해 재현한다. 운영 청산망이나 공식 표준을 구현했다고 표현하지 않는다.

## 대사와 정산의 업무 의미

대사는 두 기록이 일치하는지 확인하는 과정이다. 정산은 계약·금액·수수료·지급일 등을 바탕으로 지급할 금액을 계산하고 확정하는 업무다. 현재 이체 프로젝트에서 직접 증명할 중심은 **거래 대사와 예외 복구**다. 정산 계산까지 붙이려면 누가 누구에게 어떤 금액을 왜 지급하는지 추가 정의가 필요하다.

### 제안하는 명세 계약

모의 기관이 자기 DB의 처리 기록으로 하루 명세를 생성한다. 내부 원장을 그대로 복사해 정답으로 사용하지 않는다. 독립성은 별도 구현만으로 완전해지지 않으므로 입력 시나리오의 예상 결과를 별도로 작성해 두 기록이 함께 틀린 경우도 확인한다.

| 필드 | 의미 |
|---|---|
| statement_id / revision | 명세 식별자·수정 버전 |
| business_date / timezone | 대상 업무일·Asia/Seoul |
| request_id / external_transaction_id | 양쪽 기록을 연결할 요청 ID·기관 거래 ID |
| accepted_at / completed_at | 접수·최종 처리 시점 |
| amount / currency / status | 금액·KRW·성공/거절 등 계약 상태 |
| cutoff / generated_at | 거래 범위 종료·명세 생성 시점 |
| record_count / total_amount / checksum | 파일 건수·명시된 상태의 금액 합·파일 무결성 확인 |

합계나 체크섬만으로 거래 정확성이 증명되지는 않는다. 거래별 ID·금액·상태 비교와 입력 시나리오 검증을 함께 수행한다.

### 마감 규칙 예시 — 업계 공통 규칙이 아닌 프로젝트 가정

- D일은 KST D 00:00 이상, D+1 00:00 미만에 **기관이 접수한 거래**로 정한다. `[시작, 종료)` 경계를 사용한다.
- 모의 기관은 D+1 01:00에 명세 revision 1을 생성한다. 대사는 01:10 실행한다. 시각은 설명용 제안이다.
- 명세 생성 시까지 최종 상태가 확인되지 않은 거래는 미결로 분류한다. 내부 결과 미확정 거래를 즉시 실패로 확정하거나 자동 환급하지 않는다.
- D일 접수 거래가 나중에 완료되면 D 명세 revision을 올려 보완한다. 이전 파일과 대사 결과를 보존한다. 기관이 뒤늦게 접수한 거래는 기관 접수일에 포함하고 내부 기록과의 날짜 차이를 추적한다.
- 명세 미도착·파싱 오류·합계 불일치 때는 비교 완료로 표시하지 않는다. 도착/형식/건수 검증과 거래 비교 상태를 구분한다.
- 재실행은 statement_id·revision·작업 ID로 식별한다. 동일 입력의 반복 처리와 중단 뒤 재개를 검증한다.

### 작은 정답 표본 예시

| 요청 ID | 내부 기록 | 기관 기록 | 대사 판단 |
|---|---|---|---|
| R1 | 완료 10,000원 | 완료 10,000원 | 일치 |
| R2 | 결과 미확정 20,000원 | 완료 20,000원 | 기관 결과 조회·내부 상태 확정 후보 |
| R3 | 완료 30,000원 | 완료 3,000원 | 금액 불일치·검토 |
| R4 | 완료 40,000원 | 기록 없음 | 누락 의심·지연/명세 완전성 확인 |
| R5 | 기록 없음 | 완료 50,000원 | 내부 누락 의심·조회·검토 |

금액 불일치에 자동으로 돈을 추가 이동시키지 않는다. 유형별 상태 조회·검토·확정·예약 해제 규칙을 정하고 모든 조치와 다시 대사한 결과를 남긴다. 같은 키의 전달이 여러 번 있었다는 통신 기록과 실제 중복 자금 반영을 구분한다.

## 협업에서 추천하는 역할

사용자는 팀장을 맡고 싶어 한다. 추천은 **팀장 + 핵심 백엔드 모듈 책임자**다. 팀장 희망은 확정됐지만 주제·팀·사용자는 아직 미정이다.

- 팀장: 사용자 문제·완료 기준 정리, 역할 경계 합의, API/파일 계약 조율, 리뷰·통합·릴리스 관리, 위험과 일정의 판단 기록.
- 본인 구현: 데이터 모델, 작업 상태 API, 검증/처리 배치, 중단 뒤 재개 중 하나의 연결된 모듈을 직접 책임진다.
- 공동 책임: 설계를 제안하고 팀원 의견으로 바뀐 결정·리뷰를 기록한다. 모든 코드를 혼자 작성한 결과를 협업 역량으로 환산하지 않는다.

업무 데이터 검증·리포트 서비스라면 '업로드 뒤 작업 상태와 결과를 정확히 관리하는 백엔드'를 본인 영역으로 추천한다. 화면·리포트/분석·다른 모듈은 팀원의 실질적인 책임으로 둔다. 금융 개인 프로젝트와 별도로 요구 변경·사용자 피드백·통합 과정에서 생긴 실제 사례를 제시한다.

최종 문장 목표: '팀장으로 파일 계약과 완료 기준을 합의하고, 작업 상태·검증 배치를 직접 구현했다. 통합 과정의 [실제 문제]를 [선택한 방법]으로 해결해 [측정 결과]를 확인했다.' 빈칸을 채우기 전에는 완료 경험으로 제출하지 않는다.

## 실측·기여·증빙을 만드는 방법

실측은 실제 실행에서 기록한 값이다. 기여는 본인이 판단·작성·검증한 범위다. 증빙은 다른 사람이 그 주장과 실행을 확인할 수 있는 자료다.

| 주장 | 실측 | 기여 근거 | 검토 가능한 증빙 |
|---|---|---|---|
| 동시 요청의 정확성 | 잔액·원장 불일치, 성공/거절/충돌 수 | 경합 재현·락 비교·수정 | 테스트·SQL·전후 commit·로그 |
| 재시도의 정확성 | 요청 수 대비 실제 반영 수 | 요청 키 정책·실패 재현·수정 | 응답 유실 스크립트·기관/내부 DB 확인 |
| 대사와 복구 | 탐지·오탐·미탐·처리시간·재개 후 누락/중복 | 규칙·SQL·재개 구현 | 정답 CSV·작업 로그·EXPLAIN·보고서 |
| 팀장·백엔드 책임 | 업무시간·재작업·통합 오류의 변화 | 담당 코드·결정·리뷰 반영 | PR·의사결정 문서·릴리스·사용자 피드백 |

실험은 초기 구현 고정 → 발생 조건 재현 → 데이터/부하/환경 고정 → 수정 → 같은 조건에서 반복 → 원본 보존 순서다. 개선 전 실패가 재현되지 않았다면 '오류 제거'라는 전후 주장을 쓰지 않는다. 방지 설계의 검증으로 표현한다.

측정 조건: 코드 commit, Java/DB 버전, API/DB/부하 생성기 사양과 위치, 데이터 seed·규모, 요청 분포, 집중 계좌 비율, 실행 시간, 워밍업, 반복 횟수, 오류 분류. 반복 결과의 변동도 제시한다. 실험 목적으로 단순화한 환경은 규모 가정의 운영 환경과 구분한다.

금융 프로젝트는 돈의 정확성을 먼저 확인하고 요청/거래 처리량·p95/p99·DB 비용을 함께 기록한다. API RPS와 유효 이체 TPS를 구분하고 빠른 거절이 많아져 수치가 좋아 보이는 경우를 확인한다. 서버를 키우거나 정확성 규칙을 약하게 만든 효과를 코드 개선으로 표현하지 않는다.

PR·commit 수 자체는 기여도를 증명하지 않는다. 문제를 발견한 기록, 본인이 비교한 대안, 담당 diff, 테스트와 결과, 리뷰로 바뀐 판단을 연결한다. AI 도움은 실제 맡긴 작업과 본인 확인 범위를 짧게 적는다.

## 권장 다음 결정

1. 모의 기관 연동을 이상형에 포함할지 사용자 선택.
2. 한 페이지의 거래 상태·잔액 예약 규칙과 명세 계약 검토.
3. 작은 정답 표본으로 동작을 설명한 뒤 구현.
4. 실제 사용자 접근성이 있는 협업 주제를 정하고 팀장 + 담당 모듈을 합의.

> 연동의 가치는 테스트 조건·업무 설명·실제 증거에 따라 달라진다. 모의 기관의 상태·명세·마감 시간은 학습 프로젝트 제안이며 금융 업계 공통 규칙이 아니다. 기관 협력과 테스트 API 권한은 확보되지 않았다.
