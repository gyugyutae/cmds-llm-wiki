# 코딩테스트에서 실제 개발로 넘어가는 법

## 상태 진단

김규태는 문법으로 로직을 작성하는 능력이 없는 것이 아니다. 코딩테스트는 문제, 입력, 출력, 제약, 정답이 주어지지만 실제 개발에서는 개발자가 다음을 직접 결정해야 한다.

| 코딩테스트 | 실제 개발 |
|---|---|
| 문제와 정답이 주어진다 | 무엇을 만들지부터 모호하다 |
| 한 함수·파일 중심이다 | 여러 계층과 외부 의존성이 연결된다 |
| 실행 후 종료된다 | 데이터와 상태가 계속 남는다 |
| 정답·시간복잡도로 판정한다 | 요구사항, 테스트, 운영 결과로 판정한다 |
| 혼자 완성하면 끝난다 | 다른 사람이 읽고 수정할 수 있어야 한다 |

따라서 현재 부족한 것은 코딩 능력 전체가 아니라 `요구사항 정의 → 구조 선택 → 상태·데이터 처리 → 디버깅 → 테스트 → 변경`의 전체 주기를 반복한 경험이다.

## 개발 공부의 최소 반복 단위

기능 하나마다 다음 순서를 반복한다.

1. 사용자 행동 한 문장을 쓴다: `사용자는 주문을 생성할 수 있다.`
2. 입력·출력·제약을 쓴다.
3. 완료 조건을 2~4개 쓴다.
4. 필요한 데이터와 책임을 나눈다.
5. 가장 단순한 정상 경로를 구현한다.
6. 정상·경계·실패 테스트를 작성하고 직접 실행한다.
7. 실패 원인을 추적해 수정한다.
8. 작은 단위로 commit하고 README에 판단과 한계를 남긴다.

이 한 바퀴를 돈 것이 개발 공부 1회다. 강의 한 장을 시청하거나 코드를 그대로 따라 친 것은 준비 단계일 뿐이다.

## 첫 프로젝트 — 작은 주문 시스템

새로운 아이디어를 고르는 대신 금융 백엔드 관심과 연결된 한 프로젝트를 계단식으로 확장한다.

### 1단계 — Java 콘솔 프로그램

Spring과 DB 없이 시작한다.

- `Order`: 주문 ID, 종목, 수량, 가격, 상태
- 주문 생성, 조회, 취소
- 잘못된 수량·가격 거부
- 이미 취소된 주문 재취소 거부
- JUnit으로 정상·실패 테스트

목표는 프레임워크 사용법이 아니라 클래스 책임, 상태 변화, 예외, 테스트를 직접 결정하는 것이다.

### 2단계 — Spring Boot API

콘솔 기능을 HTTP로 노출한다.

- `POST /orders`
- `GET /orders/{id}`
- `DELETE /orders/{id}` 또는 취소 endpoint
- 요청 DTO, 응답 DTO, controller, service, repository 분리
- 존재하지 않는 주문과 잘못된 입력에 일관된 오류 응답

각 계층을 나눈 이유를 설명하지 못한다면 구조를 더 복잡하게 만들지 않는다.

### 3단계 — DB 연결

메모리 저장소를 PostgreSQL 또는 MySQL로 교체한다.

- 주문 테이블과 제약조건 설계
- JPA 또는 SQL로 저장·조회
- transaction으로 상태 변경 보호
- unique constraint로 중복 요청 방지 실험
- 인덱스 추가 전후 실행 계획 비교

### 4단계 — 실무에 가까운 실패 처리

- 같은 요청이 두 번 들어오는 경우
- 없는 주문을 취소하는 경우
- 허용되지 않은 상태 전이
- DB 오류가 발생한 경우
- 동시에 같은 주문을 수정하는 경우
- 로그만 보고 실패 원인을 찾는 연습

성능 최적화나 복잡한 메시지 큐보다 정확성, 재현 가능한 실패, 테스트를 먼저 완성한다.

## 하루 2시간 루틴

| 시간 | 행동 |
|---:|---|
| 15분 | 오늘 만들 기능과 완료 조건 작성 |
| 60분 | 직접 구현 |
| 25분 | 테스트와 디버깅 |
| 10분 | 코드 정리와 commit |
| 10분 | 막힌 점, AI 도움, 내 판단, 다음 행동 기록 |

하루 목표는 `Spring 공부`처럼 넓게 잡지 않고 `잘못된 수량의 주문을 400으로 거부하고 테스트 통과`처럼 실행 가능한 기능으로 잡는다.

## 강의와 검색 사용법

- Java 전체 강의를 끝낸 뒤 시작하지 않는다.
- 기능을 구현하다 모르는 개념이 나타날 때 해당 부분만 공부한다.
- 튜토리얼을 본 뒤에는 화면을 닫고 같은 기능을 다시 구현한다.
- 예제와 변수명만 바꾼 코드는 결과물로 세지 않는다.
- 공식 문서나 강의에서 배운 내용을 현재 프로젝트에 적용하고 테스트해야 학습 완료로 본다.

## AI 사용 경계

- 기능의 문제, 입력, 출력, 완료 조건은 먼저 직접 쓴다.
- 처음부터 전체 프로젝트 생성을 요청하지 않는다.
- 막힌 오류의 원인 후보, 반례, 테스트 후보, 대안 비교에 AI를 쓴다.
- 생성된 코드는 한 번에 한 작은 조각만 받고 직접 실행한다.
- 설명하지 못하는 annotation, library, pattern은 제거하거나 따로 학습한다.
- `AI gave / I decided / I changed / I verified`를 commit 또는 개발 로그에 분리한다.

## 완료 기준

기능 하나는 다음 질문에 모두 답할 때 완료다.

- 왜 이 기능이 필요한가?
- 입력·출력·실패 조건은 무엇인가?
- 데이터는 어디에 저장되고 어떻게 변하는가?
- 왜 이 클래스와 계층으로 나눴는가?
- 정상·경계·실패 테스트가 있는가?
- 오류를 로그나 디버거로 다시 추적할 수 있는가?
- 다음 날 AI 없이 작은 변경을 할 수 있는가?
- 다른 사람이 README만 보고 실행할 수 있는가?

## 첫 7일 목표

1. 주문 생성 규칙과 완료 조건 작성
2. Java `Order`와 상태 enum 구현
3. 메모리 repository 구현
4. 주문 생성 service와 테스트 작성
5. 조회·취소와 실패 테스트 추가
6. 구조를 정리하고 기능 하나를 직접 변경
7. README와 2분 설명 녹음, 다음 주 API 전환 계획 작성

첫 주에는 Spring을 쓰지 않아도 된다. 일주일 뒤 남아야 하는 것은 강의 진도율이 아니라 직접 설계한 작은 프로그램, 테스트, commit, 실패 기록이다.
