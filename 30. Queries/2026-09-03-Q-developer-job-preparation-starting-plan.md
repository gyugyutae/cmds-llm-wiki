# 개발자 취업 준비 시작 계획

## 결론

김규태의 현재 병목은 스펙의 개수가 아니라 `Java 실전 구현`, `SQL·데이터베이스 실습`, `코딩테스트`, `직접 설명·수정·검증 가능한 프로젝트 증거`의 부족이다. 따라서 여러 분야를 동시에 탐색하기보다 첫 4주 동안 다음 세 축을 병렬로 시작한다.

1. Java로 코딩테스트와 작은 프로그램을 직접 구현한다.
2. SQL을 매일 직접 작성하고 트랜잭션·인덱스까지 연결한다.
3. 배운 내용을 작은 주문 API에 즉시 적용하고 판단·실패·검증 로그를 남긴다.

지원 범위는 넓게 유지하되, 첫 학습 서사는 `Java로 정확성과 장애 복구를 검증하는 금융 백엔드 개발자`로 좁힌다. 이는 영구적인 직무 확정이 아니라 4주 동안 적합성과 실행력을 시험하는 가설이다.

## 첫 4주 운영

주 20시간을 기준으로 한다.

| 축 | 주당 시간 | 4주 결과물 |
|---|---:|---|
| Java·코딩테스트 | 7시간 | Java 풀이 20문제와 오답 로그 |
| SQL·DB | 5시간 | SQL 30문제, 주문·계좌 스키마, 트랜잭션 실험 |
| 주문 API 프로젝트 | 6시간 | 주문 생성·조회·취소 MVP와 자동 테스트 |
| 채용·회고 | 2시간 | 관심 공고 10개 요구역량 표와 주간 회고 |

### 1주차 — 기준선 만들기

- Java 문법, 클래스, 컬렉션, 예외, 테스트 기초를 빠르게 복습한다.
- 배열·문자열·해시 문제 5개를 Java로 풀고 풀이 시간을 기록한다.
- SQL의 `SELECT`, `JOIN`, `GROUP BY`, subquery를 직접 작성한다.
- 관심 회사 공고 10개에서 언어, SQL, CS, 프로젝트, 졸업요건을 표로 추출한다.

### 2주차 — 데이터와 상태 모델링

- 스택·큐·정렬·이분탐색 문제 5개를 푼다.
- 주문, 계좌, 체결 테이블을 설계하고 PK·FK·인덱스 선택 이유를 적는다.
- Spring Boot로 주문 생성·단건 조회 API를 만든다.
- AI가 작성한 코드를 포함하더라도 각 줄을 설명하고 작은 변경을 직접 수행한다.

### 3주차 — 정확성 검증

- BFS·DFS·힙 문제 5개를 푼다.
- 트랜잭션, 격리 수준, unique constraint로 중복 주문과 정합성을 실험한다.
- 주문 취소와 상태 전이를 추가하고 정상·실패 테스트를 작성한다.
- 실패 사례 하나를 재현하고 원인, 수정, 재검증을 기록한다.

### 4주차 — 결과물로 닫기

- 혼합 문제 5개를 제한 시간 안에 풀어 1주차와 비교한다.
- 실행 방법, 설계 판단, 테스트 명령, 알려진 한계가 포함된 README를 작성한다.
- 프로젝트를 2분 안에 설명하고 녹음해 막히는 개념을 찾는다.
- 4주 지표를 보고 금융 백엔드를 계속할지, 일반 백엔드나 다른 도메인과 비교할지 결정한다.

## AI 사용 기준

- 처음 30분은 문제와 코드를 직접 다룬다.
- 막히면 정답 코드 대신 제약 재해석, 단계별 힌트, 실행 추적, 반례 생성을 요청한다.
- AI가 만든 코드는 설명, 수정, 자동 테스트, 실패 조건 확인을 통과해야 본인 증거로 인정한다.
- 로그에는 `내 판단`, `AI가 도운 것`, `내가 수정한 것`, `검증 결과`, `아직 모르는 것`을 분리한다.

## 당장 하지 않을 것

- 직무가 정해질 때까지 공부 시작을 미루지 않는다.
- 자격증 취득을 Java·SQL·코딩테스트·프로젝트보다 앞세우지 않는다.
- 운영체제, 네트워크, Spring, 금융, 반도체, 드론을 모두 강의 중심으로 동시에 시작하지 않는다.
- AI가 완성한 큰 프로젝트를 새 포트폴리오 한 줄로 추가하지 않는다.

## 오늘 할 일

1. Java 개발 환경과 빈 Spring Boot 저장소를 준비한다.
2. Java 코딩테스트 문제 1개를 30분 동안 직접 푼다.
3. 주문·계좌 테이블을 종이에 먼저 그리고 SQL로 생성한다.
4. `왜 이 구조를 선택했는가`를 다섯 문장으로 기록한다.

## 4주 후 판단 지표

- Java 문제 20개 중 힌트 없이 다시 풀 수 있는 비율
- SQL 30문제 정답률과 JOIN·집계·subquery 취약 유형
- 주문 API 자동 테스트 수와 재현 가능한 실패 사례 수
- README만 보고 다른 사람이 실행할 수 있는지
- 프로젝트 핵심 코드를 2분 설명 후 직접 수정할 수 있는지
- 공고 10개에서 반복된 요구역량과 현재 증거의 격차
