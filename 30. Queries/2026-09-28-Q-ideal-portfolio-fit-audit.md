# 이상형 금융 백엔드 포트폴리오: 생각등대·코딩웨일 기준 적합성 점검

## 판정

지금 설계는 두 영상의 조언을 **서로 다른 단계에서 결합**한다.

- **코딩웨일 영상**은 무엇을 만들지 프로젝트보다 먼저 설계하는 바깥 절차다: 목표 시장 → 합격 자료·조언 → 공통 기준 도출 → 이상형 → 현실 조정 → 현업 피드백 → 구현.
- **생각등대 영상**은 포트폴리오 안의 기술 경험을 읽히게 만드는 안쪽 구조다: 제목 → 그림 → 문제 → 해결 → 결과. 같은 구조의 문제 해결 블록 약 네 개를 제안한다.

따라서 이체·원장 중심 프로젝트 하나 안에 동시성, rollback, 멱등성, 정산 대사의 네 문제 해결 블록을 두는 현재 설계는 **방향과 형태 면에서 적합하다**. 다만 현재 결과물은 이상형을 적은 기획 문서다. 생각등대의 최종 문서가 요구하는 재현한 문제·직접 만든 그림·실제 해결 판단·측정 결과는 아직 만들어지지 않았다.

이상형은 “이만큼 하면 반드시 취업한다”는 보증이 아니다. 공개 합격 후기는 자기보고이고, 한 프로젝트만으로 서류·코딩테스트·면접 결과를 보장할 수 없다. 대신 각 주장을 실행·설명·수정·재검증할 수 있고 외부 피드백을 받은 상태를 포트폴리오 측면의 높은 준비 기준으로 둔다.

## 코딩웨일: 기획 순서 점검

| 단계 | 현재 상태 | 평가 |
|---|---|---|
| 목표 시장 범위 | 여의도 금융권 백엔드 전반. 은행·증권·카드·결제·보험·핀테크·금융 IT를 열어 둠 | 충족. 구현 업무는 이체·원장으로 좁혀 목표 직무의 넓이와 프로젝트 깊이를 같이 확보하려는 설계 |
| 합격 자료·조언 수집 | 32개 공개 자료를 합격 후기, 공개 포트폴리오, 채용공고, 회사 기술 글, 코드 자료로 분리 | 부분 충족. 원본 포트폴리오를 직접 읽을 수 있는 금융 신입 사례가 적고, 비공개/이미지/홍보 선택 편향이 있음 |
| 공통 기준 분석 | 거래 정합성, SQL·transaction·재시도 검증, 본인 기여와 측정 조건을 핵심으로 정리 | 이상형 초안을 설계하기에는 충분. 합격 원인의 통계나 업계 보편 법칙으로 취급하면 안 됨 |
| 이상형을 현실 제한 전에 설계 | 이체·원장 메인 흐름, 네 개의 실패/검증 장면, 정산 대사, 깊은 기술 글을 연결 | 현재 단계의 핵심 결과. 주당 시간이나 기존 코드로 이상을 축소하지 않음 |
| 개인 조건에 맞춘 타협 | 아직 시작하지 않음 | 의도한 다음 단계. 먼저 이상형을 확정하고 나서 어렵거나 과한 부분을 협상 |
| 외부 검토 | 아직 없음 | 신입/주니어 금융 백엔드 경험자와 기술 리뷰어에게 기획안을 보인 뒤 반영 |
| 실제 구현 | 아직 미완료 | 프로젝트·글·이력서 문장은 실제 구현과 실측 증거에 맞춰 작성 |

코딩웨일의 200~300개 자료는 영상 작성자의 조사량이다. 현재 조사에서 그 숫자를 목표나 필요조건으로 따라갈 근거는 없다. 더 많은 자료를 무작정 모으기보다 직접 볼 수 있는 제출물과 직무가 맞는 평가자의 피드백을 보강하는 편이 정보 가치가 높다.

### 네 블록의 경계

1. **동시성:** 동시에 들어온 서로 다른 유효 요청이 잔액 불변조건을 깨는가?
2. **원자성/rollback:** 한 요청의 처리 중 실패하면 잔액·상대 계정·원장 기록이 함께 되돌아가는가?
3. **멱등성:** 같은 요청을 재전달하면 자금 이동은 한 번만 발생하고 재시도 결과는 예측 가능한가?
4. **정산 대사:** 내부 거래와 외부 정산 자료가 다를 때 SQL로 누락·중복·금액 차이를 구분하고 안전하게 재처리할 수 있는가?

이 구분은 같은 테스트를 네 번 포장하지 않게 한다. 실제 실험에서 두 문제가 같은 원인이나 증거를 공유하면 블록을 합치거나 새 문제로 교체한다.

## 코딩웨일 기준의 이상형 포트폴리오

**핵심 메시지:** 돈의 이동을 원장에 정확히 남기고, 동시에 요청되거나 재시도되거나 중간에 실패해도 잔액과 기록을 보존하며, 정산 데이터의 차이는 SQL로 찾아 추적·복구하는 Java 백엔드 개발자.

**대표 프로젝트:** 계좌 간 이체와 거래 원장. 온라인 요청 처리의 동시성·원자성·멱등성을 깊게 검증하고, 같은 서비스의 별도 정산/대사 작업에서 SQL·배치·예외 복구를 증명한다. 정산 상대는 아직 정할 세부 범위다. 외부 청산/상대 은행 명세를 합성해 연결할지, 내부 원장과 계좌 잔액 대사로 제한할지에 따라 도메인 깊이와 난도가 달라진다.

**제출 구조:**

1. **짧은 이력서:** 이 프로젝트의 역할과 확인된 결과 한 줄, 가장 깊은 기술 글로 직접 연결.
2. **포트폴리오 본문:** 문제 해결 카드 네 개를 제목·그림·문제·해결·결과 순서로 일관되게 배치. 꾸미기보다 그림이 이해를 돕는지와 증거의 가독성을 우선.
3. **저장소:** README의 실행법, 도메인 규칙·상태도, ERD, ADR, API, 테스트/실험 명령과 원본 결과를 연결.
4. **기술 글:** 네 카드 중 가장 강한 한 문제를 실패 재현부터 대안 비교, SQL, 테스트 조건, 결과, 한계까지 깊게 전개.
5. **면접 자료:** 2분 설명으로 시작해 데이터 모델·실패 모드·대안·한계 질문을 직접 방어.

### 이력서 팁 영상: 트래픽과 인프라를 한 줄로

세 번째 클리핑의 조언에 따라 프로젝트의 금융 업무 규모, 예상 처리량, 서버 사양을 한 줄의 설계 가정으로 덧붙였다. 현재 한 줄은 10만 DAU·30만 이체/일·조회/이체 5:1·피크 15배라는 workload와 API/MySQL 구성을 밝히고, API 요청 RPS와 실제 이체 TPS를 구분한다. 한국은행 국내 지급결제 집계는 규모 비교에만 쓰고, 이 가정이 은행별 실트래픽이나 산업 표준이라는 뜻은 아니다. k6 실측을 마친 뒤에만 이력서에 결과를 쓴다.

아키텍처는 복잡한 구성요소 개수로 이상을 만들지 않는다. 하나의 Java/Spring 서비스와 관계형 DB에서 일관성을 증명하고, 정산 배치는 필요에 맞게 분리한다. 메시지 브로커·캐시·MSA는 요구와 장애 모델을 설명할 실제 이유가 생길 때만 추가한다.

## 포트폴리오 준비도를 자신감으로 바꾸는 완료 조건

- README대로 새 환경에서 핵심 흐름을 실행하고 네 블록의 테스트/데이터를 재현한다.
- 이력서의 모든 기술·수치·기여를 코드, 테스트, 로그, 측정 원본 중 하나로 따라갈 수 있다.
- 사용자가 그림과 구현을 자기 말로 설명하고, 일부러 실패를 만들고, 코드를 직접 바꿔 결과가 어떻게 달라지는지 설명한다.
- 성능 수치는 요청 수·데이터량·환경·측정 구간·오류율·p95/p99를 붙여 설계 가정과 실측을 구분한다.
- 정산 샘플은 합성 데이터라고 공개하고, 어느 외부 업무를 흉내 내는지와 지원/미지원 상태를 명시한다.
- 현업 백엔드 리뷰와 금융 도메인 리뷰를 거쳐 문제 정의·구현 범위·과장 여부를 수정한다.
- 포트폴리오 외의 SQL/알고리즘 테스트와 이력서·면접 준비도 별도로 확인한다.

이 조건은 포트폴리오와 기술 설명에 대한 높은 준비 기준이지 채용 성공의 보증 문구가 아니다. 사용자 의도는 이 수준을 먼저 그리고, 시간·기술·채용 피드백을 본 뒤 무엇을 줄일지 결정하는 것이다.

## 열린 질문

정산 대사가 맞춰볼 외부 기록의 출처를 구체화해야 한다. 사용자의 답변을 받아 대표 명세와 상태 전이를 정하고, 그 뒤에 문제 해결 블록 그림과 레퍼런스/현업 검토 질문을 확정한다.
