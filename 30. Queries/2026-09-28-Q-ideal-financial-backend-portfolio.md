# 금융권 백엔드 이상형 포트폴리오: 현재 역량을 빼고 먼저 그리는 기준안

## 먼저 합의할 설계 순서

사용자가 원하는 순서는 **이상적인 결과물 → 실현 가능성 조정**이다. 현재 코드, 학습 속도, 주당 시간을 이상형의 시작 조건에 넣지 않는다. 이번 안은 그 순서에 맞춘 North Star이며, 뒤의 현실 타협안을 대신하지 않는다.

사용자가 지정한 「개발자 취업, 100% 성공하는 포트폴리오 작성법」은 목표 시장 정의 → 합격 레퍼런스·조언 수집 → 공통점과 차이 분석 → 이상적인 포트폴리오 설계 → 본인 조건에 맞게 조정 → 현업 피드백 → 구현의 순서를 제시한다. 영상 작성자는 본인이 이력서·포트폴리오로 취업을 준비해 본 적은 없다고 뒤에서 밝힌다. 그러므로 이 방법은 유용한 **기획 절차 가설**로 쓰고, 제목의 성공률이나 200~300건 수집 숫자를 검증된 성과처럼 인용하지 않는다.

여기서 “가짜 이상형”은 기획 문서 속 목표 상태를 뜻한다. 이력서나 실제 제출 포트폴리오에 아직 구현·측정하지 않은 성과를 기입한다는 뜻은 아니다.

## 이상형 포트폴리오의 한 문장

> 금융 서비스의 거래 상태와 데이터가 재시도·동시 요청·장애 상황에서도 일관되도록 설계하고, SQL·테스트·측정 자료로 그 동작을 증명하는 백엔드 개발자.

이 정체성은 은행 계정계, 증권 주문, FEP/OMS 한 곳에만 묶이지 않는다. 은행·증권·카드·결제·보험·자산관리·금융 플랫폼·금융 IT 조직이 공통으로 다루는 상태 전이, 데이터 정합성, 실패 복구를 포트폴리오의 중심으로 둔다.

## 대표 프로젝트 구상

### 이름과 범위

**금융 거래 처리·정합성 플랫폼 (Financial Transaction & Reconciliation Platform)**

사용자가 채택한 중심 시나리오는 **계좌 간 이체와 거래 원장**이다. 이체의 원자성·동시성·재시도를 핵심 흐름으로 두고, 네 번째 문제 해결 사례에서 내부 원장과 정산 데이터를 SQL로 대사한다. 모든 업권을 한꺼번에 구현하지 않고, 정산 데이터의 상대는 외부 청산기관/상대 은행의 합성 명세인지 내부 잔액 집계인지 후속 결정으로 남긴다.

### 예상 트래픽 및 초기 인프라 설계 기준

- **예상 트래픽·초기 인프라(가정)**: 10만 DAU·30만 이체/일·조회:이체 5:1·피크 15배(313 API RPS/52 이체 TPS)를 기준으로 API 3대(각 2 vCPU/4 GiB)와 MySQL Primary/Standby(각 8 vCPU/32 GiB SSD)를 산정하고 k6로 검증한다.

이 한 줄은 포트폴리오에 넣을 **설계 가정**이지 운영 실적이 아니다. 숫자의 규모 감각을 위해 한국은행의 2024년 국내 지급결제동향 첨부표(한은금융망을 제외한 일평균 입금이체 2,911.9만 건)를 참고하면, 30만 건/일은 그 집계의 약 1.03%다. 이는 전국 합계에 대한 단순 비율이며 특정 은행의 사용자 수나 트래픽 점유율을 뜻하지 않는다. 10만 DAU, 인당 이체 수, 조회:이체 비율, 피크 계수, 노드 사양은 프로젝트가 명시적으로 둔 가정이다. 요청량은 30만 건/일 × (이체 1 + 조회 5) = 180만 API 요청/일, 일평균 약 20.8 RPS, 15배 피크 약 313 RPS로 계산한다. 이체 처리량은 30만 건/일 ÷ 86,400초 × 15 ≈ 52 TPS다. k6 결과를 얻으면 요청 프로필·실험 환경·오류율·p95/p99와 함께 가정치와 분리해 기록한다. 거래 원자성·잔액 불변조건·멱등성은 k6 처리량만으로 증명하지 않고 별도 DB 통합·동시성 테스트로 검증한다. [한국은행 2024년 국내 지급결제동향](https://www.bok.or.kr/portal/bbs/B0000502/view.do?menuNo=201265&nttId=10090521)

| 멱등성과 재시도 | 같은 요청 키를 반복 제출해 중복 요청이 한 번의 유효 결과를 만드는지 검증 |
| 대사·배치 | 내부 거래와 외부 정산 파일의 누락·중복·금액 불일치를 SQL/배치로 찾고 재처리할 수 있음을 보여줌 |
| 성능 판단 | 실제 실행계획·데이터 크기·부하 프로필·환경·오류율·p95/p99·처리량을 공개 |
| 운영·보안 | 배포 가능한 demo, CI, 구조화 로그·기본 지표, 접근 통제·감사 추적, 합성 데이터와 비밀 관리 |
| 아키텍처 | 하나의 경계가 왜 적절한지, 대안과 손익을 ADR에 기록하고 필요가 관측된 때에만 복잡도를 추가 |

### 생각등대 영상에 맞춘 네 문제 해결 블록

아래 네 블록은 프로젝트 기능 목록이 아니라 각기 다른 실패 원인과 검증 결과를 보여주는 설계다. 실제 포트폴리오에 넣을 때는 각 블록을 모두 같은 순서(제목 → 직접 그린 그림 → 문제 발견 → 해결 선택 → 측정 결과)로 쓴다.

| 제목 초안                            | 그림                                           | 문제에서 밝혀야 할 것                               | 해결에서 비교할 것                                           | 결과 증거                                |
| -------------------------------- | -------------------------------------------- | ------------------------------------------ | ---------------------------------------------------- | ------------------------------------ |
| 동시 이체 요청에서도 잔액 불변조건을 지켰다         | 같은 출금 계좌를 건드리는 두 DB transaction의 sequence    | 어떤 동시 요청에서 overdraft/lost update가 발생했는지 재현 | 조건부 UPDATE, optimistic/pessimistic lock 등 후보의 정확성·비용 | 초기 잔액, 요청 수, 성공/거절 수, 최종 잔액, 원장 합계   |

이 표는 이상형의 제목과 증거 조건이다. 문제 발견 문장, 선택한 해결, 그림, 수치는 구현과 실험 뒤에 본인 기록으로 채운다. 첫 세 블록은 동시성, 부분 실패 원자성, 요청 중복이라는 서로 다른 실패 모드로 구분한다.

기술 선택 목록을 늘리기보다 제약과 대안을 드러낸다. 메시지 브로커, 캐시, 마이크로서비스는 “금융 회사에 있어 보이기 때문”에 넣지 않는다. 재시도·분산 실패를 다루는 요구가 생기면 필요한 구조와 그 한계를 설명한다.

데이터는 합성하고 실계좌·개인정보는 사용하지 않는다. 부하 수치는 **설계 가정**과 **실측값**을 구별한다. 예를 들어 “이 시나리오를 초당 100건으로 가정했다”와 “이 환경에서 k6로 측정한 처리량이 100건이었다”는 서로 다른 주장이다.

## 포트폴리오 전체 구성

2026-09-30 사용자가 원하는 개인 프로젝트 하나 + 협업 프로젝트 하나의 구성을 기준으로, 개인 프로젝트에서는 거래 정확성·데이터 처리·복구를, 협업 프로젝트에서는 본인 백엔드 구현과 요구사항 조율·리뷰·통합·운영을 증명하는 이상형을 제안한다. 네 금융 사례는 한 개인 프로젝트의 해결 경험으로 묶고, 제출본의 블록 수는 가장 강한 개인·협업 증거를 선별해 정한다. 최종 산출물·대표 기술 글·레퍼런스 비교와 협업 이상형 예시는 [[2026-09-30-Q-financial-portfolio-deliverables-and-reference-review]]에 정리했다. 현재 financial-lab이나 기존 팀 프로젝트는 이상형을 실현할 후보이며, 현재 코드로 이상형의 요구를 제한하지 않는다.

포트폴리오는 많은 프로젝트를 나열하는 문서가 아니라 **검토자가 짧게 훑고, 궁금한 주장만 증거까지 따라갈 수 있는 구조**로 만든다.

1. **짧은 이력서** — 목표 직무, 대표 프로젝트 한 줄, 본인이 맡은 결정, 확인된 성과, 가장 강한 기술 글 하나를 바로 연결한다.
2. **요약 화면/PDF** — 서비스 문제, 사용자 흐름, 본인 기여, 시스템 구조, 대표 증거를 앞쪽에서 보여주고 세부 근거를 링크한다. 개인 정보나 지원처에 맞춰 PDF가 필요하면 외부 URL 없이도 핵심 설명이 남도록 한다.
3. **공개 저장소** — 실행 방법, ERD, API 명세, 아키텍처 그림, ADR, 테스트 시나리오, 측정 스크립트·원본 결과를 재현 가능한 순서로 제공한다.
4. **기술 블로그** — 대표 프로젝트에서 직접 재현한 문제를 깊게 쓴 앵커 글 한 편, 이후 관련 실험을 보강하는 짧은 후속 글을 연결한다.
5. **면접 설명 자료** — 2분 요약에서 출발해 모든 이력서 문장을 20~30분 기술 토론으로 확장할 수 있도록 문제·선택·대안·실패·한계를 복기한다.
6. **협업 증거** — 실제 팀 프로젝트나 오픈소스 기여가 있다면 본인/팀의 경계, PR·리뷰·의사결정 기록을 붙인다. 혼자 만든 일은 팀 성과처럼 표현하지 않는다.

형식의 이상형은 본문을 무작정 길게 만드는 게 아니다. 짧은 요약, 세부 문서, 코드/실험 원본의 세 단계로 펼쳐지게 한다. 공개된 48쪽·53쪽 사례는 긴 문서도 실제로 제출된 사례라는 점만 알려 줄 뿐, 분량의 효과를 입증하지 않는다.

## 기술 블로그: 토스·카카오 수준을 목표로 하는 글 한 편

사용자가 지정한 이력서 영상은 일반 블로그 홈 대신 기술적으로 깊고 직무와 가까운 **글 하나**를 이력서에서 직접 열도록 제안한다. 주제는 읽을거리 요약이 아니라 본인이 실제로 실패를 만들고 해결을 검증한 금융 백엔드 문제로 잡는다.

첫 앵커 글의 예:

> “같은 금융 거래 요청이 동시에 들어오고 재시도될 때 원장 데이터는 어떻게 보존되는가?”

글의 전개:

1. 독자가 이해할 금융상 문제와 영향
2. 초기 구현과 반드시 지켜야 할 데이터 불변조건
3. rollback·동시 요청·재시도를 재현하는 테스트와 SQL
4. 실패가 왜 생겼는지, 적용한 DB/애플리케이션 제어와 선택하지 않은 대안
5. 실패 주입 뒤 조회한 상태와 전후 측정 결과
6. 데이터·실행 환경·부하 조건, p95/p99·오류율·정합성 결과
7. 실패한 접근, 남은 한계, 이 설계를 적용하지 않을 조건
8. 독자가 재현할 명령과 저장소 commit

[토스페이먼츠 정산 시스템 재구축 글](https://toss.tech/article/42671)은 거래 기록, 실패 재처리, 대량 조회 등 운영상의 선택을 설명하는 깊이를, [카카오페이 성능 개선 글](https://tech.kakaopay.com/post/improve-service-performance/)은 목표 workload와 실제 측정치를 구분해 설명하는 방식을 참고할 수 있다. 이 글들은 운영 중인 회사 시스템의 사례라 규모·인프라를 그대로 복사하지 않고, **문제 정의·증거·선택·한계의 서술 방식**만 기준으로 삼는다.

## 이력서 클리핑에 반영할 규칙

- 프로젝트 bullet은 “문제/제약 → 본인 결정·기여 → 검증된 결과” 순으로 쓴다.
- 서버 규모·요청량·TPS 가정은 도메인과 workload 가정으로 명시하고, 실제 부하 테스트 수치와 한 문장에 섞지 않는다.
- 이력서에서 블로그 홈이 아니라 이 프로젝트의 가장 깊은 글로 직접 연결한다.
- 공고의 직무에 맞춰 동일한 검증 기반을 앞세우되, 검증하지 않은 사용자 수·처리량·개인 기여를 쓰지 않는다.
- SQL/알고리즘 코딩테스트는 별도 평가이므로 프로젝트 포트폴리오만으로 대체하지 않는다.

## 후속 논의와 검증할 질문

사용자는 2026-09-30 기존 트래픽·초기 서버 사양 가정을 기준으로 수용했다. 이상형을 더 구체화할 금융 업무 규칙, 네 블록의 실패 상황·대안 비교, 성능·복구 증거와 제출 형태 초안의 완료 조건은 [[2026-09-30-Q-portfolio-progress-and-ideal-quality-upgrade]]에 보강했다. 현재 역량에 맞춘 타협안으로 확정한 내용은 아니다.

이상형의 초안은 **이체·원장 프로젝트 하나 + 정산/대사 문제 해결 블록 + 독립적 협업/기여 증거 + 대표 기술 글 한 편**이다. 이 방향은 현재 코드나 확보 시간에 맞춰 낮춘 안이 아니다. 코딩웨일 영상의 단계로 보면 시장 정의·레퍼런스 조사·이상형 기획을 진행했고, 다음에 현업 검토와 본인 조건에 따른 범위 조정을 한다.
