# 2026 넥토리얼 AI면접 답변 전략

## 판단

김규태의 차별점은 단순히 “AI를 많이 쓴 사람”이 아니다. 더 설득력 있는 포지셔닝은 다음과 같다.

> 게임 개발 기본기는 아직 부족하지만, 문제를 사용자 관점에서 정의하고 AI를 이용해 빠르게 시제품을 만든 뒤 결과·피드백·실패를 기록하며 방향을 수정해 온 성장형 지원자다. AI가 만든 코드를 모두 자기 실력이라고 주장하지 않고, 설명·검증 가능한 범위를 넓히려 한다.

게임 포트폴리오 부재와 C++·C# 부족은 명확한 약점이다. 이를 AI 활용 이야기만으로 상쇄하려 하면 영상이 경고한 “AI 결과를 자기 실력으로 착각한 지원자”로 보일 위험이 있다. 합격 가능성을 높이는 방법은 약점을 먼저 인정하고, 문제 정의·학습력·커뮤니케이션·피드백 루프라는 실제 강점을 구체적 사례로 증명하는 것이다.

## 답변 스크립트

지원동기, 넥슨 게임 경험, 게임 포트폴리오 부재, AI 기반 학습 사례의 통합 답변은 [[2026-09-11-Q-Nexon-Tutorial-Motivation-and-Game-Answers]]를 우선 참고한다.

### 1. 자기소개

> 안녕하세요. 저는 사용자 문제를 구조화하고 AI를 활용해 빠르게 시제품을 만든 뒤, 결과와 피드백을 기록하며 개선해 온 김규태입니다. Threads 자동화에서는 글의 양보다 전달 순서가 문제라고 가정하고 포맷을 바꾸어 이용자 반응 변화를 관찰했습니다. CUEE에서는 팀장으로서 기존 비즈니스 모델의 한계를 인정하고 팀원들과 방향을 전환했습니다. 아직 게임 프로젝트와 C++ 기본기는 부족하지만, AI가 만든 결과를 제 실력으로 과장하지 않고 제가 이해하고 검증할 수 있는 범위를 꾸준히 넓히는 게임 프로그래머가 되고 싶습니다.

### 2. 왜 넥슨인가

> 초등학생 때 메이플스토리에서 친구나 모르는 사용자와 아이템과 메소를 거래했던 경험이 오래 기억에 남아 있습니다. 지금도 배경음악, 캐릭터, 몬스터와 직업을 떠올릴 정도로 하나의 세계를 경험했습니다. 넥슨이 말한 ‘머물고 싶은 세계’와 ‘오래도록 기억될 게임’이 제 경험과 연결됐습니다. 저는 제가 받았던 기억을 막연히 돌려주겠다는 데서 멈추지 않고, 거래 중 연결이 끊기거나 요청이 중복돼도 재화와 아이템이 정확히 반영되는 시스템을 배우고 만들고 싶어 지원했습니다.

### 3. 게임 포트폴리오가 없는데 왜 뽑아야 하는가

> 게임 프로젝트가 없고 C++·C# 숙련도가 낮다는 점은 분명한 약점입니다. 이를 AI 활용 경험만으로 대신할 수 있다고 생각하지 않습니다. 다만 저는 사용자 반응을 관찰해 문제를 다시 정의하고, 빠르게 시제품을 만들고, 팀과 방향을 수정하는 경험을 반복했습니다. Threads에서는 포맷 가설을 바꾸고 반응을 확인했고, CUEE에서는 사업 모델의 한계를 팀에 솔직히 공유해 피벗을 이끌었습니다. 넥토리얼에서는 이 문제 정의와 학습 속도를 게임 개발 기본기와 결합하고 싶습니다. 현재는 제출한 프로젝트의 작은 코드 단위부터 AI 없이 다시 설명하고 작성하는 방식으로 부족한 기본기를 메우고 있습니다.

마지막 문장은 실제로 작은 코드 재작성 연습을 마친 뒤에만 사용한다.

### 4. AI로 만든 코드를 설명할 수 있는가

> 솔직히 말씀드리면 프로젝트 전체 코드를 줄 단위로 설명할 수 있는 수준은 아닙니다. AI가 작성한 비중이 크고, 제가 실행과 테스트 결과를 확인한 것을 구현 전체를 이해한 것처럼 생각했던 부분도 있습니다. 다만 제가 직접 정한 문제, 입력·출력, 포맷과 검증 기준, 실패 후 수정 방향은 설명할 수 있습니다. 현재 Threads 프로젝트에서는 JSON 응답을 파싱하는 함수와 사용 가능한 provider만 선택하는 fallback 함수를 작은 단위로 정해 입력, 분기, 예외, 테스트를 다시 공부하고 있습니다. 모르는 부분을 숨기기보다 설명 가능한 경계를 밝히고 그 경계를 코드 작성으로 넓히겠습니다.

### 5. AI를 잘 활용한다는 것은 무엇인가

> 저는 AI를 잘 활용한다는 것을 많은 코드를 빠르게 받는 능력이라고 생각하지 않습니다. 먼저 문제의 목표와 제약을 정의하고, AI가 이해한 내용이 제 의도와 같은지 확인하며, 결과를 테스트하고 실패를 기록하는 능력이라고 생각합니다. Threads 자동화에서는 AI에 자료 후보와 초안을 맡겼지만, 글의 순서와 게시 기준은 제가 정했습니다. 다만 코드 이해까지 충분히 인수하지 못한 한계가 있었고, 지금은 테스트 통과와 설명 가능성을 구분해서 보고 있습니다.

### 6. CUEE 피벗과 커뮤니케이션

> CUEE를 진행하며 심사위원에게 ‘사용자가 돈을 내면서까지 쓸 것인가’라는 질문을 받았습니다. 탈락 후 제가 사용자라면 건별 결제를 하지 않을 것 같다고 판단했습니다. 이미 만든 것이 있었지만 팀원들에게 제 초기 판단이 부족했다고 먼저 인정하고, 정말 사용자가 원하는 앱을 만들려면 지금 피벗하는 편이 낫다고 제안했습니다. 팀원들도 기존 작업의 매몰비용보다 개인 무료 제공으로 시장성을 확인한 뒤 기업 제휴를 검토하는 방향에 동의했습니다. 팀원들은 경쟁사와 CPS 모델을 구체화했고 저는 방향 결정과 발표를 맡았습니다. 이 경험으로 솔직한 피드백은 상대를 꺾는 말이 아니라 판단 근거와 역할을 함께 공유하는 일이라고 배웠습니다.

이 답변의 피벗 설득 과정은 2026-09-11 사용자 자기보고이며 팀원 관점은 독립 확인되지 않았다.

### 7. 게임 개발의 매력

> 게임 개발의 매력은 제가 만든 시스템과 패치에 대해 이용자가 빠르고 솔직하게 반응한다는 점입니다. 재미가 없거나 불편한 콘텐츠는 사용자가 바로 떠나거나 강하게 의견을 줍니다. 저는 그것을 두려운 평가보다 제품을 개선할 수 있는 빠른 피드백으로 보고 싶습니다. Threads에서 실제 반응을 보고 포맷 가설을 바꿨던 것처럼, 게임에서도 이용자 반응을 관찰하되 목소리가 큰 일부 의견과 전체 행동 데이터를 구분해 개선하고 싶습니다.

### 8. 모르는 기술 질문에 답하는 방법

> 이 개념을 완전히 이해했다고 말하기는 어렵습니다. 제가 아는 범위에서는 A가 B를 위해 사용되는 것으로 이해하고 있습니다. 다만 C 조건에서 어떻게 동작하는지는 확실하지 않습니다. 실제로 확인한다면 공식 문서와 작은 재현 코드로 정상 조건과 실패 조건을 나누어 검증하겠습니다.

정의조차 모를 때는 비슷한 용어로 추측하지 말고 모른다고 말한 뒤 확인 순서를 설명한다.

## 코드 약점의 현실적 해결

면접 전 전체 프로젝트를 이해하려고 하면 실패한다. Threads 저장소에서 아래 두 함수만 먼저 자기 것으로 만든다.

### extract_json

- 입력: LLM이 반환한 문자열.
- 처리: 앞뒤 공백 제거 → 코드펜스 제거 → 잘못 끊긴 개행 보정 → 전체 JSON 파싱.
- 실패 대응: 전체 파싱이 실패하면 첫 JSON 객체 형태를 찾아 다시 파싱하고, 객체도 없으면 예외를 유지.
- 확인할 한계: 정규식으로 중첩 JSON 경계를 정확히 판별하지 못할 수 있음.

### fallback_provider_chain

- 입력: 최초 provider와 model.
- 처리: 최초 provider를 먼저 넣고 환경변수에서 fallback 목록을 읽음.
- 제외 조건: 이미 사용한 provider 또는 API key가 없는 provider.
- 출력: 사용할 provider·model·key의 순서 목록.
- 테스트: OpenAI와 Groq 순서 유지, OpenAI key가 없으면 Groq만 남는지 확인.
- 설명할 한계: fallback은 가용성은 높이지만 provider별 결과 차이와 비용·품질 변동을 만든다.

현재 저장소에서 71개 단위 테스트가 통과했지만, 이는 코드 작성 주체나 김규태의 이해도를 증명하지 않는다. 위 두 함수를 빈 화면에서 의사코드로 쓰고, 원본을 보지 않고 다시 구현한 뒤 테스트 이유까지 말할 수 있어야 이해 증거가 된다.

## 2026-09-11 자가답변 진단

### 총평

현재 강점은 정직한 지식 경계와 실제 경험의 방향 전환을 말할 수 있다는 점이다. 반면 기술 질문에서는 모르는 개념을 비슷한 단어로 연결하면서 오개념을 만드는 위험이 크다. 특히 stack과 heap, TCP와 DB 동시성, TCP handshake와 중복 거래 처리가 섞였다. 면접에서는 틀린 내용을 길게 추측하기보다 아는 범위를 짧게 말하고 모르는 경계를 밝히는 편이 낫다.

### 기술 질문의 최소 면접 답변

#### 16. 해시 테이블

> 해시 테이블은 key를 hash function으로 bucket에 매핑해 평균 O(1)에 조회·삽입하는 자료구조입니다. 다만 서로 다른 key가 같은 위치로 매핑되는 충돌이 생길 수 있고, chaining이나 open addressing으로 처리합니다. 충돌이 심하거나 hash 분포가 나쁘면 최악의 경우 O(n)까지 느려질 수 있습니다.

#### 17. stack과 heap

> 여기서 stack과 heap은 메모리 영역으로 이해하겠습니다. stack에는 보통 함수 호출 frame과 지역 변수가 저장되고 함수 반환이나 scope 종료에 따라 수명이 관리됩니다. heap은 실행 중 동적으로 할당하는 메모리 영역으로, C/C++에서는 해제와 객체 수명을 주의해야 합니다. heap은 FIFO 구조가 아니며 FIFO는 queue입니다.

#### 18. pointer와 reference

> C++에서 pointer는 주소를 값으로 저장해 null이 될 수 있고 다른 객체를 가리키도록 바꿀 수 있으며 역참조가 필요합니다. reference는 기존 객체의 별칭으로 선언할 때 바인딩하고 일반적으로 다른 객체로 재바인딩하지 않습니다. C에는 pointer는 있지만 C++식 reference는 없습니다.

#### 19. process, thread, race condition

> process는 독립된 가상 주소 공간과 자원을 가진 실행 단위이고, thread는 process 안에서 실행되는 흐름입니다. 같은 process의 thread는 메모리를 공유하기 때문에 같은 값을 동시에 읽고 수정하면 실행 순서에 따라 결과가 달라지는 race condition이 생길 수 있습니다. mutex, atomic 연산, 공유 상태 최소화 등으로 제어합니다.

#### 20. TCP와 UDP

> 실시간 게임이라고 하나만 고르기보다 데이터 성격으로 나누겠습니다. 위치처럼 최신 값이 중요하고 일부 손실을 허용할 수 있는 데이터는 UDP가 적합할 수 있습니다. 반면 로그인, 채팅, 아이템 구매처럼 순서와 신뢰성이 중요한 데이터는 TCP 또는 별도의 신뢰성 보장이 필요합니다. UDP는 handshake와 기본 재전송이 없어 지연 overhead를 줄일 수 있지만 신뢰성이 자동 보장되지는 않습니다.

#### 21. 동일 아이템 동시 구매

> 이 문제는 TCP 연결이 아니라 서버와 DB의 동시성 문제입니다. 구매를 하나의 transaction으로 처리하고, `재고가 남아 있을 때만 감소` 같은 조건부 update나 row lock·optimistic lock을 사용해 한 요청만 성공시킵니다. unique constraint도 최종 안전장치로 둘 수 있습니다. 승자는 commit하고 다른 요청에는 품절 또는 충돌 응답을 반환합니다.

#### 22. 성공 직후 연결 단절과 재시도

> 서버에서는 거래가 commit됐지만 client가 응답을 못 받았을 수 있습니다. 그래서 요청마다 idempotency key를 보내고, 서버가 key와 처리 결과를 저장합니다. 같은 key의 재요청이 오면 거래를 다시 실행하지 않고 기존 성공 결과를 반환해 이중 차감과 이중 지급을 막습니다. 재화 차감과 아이템 지급도 하나의 transaction으로 묶어야 합니다.

### 가장 시급한 학습 순서

면접 직전 우선순위는 넓은 CS 완주가 아니라 제출한 주장에 연결된 치명적 오개념 제거다.

1. `race condition → DB transaction → lock/conditional update → idempotency`를 한 흐름으로 공부해 19·21·22번을 연결한다.
2. `stack memory / heap memory / pointer / reference / object lifetime`을 묶어 17·18번을 교정한다.
3. hash collision과 TCP/UDP를 정상·경계·실패 예시 하나씩 설명한다.
4. 자물쇠와 열쇠를 AI 없이 다시 풀고 회전식, 이동 범위, lock 영역 검사, 시간복잡도를 백지 설명한다.
5. Threads 원본에서 fallback 테스트 29개의 실제 범위를 확인하고, 함수 하나를 직접 재작성해 9·10·14번의 공백을 동시에 줄인다.
6. 23·24·26번은 `상황 → 내 판단 → 팀과 한 행동 → 결과 → 검증 한계`로 60초 답변을 녹화한다.
