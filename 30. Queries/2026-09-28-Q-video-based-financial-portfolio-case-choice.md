# 영상의 문제 해결 블록으로 금융권 포트폴리오 다시 설계하기

## 영상에서 가져온 작성 규칙

클리핑에 담긴 타임스탬프별 transcript 전체를 읽었다. YouTube 페이지는 조사 도구에서 불러오지 못했으므로 화면이나 음성 자체를 별도로 확인했다고 주장하지 않는다. 아래 해석은 제공된 transcript에 한정한다.

영상은 포트폴리오를 기능 목록이나 발표용 PPT가 아니라 **문제를 발견하고, 원인을 판단하고, 해결책을 골라 적용한 뒤 결과를 보여주는 문서**로 정의한다. 약 네 개의 문제 해결 블록을 같은 순서로 쌓는 구성을 제안한다.

| 순서 | 블록 내용 | 금융 백엔드 적용 |
|---|---|---|
| 제목 | 해결한 문제를 한 문장으로 말하기 | "동시 이체에서도 출금 가능 잔액과 원장 합계를 보존했다" |
| 그림 | 상황을 한눈에 이해하는 직접 작성 도식 | 요청 순서도, DB 쓰기 순서, 트랜잭션 경계, 실행계획 전후 |
| 문제 | 어떻게 발견했고 어떤 현상이 있었는지 짧게 쓰기 | 재시도/동시 요청에서 관측한 중복·불일치·지연과 그 영향 |
| 해결 가설 | 방식, 비교한 대안, 선택 이유 요약 | 제약조건·잠금·원자적 갱신·멱등 키·배치 재실행 중 선택 |
| 결과 | 실제 변화와 조건 | 테스트 데이터, 동시 요청 수, 실패 주입, DB/부하 환경, 지표와 불변조건 |

블록은 기능 네 개가 아니라 **서로 다른 문제 해결 경험 네 개**다. 네 블록 모두 제목-그림-문제-해결-결과 순서를 유지한다. 그림은 AI가 만든 아키텍처 장식보다 본인이 이해한 데이터 흐름·시퀀스·전후 그래프를 직접 그린다. TPS·응답시간에는 수치뿐 아니라 부하 조건과 실행 환경도 붙인다.

이것은 작성 프레임이지, 네 개가 모든 채용에서 검증된 최적 개수라는 뜻은 아니다. 아직 발생하지 않은 문제와 결과를 완료 사실처럼 쓰지 않는다.

## 세 후보를 같은 프레임으로 비교

아래는 완료된 경험이 아니라 선택을 돕는 **설계 후보**다. 현상을 재현하고 결과를 측정하기 전에는 모두 문제 가설로 남긴다.

| 대표 흐름 | 강한 문제 장면 | 직접 그릴 그림 | 증명할 결과 | 잘 드러나는 역량 | 경계 |
|---|---|---|---|---|---|
| 이체/원장 | 계좌의 동시 이체·출금으로 잔액이나 원장 정합성이 흔들림 | 동시 요청부터 잔액/원장 DB 쓰기까지의 sequence diagram | 허용된 거래 수, 최종 잔액, 원장 합계, rollback 결과가 불변조건과 맞는 테스트 | SQL 트랜잭션, 원자성, 동시성, 제약조건, 자금 이동 정확성 | 흔한 주제일 수 있으므로 "계좌 API를 만들었다"가 아니라 재현 가능한 실패와 근거를 보여야 함 |
| 결제/환불 | 외부 승인 응답이 끊긴 뒤 재시도하면 승인·환불 결과가 불명확해짐 | 앱-결제사-콜백-내부 원장 상태 전이도 | 반복/역순 콜백, 중복·부분 환불, 미확정 상태 재조회가 올바른 상태를 만드는 검증 | 상태 전이, 멱등성, 외부 연동 경계, 실패 복구 | PG/card 도메인에 더 특화됨. 실연동을 하지 않으면 가상 어댑터와 테스트 경계를 밝혀야 함 |
| 정산/대사 | 내부 원장과 외부 정산 자료의 누락·중복·금액 불일치를 놓침 | 수집 → 정규화 → 매칭 SQL → 예외 목록 → 재처리 흐름 | 합성 표본의 오류 탐지, 실행계획, 데이터량·측정시간, 중단 후 재실행 결과 | SQL·집계·조인·배치 재실행·감사 추적 | SQL은 선명하지만 단독으로 온라인 요청 처리와 트랜잭션 경계를 충분히 보여주기 어려움 |

환불은 독립적인 대표 흐름보다 결제에서 발생하는 **역거래/취소**로 다루는 편이 자연스럽다. 정산은 어느 주 흐름에나 대조 문제 해결 블록으로 연결할 수 있다.

## 채택한 방향: 이체/원장을 중심축으로 두고 정산 대사를 연결

사용자는 2026-09-28에 **계좌 간 이체·거래 원장**을 중심 업무로 두고, **정산·대사**를 별도의 문제 해결 블록으로 연결하기로 했다. 이유는 현재 프로젝트와의 편의가 아니라 금융권 전반의 거래 정확성과 SQL 기반 데이터 검증을 함께 보여주려는 목표다.

영상 프레임으로 그릴 네 블록의 초안:

1. **동시 이체 요청에서도 잔액 불변조건을 유지** — 동시 요청과 DB 갱신 순서를 그리고, 별도 연결 동시 테스트의 최종 잔액·성공 수를 결과로 둔다.
2. **중간 실패에서 잔액과 원장을 함께 되돌림** — DB 변경 순서와 강제 실패 지점을 그리고, 예외 뒤 재조회 결과를 둔다.
3. **중복 재시도에도 거래를 한 번만 반영** — 같은 요청 키의 최초/반복 흐름을 그리고, 요청 횟수와 실제 원장 반영 수를 결과로 둔다.
4. **원장과 집계 잔액의 차이를 SQL로 찾아 복구** — 거래에서 대사 쿼리까지 그리고, 불일치 유형별 검출·재처리 및 실행계획을 둔다.

이 네 가지는 아직 구현 성과가 아니다. 실제 오류 재현·측정 결과가 없으면 문제와 수치, 그림을 고쳐야 한다. 첫 세 블록도 실패 원인과 검증 장면이 중복되지 않도록 나눠야 한다.

정산 대사의 상대 데이터가 외부 청산/상대 은행 명세인지, 내부 잔액 집계인지는 아직 구체화하지 않았다. 실데이터 연결을 주장하지 않고 합성 명세를 사용하더라도, 어떤 기관 사이의 어떤 의무를 대사하는지 업무 규칙을 정해야 한다.

## 후속 설계 질문

세 흐름 중 주제를 고르는 단계는 완료됐다. 포트폴리오의 한 문장 초안은 다음과 같다.

> 한 금융 거래 요청이 동시에 들어오거나 재시도되어도 자금 이동은 한 번만 반영되고, 잔액과 원장 기록이 일치하는 시스템을 만들었다. 실패 주입·동시 테스트·SQL 대사로 이 불변조건을 확인했다.
