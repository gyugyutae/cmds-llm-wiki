## 재시험 진행 기록

### 1. 동일 아이템 동시 구매

#### 사용자 답변 요지

두 사용자가 동시에 구매하면 하나의 재고가 두 사람에게 돌아갈 수 있다. 구매를 transaction으로 보고 재고가 1 이상일 때만 조건부 update하며, row lock이나 optimistic lock으로 하나의 요청만 성공시킨다. 승자는 commit하고 패자는 품절·충돌 메시지를 받는다. race condition은 실행 순서에 따라 결과가 달라지는 문제라고 설명했다.

#### 평가

- 결과: 통과
- 점수: 약 85점
- 개선: TCP가 아니라 DB 동시성 문제로 교정됐고 transaction, 조건부 update, commit을 연결했다.
- 남은 주의점: 조건부 update, row lock, optimistic lock은 항상 전부 함께 쓰는 절차가 아니라 상황에 따라 선택하는 방법이다.
- 범위 구분: 한 process의 thread 문제는 mutex·atomic으로 다룰 수 있지만 여러 server/process가 공유하는 거래 상태는 DB의 원자적 연산이나 lock을 기준으로 제어해야 한다.

#### 정리된 답변

> 두 사용자가 재고 1개를 동시에 확인하고 동시에 구매하면 둘 다 성공했다고 판단하는 race condition이 발생해 중복 판매될 수 있습니다. 구매를 transaction으로 묶고, DB에서 재고가 1개 이상일 때만 차감하는 조건부 UPDATE를 원자적으로 실행하겠습니다. 변경된 행이 1개인 요청만 commit하고, 0개인 요청에는 품절 응답을 반환합니다. 상황에 따라 row lock이나 optimistic lock을 사용할 수 있으며, 여러 서버가 동작할 수 있으므로 한 process의 mutex만으로 해결하지 않겠습니다.

### 2. 거래 성공 후 응답 유실과 재요청

#### 첫 답변과 혼란

서버에서는 성공했지만 결과가 client에 전달되지 않을 수 있고, 같은 멱등성 키나 request ID로 재시도하면 저장된 처리 결과를 반환한다고 답했다. 다만 `저장된 처리 결과`가 구체적으로 무엇인지 이해하지 못했다고 밝혔다.

#### 교정 후 재답변

멱등성 키를 기준으로 success 결과를 기록하며, 응답이 유실돼 client가 같은 키로 재시도하면 아이템 지급을 다시 실행하지 않고 기존 거래 결과를 반환한다고 설명했다.

#### 평가

- 결과: 통과
- 점수: 약 85점
- 표현 교정: 결과는 key 자체에 저장되는 것이 아니라, server가 key를 기준으로 DB의 처리 기록을 조회할 수 있게 저장한다.
- 개념 교정: idempotency key는 같은 논리적 요청의 재시도를 식별한다. 일반적인 request ID는 시도별 추적 목적으로 새로 부여될 수도 있으므로 두 용어를 항상 같은 것으로 단정하지 않는다.

#### 정리된 답변

> 서버는 구매 요청의 멱등성 키를 기준으로 처리 여부와 거래 결과를 저장합니다. 첫 요청의 구매가 성공했지만 응답이 유실되더라도, client가 같은 멱등성 키로 재시도하면 이미 성공한 요청인지 확인할 수 있습니다. 결제와 아이템 지급을 다시 실행하지 않고 기존 거래 결과를 반환해 이중 결제와 중복 지급을 막습니다.

### 3. 아이템 지급과 멱등성 기록의 원자성

#### 사용자 답변 요지

두 작업을 하나의 transaction에서 처리하고 전부 성공하면 commit하며, 중간에 실패하면 rollback해 전체를 실패 상태로 만든다고 설명했다.

#### 평가

- 결과: 통과
- 점수: 약 90점
- 이해한 개념: transaction의 atomicity
- 범위 주의: 같은 DB 안의 재화 차감·아이템 지급·멱등성 기록은 한 transaction으로 묶을 수 있다. 외부 결제 시스템까지 포함하면 단일 DB transaction으로 끝나지 않아 상태 저장, 재시도, 보상 처리 같은 추가 설계가 필요할 수 있다.

### 4. stack과 heap

#### 사용자 답변 요지

stack에는 지역변수와 매개변수가 있고 함수가 끝나면 수명을 다하며, heap은 동적으로 할당하는 곳이라고 설명했다. 하지만 “heap이 메모리를 관리한다”고 말했고, heap 오관리 문제를 메모리 사용량 증가로만 설명했으며 queue와의 구분도 불완전했다.

#### 평가

- 결과: 부분 통과
- 점수: 약 60점
- 확인된 이해: stack의 대표 용도와 scope 종료에 따른 자동 수명, heap의 동적 할당
- 남은 공백: heap 메모리의 소유·해제 주체, memory leak, dangling pointer, use-after-free, double free
- 핵심 구분: queue는 FIFO 동작 규칙을 가진 자료구조이고 heap은 여기서 동적 메모리 영역이다. queue 구현이 내부적으로 heap 메모리를 사용할 수도 있다.

#### 정리된 답변

> stack에는 일반적으로 지역변수와 함수 호출 정보가 저장되며 변수의 scope가 끝나면 자동으로 소멸합니다. heap에는 실행 중 필요한 객체를 동적으로 할당하며 함수가 끝나도 자동으로 사라지지 않기 때문에 프로그래머나 스마트 포인터가 수명을 관리해야 합니다. 잘못 관리하면 memory leak, dangling pointer, use-after-free, double free가 발생할 수 있습니다. queue는 FIFO 규칙을 가진 자료구조이고 heap은 메모리 영역이므로 서로 다른 개념입니다.

## 12개 질문군 모의면접 재시작

## 질문 1 — 1분 자기소개와 지원동기

### 사용자 답변 요지

- 어린 시절부터 메이플스토리를 하며 얻은 행복한 기억을 지금도 간직하고 있다.
- 그 경험을 넥토리얼을 통해 다른 사람에게 돌려주고, 머물고 싶은 세계와 오래 기억될 게임을 만들고 싶다.
- C/C++ 기본기가 부족하지만 AI를 24시간 개인 교사처럼 사용하고 있다.
- 자물쇠와 열쇠 문제에서 해석의 누락·오류·모호함을 질문하고 회전 배열 구현을 학습했다.
- 넥슨의 오래된 IP 위에서 향수와 추억을 불러오는 게임을 만들고 싶다고 설명했다.

### 평가

- 결과: 보완 후 사용 가능
- 점수: 약 68점
- 강한 부분: 메이플스토리가 돌아갈 수 없는 어린 시절을 다시 떠올리게 한다는 개인적 동기가 구체적이고 진솔하다.
- 구조 문제: 같은 결론이 반복되어 1분을 넘기기 쉽고, 자물쇠와 열쇠의 세부 설명 때문에 자기소개 중심이 흐려진다.
- 직무 문제: 왜 게임을 만들고 싶은지는 설명했지만 왜 기획자가 아니라 프로그래머여야 하는지는 부족하다.
- 표현 위험: “넥슨은 필수”, “IP는 해자” 같은 표현은 개인 동기보다 사업 용어로 들릴 수 있다.
- AI 경계: 정답을 요구하지 않았다고 말하면서 회전 구현을 받았다고 설명하면 모순처럼 들릴 수 있다. 회전 원리와 Python 표현법에 제한된 힌트를 받았고 전체 탐색·경계 적용은 직접 했다고 구분해야 한다.

### 60초 개선 답변

> 안녕하세요. 저는 모르는 문제를 작은 단위로 나누고, 직접 구현하고 검증하면서 이해의 범위를 넓혀 가는 김규태입니다. 어린 시절 형제들과 메이플스토리를 하며 느꼈던 즐거움은 지금도 제게 오래 남아 있습니다. 게임은 재미뿐 아니라 사람의 시절과 관계까지 기억하게 만드는 매체라고 생각하며, 이제는 제가 받았던 경험을 다른 이용자에게 돌려주고 싶어 게임 프로그래머에 지원했습니다. 특히 오랫동안 사랑받는 IP와 세계를 만들어 온 넥슨에서 이용자가 안심하고 머물 수 있는 시스템을 만들고 싶습니다. 아직 게임 프로젝트와 C++가 부족하지만, C와 자료구조를 다시 공부하고 AI에는 정답보다 제 해석의 오류와 빠진 조건을 질문한 뒤 직접 구현하는 방식으로 보완하고 있습니다. 넥토리얼에서 이 학습 방식을 실무 기본기로 발전시켜 오래 기억되는 게임을 만드는 프로그래머로 성장하겠습니다.

### 현재 대기 중인 꼬리질문

> 게임은 기획자, 아티스트, 사업 담당자도 만들 수 있습니다. 그런데 왜 게임 기획자가 아니라 반드시 게임 프로그래머가 되고 싶은가요? 본인이 좋아하는 게임 이야기보다 프로그래밍으로 어떤 문제를 해결하고 어떤 시스템을 만들고 싶은지를 중심으로 답해 보세요.
