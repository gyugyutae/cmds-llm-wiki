# 5장 포트폴리오 검토와 거래 확정 기준

## 최신 확정과 구조 재검토

최신 사용자 결정은 개인 **4장**(동시성·원자성·멱등 재시도·대사/복구)과 협업 **1장**이다. 총 5개 문제 해결 블록이며 아래 개인3/협업2와 4블록 안은 이전 제안으로 보존한다. [[금융 백엔드 포트폴리오 5장 원고]]를 목표로 현재 코드·설정·테스트를 확인해 다음 구현을 안내한다. 별도 에이전트 개발 길잡이는 사용자 요청으로 삭제했다. 상세 구조와 대표 글 계획은 필요할 때 함께 참조한다.

후속 확정: [[금융 백엔드 포트폴리오 5장 원고]]에서 **개인 3블록(3장)·협업 1블록(2장)**을 `제목→그림→문제 원인 약 3줄→해결 과정 약 3~4줄→결과`로 반복한다. 검증 조건·한계·근거는 결과 안에 둔다. 이력서는 두 프로젝트의 가장 강한 사례를 각각 선택한다. 실제 페이지 배치는 사용자 요청대로 보류한다.

사용자는 결과 증거 기준과 판단·증거 복원을 채택했다. 이력서는 영상 첫 번째 문제 해결형으로 변경한다. 개인 하나·협업 하나의 가장 강한 사례를 원인→해결→검증→결과로 구성하고 기본기 증거를 각 사례에 포함한다. [[금융 백엔드 이력서 2장 원고]]에 목표 문안을 작성했다.

포트폴리오는 **표지·보조 정보 없이 총 5장**으로 확정한다. 노션의 A3·크기83 설정을 사용하며 실제 PDF 페이지 수는 미검증이다. 아래 과거 임시안의 보조 정보 5장은 다음으로 대체한다.

| 장 | 현재 권장 구성 |
|---|---|
| 1 | 개인 서비스의 최소 맥락·전체 구조 + 동시성/원자성 판단과 검증 |
| 2 | 개인 대표 사례: 응답 유실·미확정·멱등 처리·확정 증거 |
| 3 | 개인 대사·SQL·배치 재개·복구 결과 |
| 4 | 협업 대표 사례의 문제·원인·대안·본인 구현 |
| 5 | 같은 협업 사례의 통합 검증·공동 출시·사용자 결과·본인 기여 |

협업 마지막 장은 별도 문제를 꾸며 넣지 않는다. 한 사례를 두 장에 걸쳐 판단과 증거로 설명할 수 있다. 실사용/통합 증거가 한 장에 충분하면 다른 강한 사례의 그림·측정에 공간을 재배분한다. 현재는 개인 3장·협업 2장이 가장 균형 있는 시작안이며 증거가 생긴 뒤 순서를 조정한다. 보조 정보는 이력서에만 배치한다.

첫 번째 이력서 형식은 영상에서도 기본기 확인이 어려울 수 있다고 경고한다. 따라서 본인 API 계약·SQL/스키마·트랜잭션·예외 처리·검증을 짧게 명시한다. ‘기본기가 출중하다’는 자기평가 대신 직접 작성·설명·반례 수정·독립 검증 가능한 근거로 판단한다. 도구 이름과 목표 수치만 있는 사례는 강한 성과로 취급하지 않는다.

이 문서는 financial-lab 개발·학습 길잡이에 연결하는 검토안이다. 제출본 제작·실험 결과가 아니다. 최신 사용자 결정은 **이력서 2장 + 포트폴리오 5장**이다. 이전 포트폴리오 2쪽 결정은 폐기한 분량 기준으로 보존한다. 노션 A3·83 설정의 정확한 의미와 표지 포함 여부는 질문 중이며 실제 PDF 페이지 검증은 하지 않았다.

## 거래 확정·예약 해제 기준을 정하는 방법

아래는 모의 기관 계약을 설계하기 위한 제안이며 금융업계 공통 계약이 아니다. 먼저 요청 키의 동일 거래 보장, 결과 조회의 의미, 최종 거절의 불가역성, 명세 완전성과 수정 규칙을 계약으로 정한다. 그 계약이 허용하는 증거만 상태 전이의 근거로 사용한다.

| 관측 | 판단 | 금액 처리 |
|---|---|---|
| 기관이 같은 거래 ID·금액·통화에 대해 최종 성공을 반환 | 로컬 성공 확정 후보 | 로컬 트랜잭션에서 예약을 실제 출금으로 전환·원장 기록. 중복 반영 금지 |
| 기관이 최종 거절하며 이후 처리되지 않는다고 보장 | 실패 확정 후보 | 로컬에서 예약 해제·거절 사유 기록. 반복 해제 금지 |
| 타임아웃·연결 오류·일시 오류 | 결과 미확정 | 예약 유지·같은 거래로 결과 조회 |
| 조회 결과 ‘없음’ | 조회 지연·미접수 가능성 구분 필요 | 단순 부재만으로 예약 해제 금지 |
| 마감 지남·오래 기다림 | 재조회·검토 필요 | 시간만으로 성공/거절을 확정하지 않음 |
| 명세에서 일치하는 확정 결과 발견 | 계약상 최종성·버전·완전성 확인 후 복구 후보 | 기존 확정 경로 사용·재대사 |
| 금액 차이·서로 모순된 최종 결과 | 검토 필요 | 자동 금액 조정·예약 해제 금지 |

최종 거절은 늦은 Worker가 같은 거래를 다시 지급할 수 없는 상태여야 한다. ‘아직 못 찾았다’와 ‘앞으로도 처리되지 않는다’를 구분한다. 취소를 추가한다면 기관의 취소 확정과 발송 중 작업 경합을 별도 설계한다. 계약이 제공하지 않는 취소를 임의로 가정하지 않는다.

모의 모델에서 원금 10만원 중 1만원을 예약하면 사용 가능 9만원·예약 1만원으로 표현할 수 있다. 성공 확정 시 예약 1만원을 소진하고, 확정 거절 시 사용 가능 금액으로 반환한다. 이는 설명용 예약 모델이며 계좌 회계·원장 구현의 실제 필드와 맞춰 정의해야 한다.

**다음 계약 질문:** 성공·거절이 최종이라는 증거는 어떤 필드인가? 조회의 ‘없음’은 처리 중에도 가능한가? 명세는 수정될 수 있는가? 재시도 키는 얼마나 보관하는가? 장기 미확정은 어느 시점에 누구에게 검토 요청하는가? 시간 값은 금융 표준처럼 만들지 않고 모의 SLA로 표시한다.

## 압축 전 원고와 2쪽 원고 비교

10월 1일 원고는 개요·전체 구조·개인 네 사례·협업 개요/사례·보조 정보를 여러 쪽으로 분리했다. 2쪽 원고는 개인의 동시성·rollback·요청 키를 하나의 블록에 묶고 대사를 두 번째 블록으로 만들었다. 따라서 내용이 모두 삭제된 것이 아니라 상세 설명과 그림·표의 공간이 줄었다.

| 복원·보강할 항목 | 5장에 활용할 방법 |
|---|---|
| 경합 대안 비교·집중 계좌·락 비용 | 동시성 사례에서 조건부 갱신/낙관·비관 잠금의 판단과 실측표 |
| rollback 실패 위치·독립 DB 조회 | 동시성/원자성 사례 안의 작은 실패 위치 표로 복원 |
| 키 범위·내용 충돌·재시작·보관 정책 | 응답 유실 사례의 계약·경계·반례로 복원 |
| 상세 시퀀스·미확정 처리 | 응답 유실 사례의 중심 그림 |
| 대사 SQL·EXPLAIN·중단 재개·오탐/미탐 | 대사 사례의 비교표·오류 분류·재대사 결과 |
| 협업 API 계약·리뷰로 바뀐 판단·기여 | 협업 사례에서 실제 경험으로 교체 |
| 재현·조건·한계·근거 링크 | 매 사례에 짧은 공통 행으로 배치 |

연구실 요청 자료는 사용자 삭제 결정을 유지한다. 5장으로 늘었다고 되살리지 않는다. 긴 학습 목차·모든 코드·원본 로그·대표 글 본문은 길잡이와 저장소에 남긴다. 새 기능 수집보다 판단·증거가 읽히는 공간을 복원한다.

## 포트폴리오 5장 배치 제안

표지를 따로 쓰지 않고 총 5장에 모두 포함하는 임시안이다. 사용자 답변에 따라 변경한다. 개인 1개·협업 1개를 유지하며 사례 수와 프로젝트 수를 구분한다.

| 장 | 핵심 사례·내용 | 그림·증거 |
|---|---|---|
| 1 | 이름·목표·연락처·개인 서비스 한 문장·운영 가정 한 줄 + 동시 출금/원자성 사례 | 작은 전체 구조와 핵심 경합/실패 위치, 오류·p99·경합 비교 |
| 2 | 응답 유실 거래의 멱등 재시도·미확정 확인 | 시퀀스·계약·대안·재시작 결과·대표 글 직접 링크 |
| 3 | 거래 대사·배치 재개·복구와 정산 집계 연결 | 독립 입력·오류 분기·SQL/실행계획·재대사 결과 |
| 4 | 협업에서 본인이 해결한 핵심 통합/요구 변경 문제 | 실제 시스템 흐름·PR·API 계약·리뷰·사용자 결과 |
| 5 | 협업 출시/팀장 기여 요약 + 직무 관련 경험·학력·자격·어학 | 팀 전체/본인 책임 구분·증빙. 내용이 부족하면 앞 사례 설명 공간으로 활용 |

1장에 그림 두 개가 과밀하면 전체 구조를 작은 도식으로 만들거나 인접 장으로 조정한다. ‘각 장 하나의 핵심 사례’를 유지하되 모든 사례에 전체 아키텍처를 반복하지 않는다. 순서는 실제 증거가 가장 강한 사례를 기준으로 바꿀 수 있다. 별도 표지나 별도 자격 페이지를 의무로 두지 않는다.

## 이력서 2장 배치 제안

- **1장:** 이름·연락처·대표 강점 한 문장·대표 글 직접 링크·설명 가능한 핵심 기술·개인 프로젝트 약 6~8줄.
- **2장:** 협업 프로젝트 약 6~8줄·관련 인턴/실습이나 실제 직무 활동·학력·자격·어학.
- 프로젝트마다 서비스·기간·팀/역할·본인 기본 구현·대표 문제/선택/결과·상세 근거를 표시한다. 기본 구현도 기능의 목적과 확인한 동작으로 짧게 쓴다.
- `자격 | 정보처리기사 [취득 연월] · SQL 개발자(SQLD) [취득 연월]` 한 줄. 실제 취득한 경우만 제출한다.
- 약 7줄만으로 2장을 억지로 채우지 않는다. 남는 공간은 역할·근거·읽기 편한 배치에 쓰며 미완료 경력을 추가하지 않는다.

## 새 인제스트 자료에서 추가로 반영할 점

[[ideal 이력서와 포트폴리오 참고 영상 활용 지도]]의 21개 영상 요약과 관련 Wiki를 기준으로 검토했다. 로컬 자막과 요약을 참고했으며 모든 영상을 재생하거나 채용 효과를 검증한 것이 아니다.

1. **기본기와 역할:** 문제 해결 성과만 남겨 API·DB·검증의 본인 구현 범위를 지우지 않는다. 신입의 기본 구현도 보여준다.
2. **선택의 이유:** 기술 이름 대신 이 제약에서 왜 선택했고 무엇을 포기했는지 쓴다.
3. **그림의 목적:** 경합은 트랜잭션, 응답 유실은 시퀀스, 성능은 전후 그래프를 고른다. 화살표를 본인이 설명할 수 있어야 한다.
4. **조건 있는 결과:** 가정 TPS/사양과 실측을 구분하고 같은 기관 계약·데이터에서 비교한다. 링크 없이도 조건·결과를 이해하게 쓴다.
5. **대표 글:** 홈 대신 글로 연결하되 제출본에도 핵심 판단을 요약한다. 클릭해야만 프로젝트가 설명되는 구조는 피한다.
6. **AI 역할:** 도구를 썼다는 사실보다 문제 정의·검증·직접 변경을 표시한다. 금융 프로젝트에 AI 기능을 억지로 추가하지 않는다.
7. **피드백:** 문장마다 설명해 보고 표현/이해/근거 부족을 나눠 개선한다. 최종 PDF 페이지·잘림·링크는 설정 확인 후 검증한다.
8. **지원처 적합성:** 공고별 역할과 관련 경험의 순서를 바꾸고 학점·활동·수상의 가치를 영상의 일반론만으로 결정하지 않는다.

## 미결 사항

- ‘노션 A3 크기83’이 A3 PDF의 배율 83%인지와 내보내기 방식/방향: 질문 중.
- 5장에 표지·보조 정보도 포함하는지: 질문 중.
- 위 상태 전이는 권장 설계안이며 기관 조회·명세 계약의 세부 조건은 논의 후 확정한다.
