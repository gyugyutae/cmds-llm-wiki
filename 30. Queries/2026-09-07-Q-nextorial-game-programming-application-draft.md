## A안 선택 후 문항별 재배치 — 논의용, 제출본 아님

2번을 CUEE 경쟁 분석으로 쓰면 기획 중심으로 읽힐 위험이 있어 Threads를 우선 후보로 재배치한다. Threads의 기술 문제와 본인 해결 증거가 없으면 확인된 운영 개선으로 범위를 한정한다. JavaParser는 원인 분석까지 수행했고 개선 재실행은 없으므로 `문제 해결 완료`를 요구하는 문항의 주력으로는 약하다.

핵심 제안 문장: `AI를 활용해 아이디어를 반복 운영 가능한 작업으로 만들고, 사용자 반응과 피드백을 다음 개선에 반영해 온 지원자입니다.` 실제 코드 검증 역량은 별도 증거로 보완해야 하며, 모든 생성 결과를 직접 검증했다고 일반화하지 않는다.

확인된 학습 소재는 컴퓨터프로그래밍·자료구조 수업에서 C를 사용한 경험, 코딩테스트 준비 과정에서 자료구조·알고리즘을 별도로 공부한 경험, Gemini Gem을 단계별 힌트와 재설명 중심으로 사용한 학습법이다. 학점은 넥토리얼 지원서 소재에서 제외한다. 당장 새로운 C++ 프로젝트를 준비했다는 서사도 사용하지 않고 현재까지의 경험으로 작성한다. Threads 팔로워 650명은 2026-08-31 자기보고이며 기술력이나 개선의 인과효과로 해석하지 않는다. CUEE 팀 수상은 개인 구현력의 증거와 구분한다.

품질 공백: 참조 페이지는 partial/unverified가 포함되며 explored 상태도 섞여 있다. standalone이므로 mainVaultRelated 미설정은 연결할 모선이 없는 상태다. harness와 cuee에는 지정 형식 Bias Check가 없으므로 이 논의에서 기여·검증 범위의 제한을 명시한다.

현재 확인된 언어 기반은 전공수업에서 사용한 C와 코딩테스트에서 사용하는 Python이다. C++·C#·Unity·Unreal 경험은 없다. 자기소개서는 `C와 자료구조·알고리즘 기초 → 질문·설명·재검증 중심 학습 → AI 프로젝트 실행과 운영 → 게임 프로그래밍으로의 확장`을 중심축으로 삼는다.

사용자가 확인한 게임 동기는 메이플스토리에서 다른 이용자와 재화·아이템을 거래하며 형성되는 상호작용이다. 희망 기여 영역은 이런 유저 간 상호작용을 가능하게 하는 게임 시스템과 개발자의 반복 작업을 줄이는 자동화 도구다. 이는 공식 공고의 게임·플랫폼 서버/시스템 구현과 개발 생산성 향상용 툴·자동화 업무에 연결할 수 있다. 메이플스토리의 구체 플레이 기간, 거래 장면, 개발 관점에서 느낀 문제 또는 만들고 싶은 기능은 추가 확인이 필요하다.

사용자는 교내 드론 동아리에서 C를 사용해 개발한 경험이 있다고 정정했다. NSquare는 이 경험과 무관하므로 지원서에서 제외한다. 현재 Wiki와 로컬 검색에서는 드론 동아리 활동 자료가 확인되지 않으므로, 동아리명·기간·목표·작성한 코드·AI 기여·실행 결과를 확인한 뒤 자기소개서의 C 활용 근거로 사용한다.

추가 자기보고에 따르면 활동명은 `자비스`, 기간은 2025년 2학기 한 학기이며 팀 활동이었다. Arduino 기반 드론 자율주행을 목표로 PX4-Autopilot 기존 코드를 AI의 도움으로 수정했고, MAVLink 통신과 Pixhawk 모터 제어를 다뤘다. 실제 테스트는 수행하지 못했고 현재 코드를 거의 설명하지 못한다. 따라서 `C로 드론 자율주행을 구현했다`는 완료 성과로 쓰지 않는다. 방대한 오픈소스 코드베이스를 접하며 기존 코드를 읽고 수정하는 어려움과, 이해·검증 없이 AI 수정에 의존했을 때 지식이 남지 않는 한계를 배운 경험으로만 사용할 수 있다.

현재 코딩테스트 수준은 사용자 자기보고 기준 프로그래머스 Level 2의 어려운 문제와 Level 3의 쉬운 문제에 도전하는 단계다. `자물쇠와 열쇠`에서 2차원 배열의 90도 회전과 배열 경계처리에 막혔고, Gemini Gem으로 회전 하위 문제의 힌트를 받은 뒤 적용했다. 경계처리의 최종 해결 방식과 AI 없이 재풀이했는지는 아직 확인되지 않았다.

Threads 프로젝트에서 사용자가 직접 결정했다고 확인한 것은 게시물의 글 포맷이다. 이 프로젝트는 공식 공고의 생성형 AI 활용·구조적 사고·개발 생산성 자동화와 정합성이 있어 4번 핵심역량의 우선 소재로 쓸 만하다. 그러나 어떤 포맷을 왜 선택했는지, 비교한 지표와 전후 결과, 사용자가 직접 수정·검증한 범위를 확인하기 전에는 2번 문제 해결 사례로 확대하지 않는다.

추가 확인 결과, 초기의 일반적인 논문 작성 팁 형식은 반응이 낮았고 `자주 하는 실수 → 좋지 않은 결과 → 나쁜 예시 → 좋은 예시` 형식으로 바꾼 뒤 반응이 증가했다고 사용자 자기보고로 확인했다. 사용자는 글 포맷을 결정하고, AI가 생성한 Python 코드를 읽으며 자신의 의도대로 작성됐는지 질문하고 모호하거나 잘못된 부분을 직접 고쳤다고 설명했다. AI가 수정 시작점을 제안하거나 코드 완성을 보조하면 사용자가 선택·수정하는 방식으로 약 50:50의 기여 비율을 유지하려 했다는 것은 사용자 자기평가이며, 라인별 기여율로 검증된 수치는 아니다.

현재 로컬 저장소에는 OpenRouter와 Groq용 API 키를 분리하고, 기본 provider 실패 또는 malformed JSON 이후 다른 provider로 전환하는 `fallback_provider_chain()`과 실행 흐름, 관련 테스트가 존재한다. `python3 -m unittest tests.test_generate_auto_thread`로 29개 테스트 통과를 확인했다. 다만 해당 fallback 구간은 현재 작업 트리에서 미커밋 상태로 표시되므로 구현 시점·작성 주체·실제 운영 장애에서의 사용 여부는 추가 확인이 필요하다. 비동기·동시성 구현은 저장소 검색에서 확인하지 못했으므로 자기소개서에 확정적으로 쓰지 않는다.

사용자 설명의 `fallback은 OpenAI`는 코드상 `Groq provider를 통해 openai/gpt-oss-120b 모델 사용`으로 구체화한다. 실제 운영에서 fallback이 작동한 적은 없고 코드와 단위 테스트로만 확인했다. 현재 GitHub Actions의 `LLM_FALLBACK_PROVIDER`는 빈 값이므로 배포 workflow에서는 활성화돼 있지 않다. 따라서 `API가 소진돼 실제 서비스가 자동 복구됐다`가 아니라 `API 실패를 예상해 대체 provider 구조를 만들고 단위 테스트로 전환 흐름을 확인했다`고 쓴다.

사용자가 중요하게 보는 개발 원칙은 `만약 실패한다면 어떻게 할 것인가`를 먼저 묻고 fallback과 예외처리를 설계하는 것이다. 이는 Threads provider 전환, 잘못된 JSON 재시도, CI/CD 실패 처리 경험을 근거로 2번과 4번에 일관되게 연결한다.

사용자는 CI/CD 과정에서 반복되는 오류를 AI와 함께 원인 후보를 찾고 잠재적 위험 구간을 검토해 직접 개선했다고 보고했다. 정확한 실패 메시지, 원인, 수정 파일, 재실행 결과는 아직 특정되지 않았다.

사용자가 제공한 GitHub Actions 오류는 `Daily publication objective was not verified`와 exit code 1이다. `Auto Publish Daily Threads Chain` workflow를 수정하고 단위 테스트를 시도했다고 보고했다. 현재 작업 트리에서는 해당 오류 문자열을 찾지 못해 과거 workflow 버전 또는 GitHub 실행 시 생성된 검증 문구일 가능성이 있으며, 정확한 원인과 수정 diff는 미확인이다.

첨부 스크린샷을 직접 확인한 결과, 상위 원인은 `Select prevalidated reserve chain` 단계에서 사용할 수 있는 검증된 reserve 글을 찾지 못한 것이다. 게시 단계가 실행되지 않았고, 이어진 `Verify daily publication objective`가 `post_missing`, top-level post count 0을 반환했다. 마지막 `Daily publication objective was not verified`는 앞선 게시 누락을 보고한 결과다. GitHub Actions 공개 이력에는 2026-08-27 이후 2026-09-06까지 조회한 최근 run이 모두 failure로 남아 있다. 따라서 end-to-end 자동 게시 장애를 해결했다고 표현하지 않는다. 과거에는 success run이 존재하지만 현재 장애의 해결 결과로 연결할 수 없다.

사용자는 여러 논문과 자료를 크롤링해 초안을 만들 때 시간이 오래 걸려 비동기 처리했다고 보고했다. 현재 저장소 검색에서는 Python의 `asyncio`, `async def`, `ThreadPool`, `concurrent.futures` 구현을 확인하지 못했다. TypeScript dashboard 일부에는 `await`와 `Promise.all`이 있으나 사용자가 말한 논문 크롤링과 같은 기능인지 확인되지 않는다. 해당 주장은 코드 위치 확인 전에는 제출본에서 제외한다.

AI 공동 코딩 방식은 사용자가 먼저 의도와 요구사항을 제시하고, AI에게 수정 시작점과 코드 후보를 받은 뒤 해당 코드가 의도대로 작성됐는지 질문·검토하며 직접 수정하는 과정이다. `50:50`은 목표로 삼은 자기평가이므로 정확한 기여율 수치보다 이 작업 순서를 설명한다.

성과 수치는 포맷 변경 전 게시물이 좋아요 2개·댓글 7개, 변경 직후 게시물이 좋아요 63개·재게시 28개·전송 32개, 이후 좋아요 100개 이상 게시물 3개라는 사용자 자기보고가 추가되었다. 현재 로컬 `threads-post-metrics.csv` 27행에서 독립적으로 확인되는 최대값은 좋아요 67·재게시 26·조회 11,349로 범위와 시점이 다르다. 지원서에는 실제 Threads 화면이나 내보낸 데이터로 다시 확인한 수치만 최종 사용한다.

CUEE에서는 `모두의 창업` 1차 탈락 후 팀장으로서 `이대로 가면 실패할 것 같다`는 위기의식을 팀에 전달하고, 당시 피드백을 토대로 수익구조와 경쟁사 분석을 보완했다고 자기보고했다. 이후 2026-05-27 최우수상과 2026-06-16 대상을 받았다. 3번에서는 공격적인 표현 대신 문제·본인 책임·근거·대안을 어떤 순서로 말했는지와 팀 반응을 확인한 뒤 사용한다.

팀원들은 위기의식에 동의했고 이를 다시 집중하는 계기로 삼았다. 경쟁사 분석은 팀원 한 명이 담당했고, 최종적으로 PPT를 개선해 다음 대회에서 좋은 결과를 얻었다. 다만 수익구조 담당자, 사용자가 직접 수정한 PPT 부분, 팀원 한 명이 제시한 반대 의견 여부는 아직 불명확하다.

메이플스토리는 초등학생 때 지속적으로 플레이했다. 모르는 사람과 교환창에서 재화와 아이템을 주고받고, 자유시장에서 여러 상인이 채팅으로 거래하는 모습이 실제 시장처럼 느껴져 재미를 느꼈다. 희망 기여 영역은 거래소·경매장·재화 흐름이다. `넥슨 게임들은 인플레이션이 심각하다`는 포괄적 평가는 근거 없이 사용하지 않는다. 대신 장기 서비스에서 재화의 생성·소모와 거래 규칙이 이용자 경험에 미치는 영향을 관찰했고, 안정적이고 지속 가능한 경제 시스템을 만드는 데 관심이 있다고 표현한다.

## 자기소개서 1차 초안

### 1. 지원동기와 노력 과정

초등학생 때 메이플스토리에서 모르는 사람과 교환창을 열어 메소와 아이템을 거래하곤 했습니다. 거래를 확정하는 순간 메소와 아이템이 양쪽 계정에 실시간으로 정확히 반영되는 과정이 신기했습니다. 지금은 개발자의 관점에서 거래 도중 연결이 끊기거나 요청이 중복되더라도 재화와 아이템이 누락되거나 중복 지급되지 않도록 만드는 방법에 관심을 갖고 있습니다. 이러한 거래 시스템을 개발하고 싶어 넥토리얼에 지원했습니다.

Threads 자동화를 운영하며 API가 실패했을 때의 처리와 반복 검증이 중요하다고 느꼈습니다. 이 경험을 거래소·경매장 개발에 연결해, 아이템 등록·구매·취소와 거래 실패 상황에서 재화와 아이템이 올바르게 반영되는지 확인하는 테스트를 자동화하고 싶습니다. 오류 기록을 모아 원인 분석을 돕는 도구를 만들어, 개발자의 반복 확인을 줄이고 이용자가 안심하고 거래할 수 있는 시스템에 기여하고 싶습니다.

컴퓨터프로그래밍과 자료구조 수업에서 C를 익혔고, 현재는 Python으로 프로그래머스의 어려운 Level 2 문제와 쉬운 Level 3 문제에 도전하며 자료구조와 알고리즘을 공부하고 있습니다. Gemini Gem에는 정답을 바로 알려주지 않고 단계별 힌트를 제공하도록 설정했습니다. ‘자물쇠와 열쇠’ 문제에서는 배열 경계와 회전 로직에서 막혔습니다. Gem이 제시한 Python 컴프리헨션 회전 예시를 참고해 제 코드에 맞게 작성하고 문제를 통과했습니다.

자비스 드론 동아리에서는 C/C++로 작성된 PX4-Autopilot의 기존 코드에서 MAVLink 통신과 Pixhawk 모터 제어 관련 부분을 AI의 도움을 받아 탐색·수정했습니다. 팀 활동에서는 자율비행 시뮬레이션을 진행했으며, 실제 기체 시험까지 이어가지는 못했습니다. 방대한 코드에서 수정할 지점을 찾는 어려움을 겪으며 기존 구조와 변경 영향을 이해하는 과정의 중요성을 배웠습니다. 넥토리얼에서도 모르는 부분을 질문하고 코드와 테스트로 확인하며 실무 역량을 키우겠습니다.

### 2. 프로젝트와 어려운 문제

AI 논문 활용법을 소개하는 Threads 콘텐츠를 조사·작성·게시하고 반응을 수집하는 자동화 프로젝트를 운영했습니다. 가장 어려웠던 문제는 자동으로 많은 글을 만드는 것이 아니라, 이용자가 실제로 필요로 하는 내용을 읽기 쉬운 형식으로 만드는 일이었습니다. 초기에는 논문 작성에 도움이 되는 일반적인 팁을 제공했지만 기대한 반응을 얻지 못했습니다. 저는 정보의 양보다 문제를 제시하고 해결책을 보여주는 순서가 불명확한 것이 원인이라고 가정했습니다.

이에 글을 `사람들이 자주 하는 실수 → 그로 인해 생기는 좋지 않은 결과 → 나쁜 요청 예시 → 좋은 요청 예시` 순서로 바꾸었습니다. AI에는 자료 후보 조사와 초안·반복 코드 작성을 맡겼고, 저는 글의 포맷과 전달 순서를 결정했습니다. 생성된 문장과 Python 코드가 제 의도대로 동작하는지 실행하고 검토했으며, 모호하거나 다른 동작을 하는 부분은 다시 질문하고 수정했습니다. 포맷 변경 전 대표 게시물은 좋아요 2개·댓글 7개였지만, 변경 직후 게시물은 좋아요 63개·재게시 28개·전송 32개를 기록했습니다. 이후에도 좋아요 100개 이상을 기록한 게시물 3개가 나왔고, 계정은 2026년 8월 기준 팔로워 650명에 도달했습니다.

이 경험을 통해 자동화의 가치는 작업량을 늘리는 데만 있지 않으며, 결과를 관찰하고 가설을 수정할 수 있는 반복 구조를 만드는 데 있다는 것을 배웠습니다. 게임 시스템을 개발할 때도 기능 구현에서 멈추지 않고, 이용자의 실제 반응과 데이터를 바탕으로 개선하겠습니다.

### 3. 협업 중 솔직한 피드백

노인의 앱 사용을 돕는 길잡이 CUEE의 5인 팀장으로 활동하며, 심사위원에게 “사용자가 돈을 내면서까지 쓸 것인가”라는 질문을 받았습니다. ‘모두의 창업’ 탈락 후 저 역시 건별 결제라면 사용하지 않을 것 같다고 느꼈습니다. 팀원들에게 제 판단이 부족했음을 인정하고, 지금 방향을 재검토해야 한다고 솔직하게 말했습니다. 팀은 개인에게 무료로 제공해 시장성을 검증한 뒤 기업과 제휴하는 방향으로 계획을 바꿨습니다. 팀원들이 경쟁사 분석과 예약 성공 건당 수익을 얻는 CPS 모델을 구체화했고, 저는 발표를 맡아 팀원들과 대본을 반복 개선했습니다. 이후 두 대회에서 최우수상과 대상을 받았습니다. 이미 들인 시간과 노력이 아깝더라도, 잘못된 방향을 알아차렸다면 솔직하게 말해야 한다는 것을 배웠습니다. 매몰비용 때문에 침묵하기보다 기존 작업을 바꾸는 부담을 감수하고, 근거를 공유하며 더 타당한 방향으로 함께 나아가겠습니다.

### 4. 핵심 역량

제가 자신 있게 활용하는 역량은 AI가 개발 맥락을 이어받도록 문서를 구조화하고 관리하는 능력입니다. 구요환 님의 공개 LLM Wiki 패턴을 개인화해 Codex 개발에 활용하고 있습니다. ## 자기소개서 설계

### 1. 지원동기와 노력 과정 — 1,000자

아직 확정할 수 없는 핵심 사실은 `왜 게임인가`, `왜 넥토리얼인가`, `어떤 게임 또는 시스템 경험이 계기가 되었는가`다. 확인 후 아래 순서로 쓴다.

1. 게임을 소비하는 데서 시스템을 만드는 쪽으로 관심이 이동한 구체적 계기
2. 소프트웨어공학 전공에서 쌓은 문제 분해·서버·성능·데이터 처리 경험
3. 프로젝트를 빠르게 시작하되 AI 결과를 이해·수정·검증할 수 있어야 한다고 배운 과정
4. 넥토리얼에서 기존 CS 기초와 AI 활용 경험을 게임 기능·도구 개발에 연결하려는 목표

### 2. 프로젝트와 가장 어려웠던 문제 — 1,000자

현재 가장 안전한 소재는 `CUEE`의 서비스 방향 전환과 경쟁 서비스 분석이다. 팀장으로서 노년층에게 앱 사용법을 학습시키는 `배우담`에서 실제 사용 순간 다음 행동을 안내하는 오버레이 앱 `CUEE`로 전환했다. 첫 아이디어톤에서 경쟁 서비스 분석이 부족하다는 질문을 받은 뒤 동일 평가항목의 비교표를 만들어 차별성을 명료화했고, 5인 팀으로 아이디어톤 최우수상·경남권 창업동아리 대상·U300+ 연계 우수상을 받았다. 다만 Android 코드는 AI가 작성했으므로 직접 구현 성과로 표현하지 않는다.

### 3. 반대 의견·솔직한 피드백 — 500자

`모두의 창업` 1차 탈락 뒤 팀원들에게 부족한 점과 아쉬움을 숨기지 않고 공유한 사례를 사용한다. 경쟁 서비스 분석 부족을 인정하고 비교 기준을 다시 세웠으며, 다음 학기 재도전과 후속 대회 목표를 제안했다. 이후 수상으로 이어졌지만, 성과보다 `실패를 공개하면 팀의 발언 장벽이 낮아지고 반대 의견을 개선 재료로 다룰 수 있다`는 배움을 중심으로 쓴다.

### 4. 자신 있는 핵심 역량 — 500자

현재 가장 강한 후보는 Python과 AI 활용 workflow다. Codex를 단순 생성 도구가 아니라 단계별 artifact와 검증 흐름을 갖춘 Python 기반 harness로 구조화했고, Threads 자동화에서는 여러 콘텐츠 형식을 시험해 반응이 좋은 형식을 템플릿으로 고정하고 GitHub Actions로 반복 운영했다. 2026-08-31 자기보고 기준 팔로워 650명이며, 저장소 스냅샷에서 성과 CSV 52행과 지표 집계 로직을 확인했다. 게임 직무에는 반복 작업을 도구화하고 결과를 측정·개선하는 역량으로 연결하되, C++·엔진 숙련도로 바꾸어 말하지 않는다.

## 자기소개서 서사 옵션

### A. AI-Augmented Developer — 권장

- 중심: AI로 코드를 생성하는 사람보다 문제를 정의하고 생성 결과를 평가·수정·운영하는 개발자로 성장
- 대표 증거: Threads workflow, harness, AI 활용 경계 기록
- 게임 연결: 대규모 콘텐츠와 반복 작업이 존재하는 게임 개발에서 AI를 도구·파이프라인·검증 자동화에 활용
- 약점: 게임 자체에 대한 개인적 동기가 추가되지 않으면 일반 AI 개발자 지원서처럼 보임

### B. 사용자 경험·제품 전환형

- 중심: CUEE에서 사용자가 막히는 순간을 줄이기 위해 학습 앱에서 실시간 안내 방식으로 전환
- 대표 증거: 팀장 판단, 경쟁 분석, 세 차례 수상
- 게임 연결: 플레이어 행동을 관찰하고 복잡한 시스템을 직관적인 상호작용으로 만드는 관심
- 약점: 실제 사용자 테스트와 직접 Kotlin 구현 근거가 부족함

### C. 시스템·성능 성장형

- 중심: 서버·성능·정적 분석 경험을 게임 클라이언트/서버의 latency, 안정성, 대규모 코드 이해로 확장
- 대표 증거: JavaParser 연구와 financial latency 문제의식
- 게임 연결: 프레임 시간, 네트워크 지연, 병렬 처리 같은 실시간 시스템 관심
- 약점: latency 프로젝트를 직접 구현·검증하지 않아 현재 대표 서사로는 위험함

### D. 도구·파이프라인 개발형

- 중심: 반복 작업을 workflow와 quality gate로 구조화해 팀이 핵심 문제에 집중하도록 만드는 성향
- 대표 증거: Threads workflow, harness, 해커톤 template
- 게임 연결: 빌드·테스트·콘텐츠 제작·데이터 검증을 돕는 게임 개발 도구와 파이프라인
- 약점: `직접 코드를 작성해 구현 가능한 영역` 설문에는 AI 생성 코드가 아닌 본인 구현 증거가 필요함

권장 조합은 A를 본문 중심으로 하고 B의 팀 프로젝트·사용자 관점을 보조하는 방식이다. D는 장기 희망 분야로 한 문단만 연결한다.
