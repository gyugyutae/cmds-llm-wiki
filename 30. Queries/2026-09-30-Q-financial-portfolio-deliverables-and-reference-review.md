# 금융 백엔드 최종 산출물과 개인·협업 포트폴리오 검토

## 권장 구성과 설계 순서

이상형은 현재 financial-lab 코드의 범위와 독립적으로 설계한다. 현재 프로젝트는 그 이상형을 실현할 후보이며, 계좌·이체라는 업무 경계가 맞아 발전시키기 좋은 출발점이다. 기존 구현 때문에 설계 목표를 낮추거나, 기존 코드의 존재만으로 선택을 확정하지 않는다. DB·원장 모델과 검증 요구에 맞춰 필요한 부분을 수정할 수 있다.

사용자는 개인 프로젝트 하나와 협업 프로젝트 하나를 원한다. 권장 기준은 **개인 금융 거래·원장 프로젝트 + 본인 백엔드 기여와 팀 협업을 증명하는 프로젝트**다. 협업 프로젝트는 금융 도메인일 필요가 없으며 데이터 처리·운영·API 통합 등의 경험으로 개인 프로젝트를 보완할 수 있다.

| 단위 | 권장 형태 |
|---|---|
| 개인 프로젝트 | 하나의 이체·원장 서비스와 대사 배치, 하나의 대표 저장소 |
| 해결 경험 | 동시성·부분 실패 원자성·멱등 재시도·대사의 서로 다른 네 사례 |
| 협업 프로젝트 | 별도 프로젝트에서 본인 구현, 리뷰·통합·릴리스·피드백 근거 |
| 전체 포트폴리오 | 개인·협업 두 프로젝트를 한 문서에 수록 |
| 대표 기술 글 | 가장 깊은 문제 하나를 충분히 다룬 글, 이력서에서 글 URL로 직접 연결 |

네 사례를 네 독립 프로젝트로 만들 필요는 없다. 생각등대의 약 네 블록은 문제 해결 경험의 서술 단위다. 프로젝트 수나 정확히 네 개라는 할당량으로 해석하지 않는다. 개인 프로젝트 상세 문서에는 네 사례를 모두 남기고, 제출본에서는 가장 강한 개인 사례와 협업 사례를 골라 약 4~6개 블록으로 제시하는 안을 권한다. 분량이 제한되면 개인 3개 + 협업 1개를 본문에 담고 나머지 개인 사례를 상세 문서로 연결한다.

## 토스 글에서 가져올 장점과 더 보강할 점

토스 정산 개편 글은 업무 제약, 거래별 추적, 계산 당시 설정 보존, 실패 재처리, 배치 개선과 투입 검증을 설명한다. 특히 전체 기술 목록보다 선택을 하게 된 업무 이유와 운영 결과의 연결을 참고할 수 있다. 다만 이 글이 개인 프로젝트를 그대로 실행할 수 있는 재현 패키지나 모든 성능 실험의 환경·원본 결과를 제공하는 것은 아니다. 설명용 코드와 수치 예시를 우리 프로젝트의 실측으로 사용하지 않는다. [토스 정산 개편기](https://toss.tech/article/42671)

따라서 대표 글에는 문제 상황·가설·대안·선택 이유·재현 명령·동일 조건의 전후 결과·실패한 시도·한계를 넣는다. 성능이 개선되지 않았어도 중복 거래나 부분 반영을 제거한 결과와 그 비용을 정확하게 적는다. 카카오페이 글은 목표 부하와 기존 처리 한계, DB 병목과 선택 이유, 정합성의 한계를 구분해 설명하는 참고 자료다. [카카오페이 성능 개선기](https://tech.kakaopay.com/post/improve-service-performance/)

## financial-lab을 발전시킨 최종 결과물의 명세

### 실행되는 결과물

- Java/Spring API: 계좌 조회, 이체 요청과 거래 결과 조회. 요청 키와 거래 ID를 이용해 결과를 추적한다.
- 관계형 DB: 스키마·제약조건·migration·이체 기록·원장. 초기 잔액과 원장 반영을 어떻게 연결하는지 명시한다.
- 대사 작업: 독립적으로 구성한 합성 기준 명세와 내부 기록의 누락·중복·금액·상태 차이를 탐지하고 예외 목록을 출력한다.
- 복구 절차: 처리 단계별 강제 실패, 응답 유실 뒤 재시도, 배치 중단 뒤 재실행을 재현한다.
- 실행 패키지: README, 환경 변수 예시, DB 준비·합성 데이터 생성, 테스트·실험·시연 명령. 실제 실행 환경에 맞는 명령은 구현 뒤 확정한다.

내부 계좌이체의 대사와 PG 가맹점 정산은 업무가 다르다. 내부 이체와 상대 기관 명세를 연결하려면 어떤 거래가 그 명세에 나타나는지 먼저 정의한다. 대사 구현만으로 수수료 계산·지급일 산정·은행 간 청산·실제 자금 집행을 구현했다고 쓰지 않는다. 최종 업무 범위에 따라 결과물의 이름도 정산 계산인지 거래 대사인지 정확하게 정한다.

### 정확성·데이터 처리·장애 대응의 완료 증거

| 역량 | 완료 시 보여줄 것 | 확인 방법 |
|---|---|---|
| 정확성 | 음수 잔액 금지, 완료 거래의 차변·대변 균형, 잔액과 기록의 일치 | 실패·동시성 테스트 뒤 별도 DB 연결과 검증 SQL로 최종 상태 확인 |
| 원자성 | 출금·입금·원장 반영이 함께 완료되거나 함께 취소 | 단계별 실패 주입과 commit/rollback 상태 비교 |
| 멱등성 | 같은 키의 동시 재요청과 응답 유실에도 한 번의 유효 반영 | 요청 수·실제 이체 수·원장 수·충돌 요청 처리 확인 |
| 데이터 처리 | 합성 오류 표본의 누락·중복·금액 차이 탐지와 SQL 비용 | 정답 표본 대비 탐지·오탐, EXPLAIN, 조회·쓰기 횟수, 데이터량별 소요시간 |
| 성능 | 목표 부하에서의 처리량과 비용, 집중 계좌 경합 | 환경·데이터·패턴·기간을 명시한 오류율·p95/p99·DB 자원 지표 |
| 복구 | 배치 중단·재시작 또는 API 중단 뒤 거래 추적·재처리 | 복구 전후 누락·중복, 복구 시간, 로그와 재시작 절차 |

앱 인스턴스나 DB 대기 서버를 구성했다는 사실과 장애 후 거래가 보존됐다는 증거는 따로 확인한다. 유지하려는 데이터 범위와 복구 시간은 실험 조건과 함께 쓴다.

### 제출과 검토에 쓰는 결과물 묶음

1. 실행 가능한 저장소와 고정된 release/commit.
2. 짧은 README와 업무 규칙·ERD·직접 설명할 수 있는 구조 그림.
3. 네 문제 해결 문서: 발생 조건, 초기 구현, 가설, 비교, 결과, 한계.
4. 테스트·SQL·합성 데이터와 재현 스크립트.
5. 측정 보고서와 원본 결과: 개선 전후 commit, DB 버전, 데이터 seed·크기, 실행 구간·횟수, 요청 분포, 오류 분류.
6. 장애 대응 runbook: 거래 ID로 상태 확인, 재처리 가능 여부, 실행·검증 순서.
7. 정상 이체 → 실패 → 동시 요청 → 응답 유실 재시도 → 대사 오류·재실행을 보여주는 짧은 시연.
8. 대표 기술 글 한 편과 이를 요약한 이력서·포트폴리오 블록.

코드는 사용자가 직접 작은 단위로 작성한다. 기능마다 요구사항과 실패 조건을 먼저 적고, 본인의 예상 결과 → 구현 → 검증 SQL/테스트 → 설명 → 수정의 순서로 진행한다. AI의 질문·힌트·리뷰와 본인이 작성·판단한 부분을 기록한다. 단순히 최종 코드를 읽어 설명하는 것보다, 본인이 실패를 재현하고 수정한 commit과 판단 기록이 강한 근거다.

## 대표 기술 글 초안

**제목 후보: 응답이 끊겨도 계좌이체는 한 번만 — 거래 원장과 멱등성을 검증한 과정**

1. 성공했는지 알 수 없는 이체 요청이 사용자에게 어떤 문제인지 설명.
2. 이체 완료·거절·결과 미확정 상태와 보존할 잔액·원장 조건 정의.
3. 초기 구현에서 응답 유실·재요청·동시 중복 요청을 만드는 실험.
4. 중복 확인·저장 사이의 경쟁을 분석하고 DB 제약과 transaction 경계 후보 비교.
5. 선택 이유와 구현: 그림, 핵심 코드, SQL, 요청 키의 내용 충돌 정책.
6. 재현 환경과 명령, 동일 조건의 개선 전후 표.
7. 중복 반영 수·원장 불일치·오류율·p95/p99, 정확성을 얻는 비용.
8. 해결하지 않은 실패 조건, 적용 경계, 다른 접근이 나을 조건.
9. 코드 commit·테스트·측정 원본 링크.

제목은 목표 제목이다. 결과 수치는 실험 뒤에만 채운다. 네 사례의 상세 기록을 모두 갖추되 대표 글은 하나의 질문을 깊게 다룬다. 같은 글의 필요한 배경에서 rollback·대사를 연결할 수 있다.

## 협업 프로젝트의 이상형

프로젝트 주제보다 실제 공동 작업과 본인 백엔드 책임이 중요하다. 본인이 데이터 모델·API·배치·운영 개선 중 하나를 맡고 다른 사람의 기능과 통합한 경험을 보여준다. API 계약 변경, 리뷰로 바뀐 설계, 통합 실패 해결, 공동 릴리스와 사용자/다른 팀원의 피드백을 근거로 남긴다. 혼자 여러 역할을 수행한 것을 팀 협업으로 포장하지 않는다.

기존 CUEE는 위키상 제품 방향 결정·팀 리딩과 AI 구현을 운영한 기록이 강점이며 독립적인 Kotlin 구현 증거로 쓰지 않는다. CUEE나 프로펠러 에이전트를 발전시킬지 새 백엔드 프로젝트를 할지는 아직 선택하지 않았다. 기존 것을 선택하면 실제 본인 서버 구현·PR 리뷰·통합·운영 증거를 추가할 수 있는지 먼저 검토한다.

사용자는 협업 프로젝트도 **이상형을 먼저 본 뒤 후보를 정하기**로 선택했다. 현재 프로젝트에 맞춰 아래 기준을 줄이지 않는다.

### 구체적인 협업 이상형 예시 — 업무용 데이터 검증·리포트 플랫폼

이것은 새로 구현했다고 주장하는 프로젝트가 아니라 검토할 후보 모델이다. 대상 조직의 사용자가 업무 데이터 파일을 업로드하면 오류를 검증하고 가공 결과·리포트를 조회한다. 담당자와 파일 형식·오류 처리 요구를 합의하고 배포 이후 피드백을 반영한다. 금융 데이터로 구현할 수도 있고 다른 업무 도메인으로 구현할 수도 있다.

| 축 | 목표 경험 |
|---|---|
| 제품 | 실제 담당자의 반복 작업과 불편을 확인하고, 시범 사용 전후 처리시간·재작업·오류 유형을 비교 |
| 본인 백엔드 | 업로드 요청·작업 상태 API, 데이터 모델·검증/처리 배치·SQL 조회 중 명확한 기능 경계를 직접 책임짐 |
| 공동 작업 | 화면/분석/다른 서버 담당자와 API·데이터 계약을 합의하고 실제 PR 리뷰·통합·공동 배포 |
| 문제 해결 | 파일 스키마 변경으로 통합이 깨짐, 처리 중단, 조회 지연 등의 실제 문제를 재현·분석·수정 |
| 결과 | 직접 작성한 코드·리뷰 후 변경·사용자 피드백 반영·릴리스와 측정 원본을 제시 |

가장 강한 협업 블록은 '팀장 역할'이라는 직함보다, 예를 들어 '데이터 형식 변경으로 화면과 배치가 함께 깨진 문제를 API 계약·검증 규칙을 합의해 해결하고 공동 릴리스한 경험'처럼 구체적인 기술 문제와 협업 판단을 연결한다. 최종 제목과 수치는 실제 경험 뒤에 채운다.

## 레퍼런스 공통 장점과 현재 초안 비교

현재는 좋은 사례의 평가 항목을 설계에 담았다는 수준이다. 완성된 사례와 동등하거나 우위라고 판정할 재현 결과·문서·외부 평가가 없다. 특히 인턴·실무에서 얻은 운영·조직 경험은 개인 프로젝트의 기능 개수로 대체되지 않는다. 이상형에서는 실제 협업·사용·검토와 복구 경험을 확보해 이 공백을 보완한다.

금융 백엔드라는 목표에 대해 중요한 역량을 이 설계에서 뽑으면 업무 규칙을 데이터와 코드로 표현하기, SQL·모델링, transaction·동시성·재시도 판단, 데이터 추적·대사, 장애 분석·복구, 비용을 설명하는 성능 측정, 본인 기여와 팀 소통이다. 자격증 수·프로젝트 수가 위 역량을 입증하는 공통 기준은 아니다.

## 포트폴리오 문서와 마지막 페이지

권장 제출 구조는 소개/요약 → 개인 프로젝트 개요·핵심 사례 → 협업 프로젝트 개요·본인 사례 → 기타 경험·학력·자격·어학이다. 본문 분량은 사례 강도와 지원처 양식에 맞춘다. 요약만 읽어도 핵심 역할과 결과가 남고, 링크는 세부 근거를 확인하는 용도로 둔다.

현재 「취준생 대부분 포트폴리오를 잘못 만들고 있습니다」 원문에는 마지막 페이지의 자격·학력 배치 지침이 없다. 사용자가 언급한 다른 생각등대 영상의 제목/링크를 요청했다. 다음 마지막 페이지 구성은 Codex의 제안이며 영상 지침으로 귀속하지 않는다.

사용자는 영상 확인은 일단 넘어가고 나중에 출처를 찾아 주기로 했다. 아래 표는 보류한 페이지의 참고 초안이며 이번에 영상 기준으로 확정하지 않는다.

| 항목 | 넣을 내용 | 근거/배치 원칙 |
|---|---|---|
| 학력 | 학교·전공·재학/졸업예정·기간, 필요한 경우 학점 | 확정한 졸업 시점과 성적표. 지원 양식의 필수 항목은 이력서에도 기입 |
| 정처기·SQLD | 취득 자격명·취득일, 필기 합격만 있다면 정확한 단계 | 최종 취득과 준비 중을 구분. 이상형 기획의 목표 자격과 제출용 사실을 구분 |
| 어학 | TOEIC/토익스피킹 등 실제 시험명·점수/등급·응시일 | '토스'가 토익스피킹을 뜻하는지는 해석을 밝히고 성적·유효 여부 확인 |
| 인턴·실무 | 기관·기간·역할·직접 기여·결과 | 직무 관련 경험이 강하면 앞쪽의 경력/경험 영역으로 올림. 연구·교육·팀 프로젝트를 인턴으로 바꾸지 않음 |
| 수상·활동 | 검증한 상명·수여기관·일자, 교육/리딩에서 바꾼 일 | 실제 결과와 본인 역할. 참여를 수상으로 표현하지 않음 |
| 학습 기록 | 설명할 수 있는 책·구현·실험 연결이 필요할 때만 짧게 | 코테·SQL '공부 중'을 대표 성과처럼 넣지 않음 |

빈 페이지를 채우기 위해 없는 자격·인턴을 만들거나 모든 계획을 나열하지 않는다. 이상형 기획에서는 `[관련 인턴/현장실습에서 실제 업무 개선]` 같은 목표 상태를 둘 수 있다. 실제 제출본에는 확인한 사실만 들어간다. 자격·어학의 채용 가점·필수 여부와 졸업 자격은 지원 당시 공식 공고로 판단한다.

## 현재 포맷의 판정과 다음 결정

**이체·원장 중심에 동시성·부분 실패·멱등 재시도·대사를 연결하는 포맷을 유지하는 것이 적합하다.** 정확성·온라인 처리·SQL 데이터 처리·실패 복구를 하나의 업무 흐름에서 설명할 수 있기 때문이다. 다만 rollback은 기본 기능 소개로 끝내지 않고 실패 조건과 저장 상태의 증거를, 대사는 JOIN 구현을 넘어 추적·중단·재처리를, 성능은 정확성을 함께 지킨 결과를 보여줘야 한다.

후속 작업은 개인·협업 프로젝트의 제출 형태 이상형을 먼저 작성하고 그 기준으로 협업 후보를 비교하는 것이다. 개인 프로젝트의 최종 데이터 규칙과 대사 자료의 업무 의미도 구체화한다. 마지막 페이지 영상 출처는 사용자가 나중에 제공할 때 다시 검토한다. 현업 검토 뒤 구현 범위를 정한다.
