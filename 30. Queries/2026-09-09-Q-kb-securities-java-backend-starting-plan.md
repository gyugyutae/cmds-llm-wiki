# KB증권·금융권 Java 백엔드 시작 계획

## 목표와 기한

2027년 8월 졸업 전까지 KB증권을 포함한 국내 증권사·은행·핀테크의 Java 백엔드 인턴 또는 신입 취업을 달성한다. 증권사만 기다리지 않고 금융 IT 자회사, 결제사, 금융 솔루션사와 실무형 인턴까지 지원하되, 포트폴리오 서사는 `정확성과 복구 가능성을 검증한 Java 금융 주문 백엔드`로 고정한다.

## 2026-09-09 현재 기준선

### 사용자 자기보고로 확인된 사실

- Python으로 코딩테스트를 계속 공부하고 있으며, 현재 가장 자신 있게 말할 수 있는 역량은 코딩테스트다.
- Java는 아직 할 줄 모르며 Spring Boot도 시작 전이다.
- SQL 문을 직접 작성하는 데 자신이 없고 별도 학습을 시작하지 않았다.
- `JOIN`, 인덱스, 트랜잭션과 격리 수준, 동시 주문, 테스트 코드, Docker를 현재 설명하거나 구현하지 못한다.
- TOEIC은 730점이고 TOEIC Speaking을 추가할 계획이다.
- SQLD와 정보처리기사를 취득할 계획이다.
- 면접에서 직접 설명할 수 있는 포트폴리오가 현재 없다.
- 《스프링 부트와 AWS로 혼자 구현하는 웹 서비스》를 이용해 Java·Spring·배포를 학습하고 모의 증권거래 프로젝트로 확장하려 한다.
- AI 자동완성과 직접 코딩을 함께 사용하되 자신의 의도와 판단을 유지하는 학습 방식을 원한다.

### 현재 병목에 대한 해석

가장 큰 병목은 스펙 개수가 아니라 `Java + SQL + Spring으로 직접 구현하고 설명·수정·검증한 증거`의 부재다. 어학과 자격증은 서류 보완재지만 이 병목을 대신하지 못한다. 반대로 코딩테스트 학습 경험은 문제 분해와 반복 훈련 습관이라는 출발 자산이다.

## 우선순위

| 순서 | 할 일 | 완료 증거 |
|---:|---|---|
| 1 | Java 기초 | 계좌·주문 콘솔 프로그램과 JUnit 테스트 |
| 2 | SQL·관계형 DB | 직접 작성한 JOIN, 제약조건, 인덱스와 `EXPLAIN` 기록 |
| 3 | Spring Boot 기초 | 회원·계좌·주문 REST API와 통합 테스트 |
| 4 | 금융 주문 MVP | 잔액·보유수량 검증, 매수·매도, 주문·거래내역 |
| 5 | 정합성 심화 | 중복 주문 방지와 동시 주문 테스트, 잠금 선택 기록 |
| 6 | 운영 증거 | Docker, CI, 배포, 로그, 부하 테스트와 전후 수치 |
| 7 | 지원 산출물 | README, 2분 설명, 이력서 bullet, 지원 기록표 |
| 8 | 보완재 | SQLD, 정보처리기사, TOEIC Speaking |

자격증 공부 때문에 프로젝트 시작을 미루지 않는다. SQLD는 SQL 실습과 묶고, 정보처리기사와 어학은 정해진 시험 기간에 한정한다.

## 교재 사용법

《스프링 부트와 AWS로 혼자 구현하는 웹 서비스》는 웹 요청부터 DB, 테스트와 배포까지 전체 흐름을 처음 연결하는 교재로 사용한다. 원본 예제를 완성하는 것은 학습 증거이지 대표 포트폴리오가 아니다.

1. 책의 예제를 한 번 실행한다.
2. 각 계층과 설정의 역할을 자기 말로 기록한다.
3. 현재 지원되는 Java·Spring Boot·JUnit 환경과 다른 점을 마이그레이션 로그로 남긴다.
4. 책을 덮고 별도 저장소에서 계좌·주문 API를 다시 설계한다.
5. 기능마다 정상·실패·경계 테스트를 직접 추가한다.

## 첫 모의 증권거래 MVP

### v1 범위

- 회원과 모의 계좌
- 초기 예수금
- 종목과 단순 현재가
- 시장가 매수·매도
- 잔액과 보유수량 검증
- 주문·거래내역 조회
- 표준 예외 응답
- 단위·통합 테스트
- 실행 가능한 배포 환경

실시간 시세, 실제 거래소 연동, MSA, Kafka, Kubernetes는 v1에 넣지 않는다. 먼저 단일 애플리케이션에서 정합성을 증명한다.

### v2 핵심 질문

> 잔액이 10만 원인 한 계좌에서 8만 원짜리 주문 두 개가 동시에 들어올 때 한 건만 성공하도록 어떻게 보장할 것인가?

이 시나리오를 재현하는 테스트, 선택한 잠금 방식, 실패했던 구현, 수정 전후 결과를 대표 포트폴리오 증거로 만든다. 이후 멱등키를 이용한 중복 요청 방지, 주문 취소, 인덱스와 실행계획, Docker와 부하 테스트를 추가한다.

## AI 사용 계약

키 입력량을 사람 50%, AI 50%로 맞추지 않는다. 다음 조건을 만족하면 AI가 작성한 코드도 학습과 프로젝트에 사용할 수 있다.

- 요구사항, 불변조건과 완료 기준을 먼저 직접 정의한다.
- AI에 완성 코드보다 힌트, 반례, 리뷰와 테스트 후보를 먼저 요청한다.
- 채택한 코드의 요청 흐름과 상태 변화를 설명한다.
- 오류를 직접 재현하고 디버깅한다.
- 정상·실패·경계·동시성 테스트를 추가한다.
- 핵심 기능을 다음 날 다시 설명하거나 일부 재구현한다.
- `AI gave / I decided / I verified / Unknown`을 작업 로그에 남긴다.

설명하거나 수정할 수 없는 AI 생성 기능은 포트폴리오 완료 범위로 계산하지 않는다.

## 공모전과 금융 도메인의 위치

한이음 입상이나 핀테크 경진대회 수상은 외부 평가, 협업과 완주를 보여주는 강한 보조 증거지만 필수 합격 조건은 아니다. 수상 여부보다 본인 기여와 기술 판단을 설명할 수 있는지가 중요하다. 완성 프로젝트, 실무형 인턴, 오픈소스 기여와 재현 가능한 성능 개선으로 대체할 수 있다.

금융 도메인 공부는 인턴보다 무조건 우선하지 않는다. 실제 관련 인턴을 얻을 수 있다면 그 경험의 가치가 더 클 수 있다. 도메인을 일찍 넣는 이유는 별도의 금융 암기가 아니라 주문·잔액·중복·결제 같은 제약이 Java·DB 프로젝트를 일반 CRUD와 구분하고 지원 동기를 일관되게 만들기 때문이다.

## 첫 8주 실행안

| 기간 | 학습 | 산출물 |
|---|---|---|
| 1~2주 | Java OOP, 컬렉션, 예외, enum, JUnit | 콘솔 계좌·주문 프로그램 |
| 3~4주 | SQL CRUD, JOIN, PK·FK·UNIQUE, 인덱스 기초 | 모의투자 ERD와 SQL 풀이 로그 |
| 5~6주 | Spring MVC, DI, JPA, 검증, 예외 처리 | 회원·계좌·종목 REST API |
| 7~8주 | 주문 트랜잭션과 테스트 | 시장가 주문·잔고 조회 MVP |

코딩테스트는 Python으로 주간 루틴을 유지한다. Java 기본 문법이 익숙해진 뒤 같은 문제 일부를 Java로 다시 풀어 채용 언어 전환 가능성을 확인한다.

## 8주 후 판정 기준

- [ ] Java로 계좌와 주문 객체를 직접 설계했다.
- [ ] JOIN을 사용한 조회 쿼리를 직접 작성했다.
- [ ] REST 요청이 Controller-Service-Repository-DB를 통과하는 흐름을 설명한다.
- [ ] 매수 주문과 잔액 변경의 트랜잭션 경계를 설명한다.
- [ ] 잔액 부족과 보유수량 부족 테스트가 있다.
- [ ] 프로젝트를 새 환경에서 실행하는 README가 있다.
- [ ] 핵심 코드를 수정하고 실패 원인을 추적할 수 있다.
- [ ] AI 기여와 본인 판단·검증 범위가 기록되어 있다.
