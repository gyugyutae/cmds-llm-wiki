# 코딩테스트 AI 학습 루프

## Short Answer

문제 풀이 중 막혔을 때 AI를 쓰는 기준은 `정답을 받는가`가 아니라 `내 사고의 다음 한 칸을 여는가`다.

가장 좋은 사용법은 AI를 정답 생성기가 아니라 다음 네 역할로 제한하는 것이다.

| 상황         | AI 역할          | 금지할 것          |
| ---------- | -------------- | -------------- |
| 문제 이해가 막힘  | 요구사항/제약 재해석 튜터 | 전체 풀이 코드 요청    |
| 접근법이 안 떠오름 | 힌트 제공자         | 알고리즘 이름을 바로 요구 |
| 디버깅이 막힘    | 반례/추적 질문자      | 수정 코드 통째로 받기   |
| 엣지케이스 실패   | 테스트케이스 생성기     | 원인 설명 없이 패치 받기 |
| 풀이 후       | 코드 리뷰어/복잡도 리뷰어 | 이해하지 않은 최적화 복붙 |

---

## 1단계: 막혔을 때 바로 답을 묻지 않는다

먼저 본인이 아래 네 줄을 적는다.

```text
내가 이해한 문제:
입력 크기/제약:
지금 떠오른 접근:
막힌 지점:
```

그다음 AI에게는 정답이 아니라 질문을 요청한다.

```text
정답이나 코드 말고, 내가 다음으로 생각해야 할 질문 3개만 줘.
문제의 핵심 제약과 관찰 포인트를 중심으로 힌트만 줘.
```

이 방식은 [[Human-AI Knowledge Boundary]]를 지키는 데 좋다. AI가 만든 풀이를 내 지식처럼 착각하지 않고, 내가 직접 생각할 여지를 남긴다.

---

## 2단계: 접근법이 안 떠오를 때는 힌트 레벨을 나눈다

AI에게 한 번에 풀이를 요구하지 말고 힌트를 단계별로 받는다.

```text
힌트를 3단계로 줘.
1단계는 관찰만, 2단계는 사용할 수 있는 자료구조 후보, 3단계는 알고리즘 방향.
코드는 절대 쓰지 마.
```

권장 순서:

1. 관찰: 정렬이 필요한가, 중복을 어떻게 볼 것인가, 그래프/트리/구간 문제인가.
2. 자료구조 후보: 해시, 스택, 큐, 힙, 그래프, DP table 등.
3. 알고리즘 방향: BFS/DFS, 이분탐색, 투 포인터, greedy, DP 등.
4. 직접 구현.
5. 구현 후 AI 리뷰.

---

## 3단계: 디버깅은 "내 코드의 실행 추적"으로 쓴다

디버깅할 때 AI에게 수정 코드를 달라고 하면 학습량이 줄어든다. 대신 현재 코드와 실패 케이스를 주고, 실행 흐름을 추적하게 한다.

```text
아래 코드를 고쳐주지 말고, 이 입력에서 변수 값이 어떻게 변하는지 단계별로 추적해줘.
어느 줄에서 내 의도와 달라지는지만 알려줘.
마지막에 수정 방향을 한 문장으로만 말해줘.
```

이렇게 하면 내가 직접 고치는 부분이 남는다. [[AI-Augmented Developer Positioning]] 관점에서도 "AI가 고쳐줬다"가 아니라 "AI를 디버깅 보조로 쓰고 최종 수정은 내가 판단했다"로 기록할 수 있다.

---

## 4단계: 엣지케이스 실패는 AI를 테스트 생성기로 쓴다

엣지케이스에서 실패하면 AI에게 원인부터 묻지 말고, 테스트 설계를 시킨다.

```text
내 접근법이 실패할 수 있는 엣지케이스를 유형별로 만들어줘.
각 케이스마다 왜 위험한지만 설명하고, 정답 코드는 주지 마.
```

좋은 엣지케이스 분류:

- 최소 입력: 빈 배열, 길이 1, 노드 1개
- 중복: 같은 값 반복, 같은 간선, 같은 문자열
- 경계값: 최대/최소 숫자, 음수, 0
- 정렬 상태: 이미 정렬됨, 역정렬, 랜덤
- 연결성: 그래프 disconnected, cycle, self-loop
- 성능: O(n^2)가 터지는 최대 입력
- 문제 조건의 예외: 불가능한 경우, 답이 여러 개인 경우

---

## 5단계: 풀이 후에는 AI에게 리뷰를 받는다

풀고 난 뒤에는 AI 활용 가치가 커진다. 이때는 정답을 받아도 학습 소유권이 크게 흔들리지 않는다. 이미 내 풀이가 있기 때문이다.

```text
내 풀이를 리뷰해줘.
1. 시간/공간 복잡도
2. 놓친 엣지케이스
3. 더 간단한 구현
4. 더 좋은 알고리즘이 있다면 핵심 아이디어만
5. 내가 이 문제에서 배워야 할 패턴 한 줄
```

중요한 것은 AI의 리뷰를 그대로 믿지 않는 것이다. 반례를 직접 실행하고, 더 좋은 풀이가 나오면 "왜 내 풀이보다 나은지"를 한 문장으로 설명할 수 있어야 한다.

---

## 기록 템플릿

```text
Problem:
First attempt time:
Blocked at:
My hypothesis:
AI used for:
AI gave:
I changed:
Edge cases added:
Final complexity:
Lesson:
```

`AI used for`에는 `hint`, `trace`, `edge-case generation`, `review`처럼 역할을 적는다. `AI gave`와 `I changed`를 분리하면 AI 활용과 본인 판단의 경계가 남는다.

---

## 좋은 프롬프트 모음

```text
정답 말고 이 문제를 풀기 위해 봐야 할 핵심 제약 3개만 짚어줘.
```

```text
내 접근법이 O(n^2)인데, 입력 크기상 위험한지 판단해줘. 대안 알고리즘 이름은 아직 말하지 말고 병목만 설명해줘.
```

```text
이 코드의 실패 원인을 고치지 말고, 실패 입력에서 변수 변화만 표로 추적해줘.
```

```text
내 풀이가 깨질 수 있는 반례 5개를 만들어줘. 각 반례의 의도만 설명하고 코드는 주지 마.
```

```text
내가 푼 뒤에 읽을 수 있도록, 이 문제의 핵심 패턴을 한 문장으로 요약해줘.
```

## Rule Of Thumb

- 15분 막힘: 문제 재해석/제약 질문만 AI 사용
- 30분 막힘: 힌트 1단계 사용
- 45분 막힘: 자료구조 후보까지 허용
- 60분 이상 막힘: 풀이 방향을 보고, 코드는 직접 구현
- 구현 후 실패: AI를 trace/반례 생성기로 사용
- 해결 후: AI 리뷰를 받고 회고 작성

이 기준을 쓰면 코딩테스트가 `AI로 답을 얻는 시간`이 아니라 `내 사고를 한 단계씩 확장하는 훈련`이 된다.

---

## Quality Gaps

- 실제 풀이 로그가 아직 없으므로, 이 루프가 김규태에게 얼마나 효과적인지는 2-4주 기록 후 확인해야 한다.
- 목표 회사별 전형이 AI 사용을 허용하는지 여부는 별도 확인이 필요하다. 실전 전형에서는 플랫폼/회사 규칙을 우선한다.
